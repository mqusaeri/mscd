# M2-11 handoff: controls, evidence and phases forms

M2-11 adds the forms that let a team keep its Statement of Applicability, its evidence and its implementation plan in the browser, on the screen host of M2-01. Three web folders hold everything: `controls-edit` (the entry panel of the Controls detail and "Add control or requirement"), `evidence-edit` (New evidence with its first file, the evidence panel with its targets, and the freshness limits) and `phases-edit` (Start and Record blocker on the Phase board). The package's own work changed no server code, shared contract, generated view, shared web file or Milestone 1 test; the third follow-up added, on the orchestrator's assignment (item 2 of "Needs from the orchestrator"), the optional `targets` of `EvidenceItem` and the server code that fills it. The end-to-end check of the "Clauses 4 to 10" group of M2-01 is in `e2e/api-only/controls-edit.spec.js`.

## Deviations

1. **Page actions and claims on built-in screens show their forms in API builds only.** `e2e/shell.spec.js` (owned by M2-01) counts the page actions of each built-in screen and clicks each for its Milestone 1 toast, and `e2e/phases.spec.js` expects the toast of Record blocker. As M2-08 did for "Import" (its deviation 1) and M2-09 for the repository claims, "New evidence" and "Freshness limits" show in API builds only, and the claims `controls.add` and `phases.recordBlocker` keep their Milestone 1 toasts in the sample build. The sample build reaches New evidence through "Define evidence" and the freshness limits through the evidence panel. When the orchestrator lets `shell.spec.js` count package page actions, remove `ctx.mode === 'api' &&` from `inApi` in `evidence-edit/actions.ts` and the sample branch of `addControl` in `controls-edit/actions.ts`.
2. **Resolved in the third follow-up.** Remove target needed the id of each target, which no read route gave. `evidence.targets.remove` takes the target's uuid; the snapshot carries only the first target of each system and `readmodel.evidence.list` none. The panel lists the first target of each system and the targets added in the session (their id comes from `evidence.targets.create`); Remove shows "Remove is not available for this target yet." for a target without an id. The web already read a `targets` member of the evidence list rows (`targetsOfRow`), so the server change of item 2 enabled Remove for every target without a web change, and the API spec now checks the full brief item by itself.
3. **The sample build keeps activity statuses.** The sample data source has no command that starts an activity and only acknowledges a blocker (Milestone 1), and `mutate` does not take activities, so Start is disabled there with its reason. A status change made by a Milestone 1 sample command in the session (for example Mark complete) also wins over `mutate`, so the sample Reject and Mark not applicable work on entries whose status comes from the sample data.
4. **Forms open in the host layer.** The brief places the forms in the detail extensions; they open from there, but render in the host layer, because a save can move the record out of the list and close the drawer (a Mark not applicable with its BR-03 warning would vanish).
5. **The freshness limits of the sample build do not change the sample's bands.** The sample derives freshness with the built-in limits; the limits set on screen are kept for the session. In API builds the bands follow the limits at once.
6. **Resolved: the orchestrator applied item 1 (9079ebb), and the API test of "Later" runs.** New evidence with "Later" waited for a shared fix in API builds. The form offers "Later" as the brief allows evidence defined before its first record exists, but the load that followed broke the built-in screens until `wire.ts` gave the empty repository slug an entry (item 1 below). The API test of "Later" was marked `test.fixme` until then; the third follow-up removed that line.
