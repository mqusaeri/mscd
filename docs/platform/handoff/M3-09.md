# M3-09 handoff: export and deletion screens

M3-09 builds the screens of M3-02 and M3-03 (MILESTONE-3 C.2, D.2, D.4, D.5): the new host screen Organisation export for Tenant Admins with the banner of the read-only period after a contract ends, and the operator console's columns "Read-only until" and "Deletion on", the Export and Deletion tabs of the organisation drawer, and the moves of Milestone 3 J.8 in the Status tab, "Reopen for export" included. No server, shared or generated file changes.

## Deviations

1. The organisations of the operator console's sample, with their exports and deletions, are one store of the browser session in `ops/sample-orgs.ts` (`sampleServiceOrgs`), and `org-export/sample.ts` reads it, so a move or an export started in the console shows in Organisation export, and the banner shows after the sample operator moves the sample organisation to offboarding. The sample organisation is active by default, so no other sample spec sees the banner.
2. The banner sits at the bottom left of the page column (its left edge follows the column, so it never covers the sidebar), because the invitation and confirmation banners take the bottom right corner and stack there.
3. The console shows the date of an instant as its day in the browser's time zone, as `whenText` shows its time; the new data attributes (`data-read-only-until`, `data-deletion-on`, `data-deletion-date`, `data-offboarding-end`) carry the same day as `YYYY-MM-DD`. The new deletion date is the chosen day at the local time of day of the current date.
4. Texts of M2-S12 that said archived is final changed with J.8: `meaningArchived`, `finalStatus` (now for deleted), `effectOffboarding3`, `effectOffboarding4`, and `effectArchived3` and `effectArchived4` replaced by `effectArchivedExports` and `effectArchivedDeletion`. The actor of a move without a person (`commandLine`) reads "MSCD or an operator command", because `org.lifecycle` now archives organisations.
5. The manifest and the certificate are saved without a name of their own, so the browser takes the server's (Content-Disposition); a part keeps the name of the detail, which is the server's too. The sample build names its files itself (blob addresses have no headers) and names its parts `.txt`, since they are text files that stand in for the archive.
6. Chromium sends a download started by a link past `page.route`, so the API specs check the address of each download (and a part's file name, which the link carries); the bytes and their `X-MSCD-SHA256` header are covered by `apps/server/test/int/org-export/requests.test.ts` and the certificate by `apps/server/test/int/org-deletion`. The sample spec reads the saved files and hashes them.
7. The ops drawer's tab is still local state of the drawer (no screen address), as in M2-S12.
8. The screens cannot read the server's `lifecycle` profile keys, so where a text names a period or size that a key sets, it says "by default": the read-only period (`offboarding_days`, 30), the deletion after archiving (`deletion_grace_days`, 30), the download period of an export (`export_link_days`, 7, also the 7 more days of a final export after a move back to active) and the part size (`export_part_bytes`, 2 GB). Where the server sends the value, the screen shows it: the deletion form's earliest day comes from `earliestAllowed` (`deletion_min_grace_days`), and the dates of the read-only period, the deletion and each export's "Downloadable until" come from the server. The 7 read-only days after "Reopen for export" and the 7 days a request waits for a decision are fixed on the server and stay without "by default".
9. "Download certificate" in the API build saves through the api's link, so the browser alone knows whether the file arrived; the toast reads "Certificate download started" in both builds, and a refusal of the link shows as the browser's failed download.
