# M2-03 handoff: pack format and upgrade path

M2-03 builds the pack format of engine 1.1.0 (E.1), the reference schema `ref/0002_milestone2.sql` (D.3, J.7), the D2-09 seeder, the `applicability.sync` job with the retry of skipped mappings (E.3), and the patch step of the pack versions. It changes no pack content and no sample: `mscd-data.js`, the seed snapshot and the Milestone 1 specs are as they were (the clause 10 fixes are M2-04). As lockfile owner it also raised the server version to 1.1.0, `zod` to 4.6.6 and `undici` to 7.30.1.

## Deviations

1. **Content references are warnings in the Milestone 1 pack versions only.** E.1 asks the validator and `parsePackDatasets` to check cycle requirement codes, `clause_at_risk`, `output_document_code` and `documented_info.template_code`. The Milestone 1 content has 97 such references that do not resolve (for example cycle requirement `8.2.2` and templates `POL-01` and `IMS-01` in ISO 22301), and the brief forbids a content change in this package. So they are warnings (validator: 97, one per row; `mscd-pack`: 66, grouped by document code) only in a version of a Milestone 1 pack below its content step (ISO27001-2022 1.3.0, ISO9001-2015 1.5.0, ISO9001-2026 0.10.0, ISO22301-2019 1.1.0, ISO37001-2016 1.1.0, ISO37001-2025 0.7.0, the minor step of E.3) that lists no documented information. The cut-over is fixed by version, in `@mscd/pack-tools` and in the validator (a pack-tools test keeps the two tables equal), so a later version with an empty `documented_info.csv` cannot skip the check; a pre-release of the content step (1.3.0-rc.1) is strict too, and every other pack is strict at any version. M2-04 must resolve every reference when it moves the packs to the minor step: `validate-sources.mjs` and `build-all` then fail on any reference that does not resolve.
2. **Versions live in `packs/content/<pack_id>/manifest.json`.** The patch step needs new versions with no sample change. The content manifest holds only `pack_version`; the extractor refuses a version lower than the sample's, and the sample cross-check keeps the sample's own version.
3. **Sync of installations made outside the worker.** E.3 says the installer queues the job. `migrate` step 5 and `mscd-server packs install` run with no job queue, so pending systems are read from the database (installations and `pack.content_synced` entries), and the worker start and the daily `packs.lifecycle` queue what is waiting. The worker's own `pack.install` queues at once.
4. **Skipped mappings are kept in the `pack.installed` audit entry.** R-14 allows no new table for them. The installer of the target pack reads the entries of the other installed packs and writes the rows that now resolve.
5. **Dropped activity and prep task templates stay in `ref`.** E.1 accepts such a version and keeps the activities created from it. The installer has no delete right on `ref` and the format has no retired flag for templates, so the old template rows stay and new systems still see them. See the follow-ups.
6. **`engine_min_version` 1.1.0 and pre-release servers.** `engineVersionSatisfies` lets 1.1.0-rc.1 install packs that need 1.1.0 (the risk row of section I on image tags). `build-bundle.sh` (not owned here) still treats 1.1.0-rc.1 as lower than 1.1.0 and refuses M2-S01 acceptance line 5 as written; see the acceptance notes and the follow-ups. Image builds without `--build-arg VERSION` (demo, smoke, E2E) take the package version 1.1.0, and a tag such as `smoke` given as the version is not compared.
7. **The sync adds entries for new targets only (E.3), so Milestone 1 systems are not filled in.** The sync seeds only the `newTargets` of the waiting installations, and the seeder counts a deleted entry as held. A system created before Milestone 2 keeps the entries its team chose: the patch step 1.2.1 that `migrate` installs adds nothing (no new row), and the content step of M2-04 adds entries only for the rows new in it. The clause rows that already existed (for an ISMS, `cl-4.1` to `cl-10.2` of D2-09) get no entry on such a system; its team adds them with the picker (`applicability.targets`). If the product owner wants existing systems filled in with every D2-09 target once, that needs a separate one-time action that calls the seeder without `only` (it still skips deleted entries). An installation without a change summary (made by a Milestone 1 build after the system was created) adds no entry; its new cycle requirements are still added to open cycles, as before.
8. **`removed.csv` keeps activity numbers contiguous.** E.1 lets `removed.csv` drop any row the sample keeps. The source validator still asks for phase and activity numbers contiguous from 1 (a Milestone 1 rule), so activities go as a whole last phase or as the last activities of a phase. Removing only `9.1` writes sources that `validate-sources.mjs` refuses ("phase 9 activity numbers are not contiguous from 1"). `mscd-pack` and the installer accept a gap, so an installed pack may still drop any activity template (the upgrade test drops 9.7). The E.4 case, the whole ISO 9001:2026 transition phase (9.1 to 9.14), validates; `packs/README.md` states the rule and `source-scripts.test.ts` covers both cases.

## Follow-ups

- **Version expectations outside this package (for the orchestrator, blocks acceptance lines 8 and 9).** The version bump changes four test files that M2-03 does not own: `apps/server/test/int/seed/demo-template.test.ts` (installed versions), `seed/scripts.test.ts` (pack file names), `parity/snapshots.test.ts` (the PACKS card versions of the Milestone 1 snapshots, now one patch above the sample) and `management-systems/management-systems.test.ts` (1.2.0). A patch that changes only these expectations is ready in the scratchpad of this session (`m2-03-version-tests.patch`, `git apply --check` still passes in the third round). In a copy of the work tree with the patch applied, acceptance line 8 and `test/int/management-systems` pass (see "Acceptance"). Its parity part raises every sample PACKS version by one patch step: M2-04, which owns `test/int/parity/**` and moves the sample to the minor step, must remove that transform, or the parity test expects 1.3.1 against 1.3.0.
- **`build-bundle.sh` and pre-release versions (for the orchestrator or M2-S01).** `check_pack_versions` compares the full version, so `--version 1.1.0-rc.1` fails before any build with "Version 1.1.0-rc.1 is lower than the server version the packs need", while the server accepts 1.1.0-rc.1 for 1.1.0 packs. A one-line patch (`semver_below "${VERSION%%-*}" "$min"` plus a comment) is ready (`m2-03-build-bundle-prerelease.patch`, `git apply --check` passes) and matches the server rule. The other choice is to change acceptance line 5 of M2-S01 to a version such as 1.1.1-rc.1, which this round ran (see below).
- **M2-04 acceptance (for the orchestrator).** With the cut-over of deviation 1, `validate-sources.mjs` and `build-all` fail on any unresolved content reference once a pack is at its minor step. A case that proves it could be added to M2-04's acceptance, for example a copy of a pack folder with one `output_document_code` changed to an unknown code, on which `node packs/scripts/validate-sources.mjs --dir <copy>` must exit 1.
- **`test/int/pack-upgrade/**` after M2-04 (for the orchestrator).** The upgrade test builds its fixture versions (1.2.2 to 1.2.5) from the development packs and checks the Milestone 1 content (117 targets, 10.3 retired and 10.1 retitled by the fixture). M2-04's content step (1.3.0, 10.3 retired, 34 requirement rows) makes these versions downgrades and changes the counts, and M2-04 does not own this folder. Add it to M2-04's Owns, or let this package's owner adapt it then (fixture versions above the content step, counts from `seedTargets`, a fixture change on rows that are still live).
- **Milestone 1 systems and D2-09 clause entries (product owner).** The sync adds only new targets (deviation 7). If existing systems should get every D2-09 target once, that is a separate action that calls `seedApplicability` without `only` (it still skips deleted entries).
- **Readers of retired rows (M2-05, M2-07, M2-11).** Retired rows are in `ref` with `retired = true`. Pickers, readiness and the clause lists still show them until their owners filter them and show "No longer in the standard" on an existing entry.
- **M2-06** calls `seedApplicability` (without `only`) when a system is created and audits `applicability.seeded`. A deleted entry counts as held, which makes no difference for a new system. The upgrade test removes the entries of its systems after creation, so it keeps working when creation seeds them.
- **Catalogue-sourced mappings.** `ref.requirement_mapping.source_catalogue_item_id` is written, but the rules in `risk-registers/rules.ts` and `files/file-commands.service.ts` read only requirement sources.
- **Dropped templates.** A retired flag on activity and prep task templates (or a delete right for the installer) would hide them from new systems (deviation 5).
- **Readiness job key.** The sync queues `readiness.recompute` with the singleton key `rr:<org>:<ms>`; M2-05 should keep the same key or change it here.
- **Web image gate.** See the M2-S01 lines below: the web image still fails the gate on this host (Alpine mirrors blocked).
