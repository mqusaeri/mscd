# M2-03 handoff: pack format and upgrade path

M2-03 builds the pack format of engine 1.1.0 (E.1), the reference schema `ref/0002_milestone2.sql` (D.3, J.7), the D2-09 seeder, the `applicability.sync` job with the retry of skipped mappings (E.3), and the patch step of the pack versions. It changes no pack content and no sample: `mscd-data.js`, the seed snapshot and the Milestone 1 specs are as they were (the clause 10 fixes are M2-04). As lockfile owner it also raised the server version to 1.1.0, `zod` to 4.6.6 and `undici` to 7.30.1.

## Deviations

1. **Content references are warnings until a pack lists its documented information.** E.1 asks the validator and `parsePackDatasets` to check cycle requirement codes, `clause_at_risk`, `output_document_code` and `documented_info.template_code`. The Milestone 1 content has 97 such references that do not resolve (for example cycle requirement `8.2.2` and templates `POL-01` and `IMS-01` in ISO 22301), and the brief forbids a content change in this package. So a pack with no `documented_info.csv` rows reports them as warnings (validator: 97, one per row; `mscd-pack`: 66, grouped by document code), and a pack with documented information rows treats them as errors. M2-04 adds documented information to every pack, so from M2-04 on they are errors in every pack.
2. **Versions live in `packs/content/<pack_id>/manifest.json`.** The patch step needs new versions with no sample change. The content manifest holds only `pack_version`; the extractor refuses a version lower than the sample's, and the sample cross-check keeps the sample's own version.
3. **Sync of installations made outside the worker.** E.3 says the installer queues the job. `migrate` step 5 and `mscd-server packs install` run with no job queue, so pending systems are read from the database (installations and `pack.content_synced` entries), and the worker start and the daily `packs.lifecycle` queue what is waiting. The worker's own `pack.install` queues at once.
4. **Skipped mappings are kept in the `pack.installed` audit entry.** R-14 allows no new table for them. The installer of the target pack reads the entries of the other installed packs and writes the rows that now resolve.
5. **Dropped activity and prep task templates stay in `ref`.** E.1 accepts such a version and keeps the activities created from it. The installer has no delete right on `ref` and the format has no retired flag for templates, so the old template rows stay and new systems still see them. See the follow-ups.
6. **`engine_min_version` 1.1.0 and pre-release servers.** `engineVersionSatisfies` lets 1.1.0-rc.1 install packs that need 1.1.0 (the risk row of section I on image tags). `build-bundle.sh` (not owned here) still treats 1.1.0-rc.1 as lower than 1.1.0 and refuses M2-S01 acceptance line 5 as written; see the acceptance notes and the follow-ups. Image builds without `--build-arg VERSION` (demo, smoke, E2E) take the package version 1.1.0, and a tag such as `smoke` given as the version is not compared.
7. **The first update fills in the D2-09 entries of existing systems.** The sync uses `seedApplicability`, as the brief asks, and the seeder adds every target that has no entry yet. A system created before Milestone 2 (Annex A entries only, for example) therefore also gets its missing clause entries on the first update after the upgrade (for an ISMS, the patch step 1.2.1 that `migrate` installs), with one notice that lists them. Demo organisations are skipped. If the product owner wants only the rows new in the version, the sync can pass the `added` codes of the change summary to the seeder.

## Follow-ups

- **Version expectations outside this package (for the orchestrator).** The version bump changes four test files that M2-03 does not own: `apps/server/test/int/seed/demo-template.test.ts` (installed versions), `seed/scripts.test.ts` (pack file names), `parity/snapshots.test.ts` (the PACKS card versions of the Milestone 1 snapshots, now one patch above the sample) and `management-systems/management-systems.test.ts` (1.2.0). A patch that changes only these expectations is ready (`m2-03-version-tests.patch`, `git apply --check` passes); with it, the four files pass (40 tests).
- **`build-bundle.sh` and pre-release versions (for the orchestrator or M2-S01).** `check_pack_versions` compares the full version, so `--version 1.1.0-rc.1` fails before any build with "Version 1.1.0-rc.1 is lower than the server version the packs need". A one-line patch (`semver_below "${VERSION%%-*}" "$min"` plus a comment) is ready (`m2-03-build-bundle-prerelease.patch`) and matches the server rule. The other choice is to change acceptance line 5 of M2-S01 to a version such as 1.1.1-rc.1.
- **Readers of retired rows (M2-05, M2-07, M2-11).** Retired rows are in `ref` with `retired = true`. Pickers, readiness and the clause lists still show them until their owners filter them and show "No longer in the standard" on an existing entry.
- **M2-06** calls `seedApplicability` when a system is created and audits `applicability.seeded`.
- **Catalogue-sourced mappings.** `ref.requirement_mapping.source_catalogue_item_id` is written, but the rules in `risk-registers/rules.ts` and `files/file-commands.service.ts` read only requirement sources.
- **Dropped templates.** A retired flag on activity and prep task templates (or a delete right for the installer) would hide them from new systems (deviation 5).
- **Readiness job key.** The sync queues `readiness.recompute` with the singleton key `rr:<org>:<ms>`; M2-05 should keep the same key or change it here.
- **Web image gate.** See the M2-S01 lines below: the web image still fails the gate on this host (Alpine mirrors blocked).
