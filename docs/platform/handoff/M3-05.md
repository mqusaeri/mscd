# M3-05 handoff: read confirmation of policies

M3-05 builds D.7 in full. A document can ask for read confirmation; each approved version then goes to the people concerned, who open it and confirm that they have read and understood it. The Management System Manager follows the confirmations in "Policy read confirmations", reminds the people still pending, downloads the register as CSV and files it as a new file of an evidence item when the request closes. Each person confirms in "Policies to confirm", reached from a banner in the host layer, their task and their notification. In audit terms the register is the record that the policy was communicated and acknowledged (ISO/IEC 27001 A.5.1, clause 7.3 "Awareness" and 7.4 "Communication" of each standard).

## What was built

### Server (`apps/server/src/modules/acknowledgements/`)

| File | Content |
|---|---|
| `acknowledgement.service.ts` | `AcknowledgementService.openForApprovedVersion` (called by the approval, skips an empty audience) and `openRequest` (also called by `acknowledgement-requests.create`): refuses a second open request of the same version (409), takes the audience snapshot, closes the earlier versions' open requests (pending people `excused` with "Replaced by version X", their tasks cancelled; confirmations stay), inserts the request, one `acknowledgement` row, one task and one notification (`acknowledgement_requested`) per person, and audits `acknowledgement_request.created`. | `acknowledgement-requests.service.ts` | The six routes of the register: list (requests of documents that count in the system: linked to it, or organisation-wide; totals for every caller), create (current approved version only, audience and due days from the body or the document's settings; a document linked to the path system, or an organisation-wide document from any system, as the snapshot lists it in every system), get (person list only with `audit.pending.all` in full; Top Management gets totals, product decision 2), remind (409 when closed, already reminded today or nothing pending; audit `acknowledgement_request.reminded` with source `manager`), close (optional `fileGeneratedEvidence` of the register CSV into an evidence item of the path system in the same transaction, open tasks cancelled, audit `acknowledgement_request.closed`), export (formula-safe CSV through `toSafeCsv`, file name `read-confirmations-<code>-v<label>-<date>.csv`, audit `file.downloaded`) |
| `me-acknowledgements.service.ts` | `me.acknowledgements` (pending rows of open requests first, then rows settled in the last 180 days), `me.acknowledgements.open` (sets `opened_at` the first time; audits `acknowledgement.opened` with `via` and `first`, and `file.opened` with `via: acknowledgement`), `me.acknowledgements.confirm` (409 when confirmed, excused or closed; 422 `ACK-OPEN-FIRST` before opening; closes the task `done`; audit `acknowledgement.confirmed`). The open route answers: for a stored (vault or pass-through) file, the content route of a system where the person may read the object through the file routes (`via: content`), otherwise the content route with `via=acknowledgement` and a redirect token that names the person's acknowledgement row (`via: acknowledgement_token`, see `files/` below); for a file in a linked repository, the redirect token address when the person may read the object through the file routes, otherwise the provider's address from the gateway (`/v1/open-url`), where the person's own access applies. A row of a document the classification rule hides from the person (it became `restricted` or changed owner after the request opened) is left out of the list, and open and confirm answer 403 `acknowledgements.restricted` |
| `acknowledgement-file-grant.ts` | `acknowledgementFileGrant(trx, userId, acknowledgementId, objectId)`: the check behind a token of a read confirmation. It passes for the person's own row that is not excused (pending in an open request, or confirmed), when the request's version holds the object, the classification rule lets the person see the document and the person still holds an asked role in a system of the document, and answers that system: the task's while they hold an asked role there, else the request's, else another system the document counts in (a linked one, or any for an organisation-wide document or audience), by slug. | `acknowledgement-visibility.ts` | `classificationAllows(user, document)`: the SQL condition of the classification rule of F.7 on the read confirmation path. ## Deviations

1. `AcknowledgementService` inserts the tasks itself. `RuleTaskService` of `jobs/rule-tasks.ts`, which the brief names, does not fit: its input accepts only the rules `BR-10`, `BR-11`, `BR-15` and `BR-31`, the file is outside the Owns list, it writes one row at a time with the system as author, and an audience can hold hundreds of people. The insert writes the same columns (`source_rule = 'acknowledgement'`, `entity_type = 'acknowledgement'`, `entity_id` = the acknowledgement row, C.3) under the same `task_open_uq`, as one statement with the approver or manager as author.
2. `DocumentsService` takes `AcknowledgementService` as an `@Optional()` dependency: `ImportsModule` builds its own `DocumentsService` without the acknowledgements module, and bulk import does not open requests (an imported document has no approval).
3. Opening a stored (vault or pass-through) version without file rights goes through the existing content route with two optional query members, `via=acknowledgement` and the token `t`. The redirect route cannot carry it: it is declared as a 302 without a body, and R-14 allows no new route. The guard chooses the route's permission by `via` (`ms.read` with it, `storage.object.read` without it), and the service then checks the token and the row (`acknowledgementFileGrant`). The orchestrator assigned the three `files/` and contract files for this (see "Files outside the Owns list" above).
4. A request shows in every system its document is linked to, in every system for an organisation-wide document, and in the system recorded on the request (`requestVisibleIn`), as long as that system is still the document's primary one. "Ask for confirmation" takes an organisation-wide document from any system, since the snapshot lists it in every system; a document linked to other systems only stays 404. The cross-system fixture of `security/cross-system.test.ts` keeps its meaning: a QMS-only request does not show in the ISMS.
5. My Tasks links to "Policies to confirm" through a page action of My Tasks, shown while confirmations are open; its rows have no link of their own. A row's button lives in `apps/web/src/MscdApp.jsx`, which the acceptance of every package forbids changing, and the task item of `GET /tasks` (`TaskItem`, `packages/shared/src/api/ui.ts`, built in `read-model/derive/tasks.ts`) does not say which record or screen a stored task belongs to. Such a row's "Done" calls `tasks.complete`, which refuses with a message that names "Policies to confirm" (D.2). Follow-up 3 holds the patch for a link per row.
6. The document record of the read model has no `acknowledgement` member yet (read-model files belong to M3-04 in wave 3). The detail section reads the member when it is there and otherwise shows the settings saved in this page session, kept per organisation (switching organisation keeps the page, and pack codes such as ISMS POL-01 repeat across organisations). When neither is there, it says that the stored settings are not shown on this page, and the dialog makes the manager choose whether people are asked before it saves (see "Web" above). The sample build knows every setting, so its documents without stored settings show the defaults.

7. The read confirmation grants a version's file in place of the file permission and the owner scope (deviation 3), and the classification rule still applies: a `restricted` document is asked of, listed for and opened by only its owner and the Management System Managers and Programme Owners of a system it is linked to (BUILD-PLAN F.7 "Classification", WP-30 "`restricted` documents are hidden from a Domain Owner who does not own them"). Top Management, Internal Auditors, Domain Owners, Risk Owners and Compliance Investigators who do not own such a document are not asked to confirm it. For an organisation-wide `restricted` document only the managers of the systems it is linked to are asked, as the file routes count them (`canReadObjectIn`), although the document list shows it to the managers of every system (`documentVisible`). If the orchestrator decides that a read confirmation should reach those people anyway, the change is one condition in `acknowledgement-visibility.ts`.
