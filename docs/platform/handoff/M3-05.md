# M3-05 handoff: read confirmation of policies

M3-05 builds D.7 in full. A document can ask for read confirmation; each approved version then goes to the people concerned, who open it and confirm that they have read and understood it. The Management System Manager follows the confirmations in "Policy read confirmations", reminds the people still pending, downloads the register as CSV and files it as a new file of an evidence item when the request closes. Each person confirms in "Policies to confirm", reached from a banner in the host layer, their task and their notification. In audit terms the register is the record that the policy was communicated and acknowledged (ISO/IEC 27001 A.5.1, clause 7.3 "Awareness" and 7.4 "Communication" of each standard).

## What was built

### Server (`apps/server/src/modules/acknowledgements/`)

| File | Content |
|---|---|
| `acknowledgement.service.ts` | `AcknowledgementService.openForApprovedVersion` (called by the approval, skips an empty audience) and `openRequest` (also called by `acknowledgement-requests.create`): refuses a second open request of the same version (409), takes the audience snapshot, closes the earlier versions' open requests (pending people `excused` with "Replaced by version X", their tasks cancelled; confirmations stay), inserts the request, one `acknowledgement` row, one task and one notification (`acknowledgement_requested`) per person, and audits `acknowledgement_request.created`. Shared helpers: `settingsOfRow`, `sameSettings`, `audienceOf` (active business roles in the target systems, never `external_auditor`, active person accounts with an active membership), `excusePending`, `closeTasks`, `primarySystemOf`, `requestVisibleIn` |
| `acknowledgement-requests.service.ts` | The six routes of the register: list (requests of documents that count in the system: linked to it, or organisation-wide; totals for every caller), create (current approved version only, audience and due days from the body or the document's settings; a document linked to the path system, or an organisation-wide document from any system, as the snapshot lists it in every system), get (person list only with `audit.pending.all` in full; Top Management gets totals, product decision 2), remind (409 when closed, already reminded today or nothing pending; audit `acknowledgement_request.reminded` with source `manager`), close (optional `fileGeneratedEvidence` of the register CSV into an evidence item of the path system in the same transaction, open tasks cancelled, audit `acknowledgement_request.closed`), export (formula-safe CSV through `toSafeCsv`, file name `read-confirmations-<code>-v<label>-<date>.csv`, audit `file.downloaded`) |
| `me-acknowledgements.service.ts` | `me.acknowledgements` (pending rows of open requests first, then rows settled in the last 180 days), `me.acknowledgements.open` (sets `opened_at` the first time; audits `acknowledgement.opened` with `via` and `first`, and `file.opened` with `via: acknowledgement`), `me.acknowledgements.confirm` (409 when confirmed, excused or closed; 422 `ACK-OPEN-FIRST` before opening; closes the task `done`; audit `acknowledgement.confirmed`). The open route answers: for a file in a linked repository, the redirect token address when the person may read the object through the existing file routes, otherwise the provider's address from the gateway (`/v1/open-url`), where the person's own access applies; for a stored (vault or pass-through) file, the content route of a system where the person may read the object, otherwise 422 `acknowledgements.file_not_readable` (deviation 3) |
| `acknowledgement-file-grant.ts` | `acknowledgementFileGrant(trx, userId, acknowledgementId, objectId)`: the check a redirect token that names a person's acknowledgement row asks before the file routes open the version for someone without file rights (follow-up 1). It passes for the person's own row that is not excused (pending in an open request, or confirmed), when the request's version holds the object. It imports nothing from `files/`, so `files/` can call it without a module cycle. Covered by `test/int/acknowledgements`; no route calls it until follow-up 1 lands |
| `acknowledgement-reminders.job.ts` | The daily `acknowledgement.reminders` job: excuses people who left the organisation ("Membership of the organisation ended") or no longer hold an asked role ("No longer holds a role that is asked to confirm"), reminds the pending people 7 days after the start, on the due date and every 7 days after it, at most 3 times (`reminderDateOn`, `MAX_REMINDERS`), and tells the Management System Managers once per request when it is overdue (`acknowledgement_overdue`) |
| `acknowledgement-text.ts` | English and Indonesian texts: task title, notification titles and bodies, excusal reasons, refusals (`acknowledgements.*` message keys), the CSV columns |
| `*.controller.ts`, `acknowledgements.module.ts` | The stub controllers replaced; the module imports `FilesModule` and `StorageModule` and exports `AcknowledgementService` |

Registers (`apps/server/src/modules/registers/`):

- `documents.service.ts`: `documents.create` and `documents.update` store the acknowledgement settings (`acknowledgement_required`, `_scope`, `_roles`, `_due_days`); the audit entry names them (`after.acknowledgement`, and `before` on update); an unchanged value writes nothing. The approval of a version in review opens the request through `AcknowledgementService` in the same transaction when the document asks for it, and the command message says how many people are asked.
- `records.service.ts`: `tasks.complete` refuses tasks of source `acknowledgement`, `access_review` and `privacy_check` with 422 `task_completes_on_screen`, naming the screen where the task completes (D.2).
- `registers.module.ts`: imports `AcknowledgementsModule`. `acknowledgements/` imports nothing from `registers/`.

### Web (`apps/web/src/screens/`)

- `acknowledgements/` ("Policy read confirmations", `/ms/:ms/acknowledgements`, Implementation group, roles Management System Manager and Top Management): totals tiles, the requests table (document, version, due date, confirmed of audience, pending, overdue, state), the request drawer with the facts, totals and person list, "Remind", "Export CSV" and "Close and file as evidence" with an evidence picker; the page action "Ask for confirmation" (document, audience, roles, days); Top Management sees totals and a note, no names and no actions. `DocSection.tsx` is the `doc` detail extension "Read confirmation": the settings and their dialog (with the BR-22 confirmation for a shared document) for whoever holds `document.manage`, and the latest request's confirmed count with "Open read confirmations" for whoever sees the register. When an API build does not know the stored settings (deviation 6), the section says that they are not shown on this page and that saving new settings replaces them; the dialog then shows a notice, offers "Ask people to confirm each new approved version" and "Do not ask for read confirmation" as a choice with neither chosen, and saves only after the manager chose one, so the defaults are never presented as the stored values. `actions.ts` adds the page action "Read confirmations" to the Document register in API builds (C.1).
- `my-confirmations/` ("Policies to confirm", `/my-confirmations` with `?ms=<system>`, all four roles): open confirmations with "Open document" (the tab opens during the click), the statement checkbox and "Confirm", which stays disabled with its reason until the version is opened and the statement ticked; the done list; the all-done scene. `Banner.tsx` is the host layer banner "You have N policies to confirm" with "Open Policies to confirm" and "Later" (put off until the page reloads or another confirmation is asked), hidden on the screen itself and stacked above the invitation banner.
- Both screens have a sample adapter over a shared per-organisation sample store (`acknowledgements/sample-store.ts`), loaded with a dynamic import only (R-13): ISMS POL-01 open and POL-14 closed, with the personas confirmed.

## Deviations

1. `AcknowledgementService` inserts the tasks itself. `RuleTaskService` of `jobs/rule-tasks.ts`, which the brief names, does not fit: its input accepts only the rules `BR-10`, `BR-11`, `BR-15` and `BR-31`, the file is outside the Owns list, it writes one row at a time with the system as author, and an audience can hold hundreds of people. The insert writes the same columns (`source_rule = 'acknowledgement'`, `entity_type = 'acknowledgement'`, `entity_id` = the acknowledgement row, C.3) under the same `task_open_uq`, as one statement with the approver or manager as author.
2. `DocumentsService` takes `AcknowledgementService` as an `@Optional()` dependency: `ImportsModule` builds its own `DocumentsService` without the acknowledgements module, and bulk import does not open requests (an imported document has no approval).
3. A stored (vault or pass-through) file opens through the existing content route only for a person who may read the object there; anyone else gets 422 `acknowledgements.file_not_readable` and no `opened_at`, so they cannot confirm (ACK-OPEN-FIRST). With the default audience this is every Top Management member and every Domain Owner, Risk Owner and Compliance Investigator who does not own the document. D.7 asks that every person in the audience can open the version through the redirect token, but `files/redirect-token.ts`, `files/object-access.service.ts` and the file route schemas of `packages/shared/src/api/files.ts` are outside the Owns list, and R-14 allows no new route. The acknowledgement side of the fix is ready (`acknowledgementFileGrant`); the change of `files/` is follow-up 1, the open item of this package. Files in a customer repository open for everyone, at the provider, as D.7 says.
4. A request shows in every system its document is linked to, in every system for an organisation-wide document, and in the system recorded on the request (`requestVisibleIn`), as long as that system is still the document's primary one. "Ask for confirmation" takes an organisation-wide document from any system, since the snapshot lists it in every system; a document linked to other systems only stays 404. The cross-system fixture of `security/cross-system.test.ts` keeps its meaning: a QMS-only request does not show in the ISMS.
5. "Policies to confirm" has no sidebar entry (`nav: false`): a new sidebar group would change the host's own test `apps/web/test/screens/host.test.tsx`. People reach it from the banner, the task title and the address `/my-confirmations?ms=<system>`.
6. The document record of the read model has no `acknowledgement` member yet (read-model files belong to M3-04 in wave 3). The detail section reads the member when it is there and otherwise shows the settings saved in this page session, kept per organisation (switching organisation keeps the page, and pack codes such as ISMS POL-01 repeat across organisations). When neither is there, it says that the stored settings are not shown on this page, and the dialog makes the manager choose whether people are asked before it saves (see "Web" above). The sample build knows every setting, so its documents without stored settings show the defaults.

## Follow-ups

1. Files (orchestrator, outside the Owns list; major finding of the verification): let every person in the audience open a stored version without file rights. Proposed change:
   - `files/redirect-token.ts`: an optional claim `k` (acknowledgement id) in `RedirectClaims`; `verify` refuses a `k` that is not a string.
   - `files/object-access.service.ts`: when the token carries `k`, check `acknowledgementFileGrant(trx, principal.user.id, k, id)` from `acknowledgements/acknowledgement-file-grant.ts` instead of `storage.object.read` and `canReadObjectIn` (403 `files.redirect_token` when it answers null), then `assertContentNotDisposed`, then for a streamed file (`streamsContent`) stream it inline through `FileResponder` with the audit `file.downloaded` in the grant's system (`after.via: 'acknowledgement'`, `records: ['document:<code>']`), and for any other file send the 302 to the provider as today. The redirect route is declared with status 302 only, so the streamed case either goes through the content route with an optional token in its query (a schema change of `storage.objects.content` in `packages/shared/src/api/files.ts`, preferred) or changes the redirect route's declared answers.
   - `acknowledgements/me-acknowledgements.service.ts` (M3-05, a few lines): for a streamed file without a readable system, issue the token with `k: row.id` and answer its address instead of the refusal `acknowledgements.file_not_readable`.
   - Tests: an integration test in `test/int/acknowledgements` where `hendra` (Top Management) and `bagus` (a Domain Owner who does not own QM-01) open the QM-01 vault version and confirm, and where the token of one person does not open the file for another; the API spec `e2e/api-only/acknowledgements.spec.js` then opens QM-01 as `hendra`.
2. Read model (M3-04 or whoever owns `read-model/**`): the `acknowledgement` member of the document record (D.2 `DocumentAcknowledgement`), so the detail section shows the stored settings after a reload.
3. Host: a sidebar entry for "Policies to confirm" with the count of open confirmations (update `host.test.tsx`), and a link from a My Tasks row of entity type `acknowledgement` to the screen.
4. M3-11: the notification links of `acknowledgement_requested` and `acknowledgement_overdue` (`KIND_SCREENS`) to `my-confirmations` and `acknowledgements`.
5. docs-edit: the approval toast drops the server message, so "N people are asked to confirm" shows only in the API answer. Showing `res.data.message` there would tell the approver.
