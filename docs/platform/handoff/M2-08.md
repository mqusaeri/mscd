# M2-08 handoff: bulk import

M2-08 builds the bulk import of Milestone 2 (D.1, D2-13): XLSX templates whose header row matches the exports, the upload of one CSV or XLSX file with a dry run of every row, and the commit of every row or none in one transaction through the existing command services, in the worker. The web screen "Import" checks a file, lists every row with its result, keeps the import back while a row has an error, follows the commit and links to the screen of the kind. The stubs of M2-02 are gone and `m2-pending/M2-08.json` is deleted.

## What was built

### Shared contract (`packages/shared/src/api/imports.ts`, schemas only)

| Change | Content |
|---|---|
| `ImportRowResult` | Every data row of the file is in `results`, with `code` (the business id the row names) and `action` (`create`, `update` or `unchanged`; left out for a row with an error), so the screen lists the whole file and filters it |
| `ImportRun` | `progress` (0 to 100, from the background task), `summary` (`created`, `updated`, `unchanged`) and `changed` (system slugs) of a committed import, `failure` (both languages) of a failed one |
| Route summaries | The answers of `imports.create` (409 same file already imported, 413 above 5 MB or 5,000 rows, 422 unreadable file or header that does not match) and `imports.commit` (409 not waiting or already imported, 422 while a row has an error) |
| `ImportTemplateQuery` | Optional `lang` (`en` or `id`) on `imports.templates`: the language of the help sheet and the headers, which the screen sets to the app language; without it `Accept-Language` decides |

No route id, permission, enum value, profile key or migration changed (R-14); `imports.templates` gained the optional query schema above.

### Server (`apps/server/src/modules/imports`)

| File | Content |
|---|---|
| `import-file.ts` | Reads CSV (UTF-8, byte order mark, quotes, comma, semicolon or tab taken from the header line) and XLSX (`exceljs`; the first sheet that is not the Allowed values sheet). The header is the first line with text; rows are numbered from it, so a row number points at the same line across blank lines. Every cell is text: a formula cell is read as its formula text, such as `=SUM(...)` (F.15); a cell an export neutralised (`'=...`) loses its quote again; date cells become `YYYY-MM-DD`. Limits: 5 MB and 5,000 rows (413), 60 columns. The row limit counts data rows (records with text). A quoted CSV cell may span several lines and still counts as one row: the CSV parser counts records in its `on_record` callback and stops with 413 at the first data row past 5,000. A file is read whole or refused with 413. Blank rows do not count; an XLSX archive is inflated off the event loop with a ceiling of 64 MB before `exceljs` reads it (413). Legacy `.xls`, files that are not UTF-8 and empty files answer 422 with the reason in both languages |
| `import-columns.ts` | The columns of each kind: applicability starts with the twelve SoA export columns (`ID`, `Title`, `Theme`, `Applicable`, `Justification`, `Status`, `Owner`, `Implementing document`, `Frequency`, `Last evidence`, `Freshness`, `Integrity`) then `Risks` and `Status note`; documents start with the ten document register export columns, then `Classification`, `Approver`, `Organisation-wide`, `Origin`, `External source`, `External reference`, `Received`; risks and evidence have their own. Columns of the export that describe state the import does not set (status, versions, freshness) are read only. Headers match in English or Indonesian, in any case and spacing; an unknown, repeated or missing required column answers 422 `imports.header_mismatch` |
| `import-lookups.ts` | Everything a file is checked against, read once per file: the system and its edition, the active members (persons), the controls and clauses of the edition (as `applicability.targets` lists them: leaf rows, retired flag, assessable), the system's entries with their current values, frequencies, document types, risk profiles with their scales, treatment options, and the codes that already exist. People are found by handle, email or full name (the exports write full names); a name that several members share is refused with a request for the handle. Codes: `Cl. 4.1`, `Clause 4.1` and `Klausul 4.1` are clauses; any other code is a catalogue item when the edition has one, else a clause |
| `import-check.ts` | The dry run. Applicability: a control or clause without an entry becomes `ApplicabilityCreateRequest` (applies by default; frequency from the cell or the pack default) followed by the update fields (`ApplicabilityPatch`: risks, documents, status note); an existing entry becomes an `ApplicabilityPatch` of the values that differ, sent with the entry's ETag. Risks and documents are added to the links an entry has. Rules through the rule engine: `APPL-ASSESS` (a clause row always applies), BR-02 (error when a change would leave an applicable entry without a risk; a warning that a new applicable entry without a risk holds its gate), BR-03 (warning per row for an exclusion justification that says nothing). Documents (`DocumentCreateRequest`, metadata only), risks (`RegisterCreate`, BR-17 for a risk without an owner, likelihood and consequence within the profile scale) and evidence (`EvidenceCreate`, targets must have an entry in the system) register new records; a code that already exists is left as it is, with a warning. Every request is parsed with its create or update schema. The request the commit sends is kept with the row (`apply`) |
| `import-template.ts` | The XLSX templates: the header row of the kind (frozen, bold, with a filter) and an "Allowed values" sheet (in the language of the `lang` query, else of `Accept-Language`) that explains each column and lists the edition's frequencies, document types, classifications, risk profiles with their scales, treatment options, Yes and No, and the controls and clauses. No person is listed: the template is open to every holder of `ms.read`, external auditors included |
| `imports.service.ts` | `imports.templates` (F.13 attachment through `FileResponder`, audited `file.downloaded`); `imports.create` (403 `imports.permission` unless the kind's permission is held in full, or for evidence for own records; the file read after the permission check; 409 `imports.already_imported` for a file already committed to the system; `import_run` stored with the SHA-256 and the row results; audit `import.validated` with the counts); `imports.get` (404 to anyone but the creator, the progress of the task); `imports.commit` (404 to anyone but the creator, the kind's permission checked again, 409 `imports.not_waiting` (at once while the worker applies the import: the row is locked with NOWAIT), 409 `imports.expired` for a check older than 24 hours, 422 `imports.rows_with_errors`, 409 `imports.already_imported`; a background task of kind `import`, `import.run` queued in the same transaction with the singleton key `im:<id>`, the import `committing`; 202 with the task id) |
| `import-run.job.ts` | `import.run`: the creator rebuilt as a principal (active member, kind permission still held, else the import fails); every row's request through its command service in one tenant transaction of the creator, with the creator as the actor of the request context, so every audit entry names the person who imported; an applicability update carries the ETag of the entry as checked (a change made since fails the import). Progress is written every 5 percent in transactions of its own. At the end the import is `committed` (the unique index refuses a second commit of the same file), the task `succeeded` with the counts, `import.committed` audited, `import_finished` sent to the creator and `freshness.recompute` queued for the whole system (applicability and evidence). The rows and the outcome run inside `ImportHold.run` (next row). When a row fails, nothing stays: the import becomes `failed` with "Row N (code): reason" on the import and on the row, the task `failed`, and the creator gets `import_finished` with the reason |
| `import-hold.ts` | `ImportHold`: what a commit keeps back until all its rows are applied, so that it does not hold up other people's writes. Each command writes its audit entry in the commit's transaction, and the first insert into `audit_trail` takes the organisation's audit chain lock (`platform.chain_hash`, an advisory lock per audit table) until that transaction ends; with the 30-second `statement_timeout` of the application role in Compose and SaaS installs, every audited write of the organisation (other people's requests, jobs) would fail while a long commit runs. The same holds for the singleton keys of `freshness.recompute`, `readiness.recompute` and `cycle.derive` (one waiting job per system and unique index in pg-boss). Inside `run`, the module's audit writer turns each tenant entry into the row the chain writer would insert (same columns, request context, changed fields, redaction, edition) and keeps it, and the module's job queue keeps those three jobs, one per job and system. When the rows are in, still in the same transaction, the jobs are queued once per system under keys of the import (`<key>:import:<id>`, the payload the whole system) and the entries are written in order with inserts of 1,000 rows, so the chain lock is held only from those inserts to the commit. A row that fails rolls the transaction back and nothing held is written. Outside `run` both are the application's own writer and queue |
| `import-tenant-scope.ts` | `ImportTenantScope`: inside `inOneTransaction` every `withTenant` of the same organisation joins the one transaction (its after-commit hooks run when it commits); another organisation is refused; `detached` opens a transaction of its own (progress) |
| `imports.module.ts`, `imports.controller.ts` | The module gives its own instances of `ApplicabilityService`, `DocumentCommandsService`, `RegistersService`, `EvidenceService` and `SharedChangeGuard` the import scope as their `TenantScope`, and the audit writer and job queue of `ImportHold` as their `AUDIT_WRITER` and `JOB_QUEUE` (a provider of the module wins over the global one; `ImportSharedModule` hands `ImportHold` the global ones). The controller passes the `lang` query of `imports.templates` to `templateLanguage`. The services and their rules are unchanged; the rules stay registered once in their modules |

## Deviations

1. **The page action "Import" shows in API builds only.** In the sample build `e2e/shell.spec.js` (owned by M2-01) counts the page actions of each built-in screen and clicks each one for its toast, so a third action on Controls & requirements and Document register fails that Milestone 1 check (R-15). The sample build reaches the screen from the sidebar. The orchestrator can drop the `ctx.mode === 'api'` condition in `actions.ts` once `shell.spec.js` counts extra page actions (follow-up 1). M2-09 adds an extra page action to `fw` in the same wave and meets the same check.
2. **The sample build imports controls and documents, from CSV only.** XLSX needs the api, and risks and evidence have no sample rows the built-in screens could show.
3. **Documents, risks and evidence are only created.** A code that already exists is left as it is, with a warning, so an export of the register imports again without errors. Only applicability entries are changed by an import (D.1 names the create schemas).
4. **Risks and documents of an applicability row are added to the entry's links.** The SoA export lists only the first implementing document of an entry, so replacing the links would remove the others on a round trip. Links are removed on screen.
5. **A check is valid for 24 hours.** An older check shows `expired` and its commit answers 409 `imports.expired`.
6. **People by handle, email or full name.** D.1 names handles and emails; the exports write full names, so a full name that only one member has is accepted too.
7. **The commit audits every row as the person who imported**, through the request context of the job, as `import.committed` is.
8. **`freshness.recompute` for the whole system after an import.** `enqueueFreshness` uses one singleton key per system, so in one transaction only the first command's job stays and it names only that command's records; the import queues one job for the whole system with its own key.
9. **The Risk Owner refusal of `imports.create` (risks) is not in `rbac/expectations/M2-08.ts`.** The refusal test of `rbac/matrix.test.ts` checks the matrix with the `kind` of the route's first sweep input (`applicability`), which a Risk Owner does not hold, so the entry would be reported as "not admitted"; `imports.test.ts` covers it.
10. **The audit entries of a commit are written at its end (`ImportHold`).** They stay in the commit's transaction, in the order the commands recorded them, with the importer as the actor and `occurred_at` the start of the transaction as before; their sequence numbers now come after the entries other people wrote while the commit ran, where before those people waited. Nothing in a command reads its own audit entry back, and the F.11 chain verifies (tested). The per-system `freshness.recompute`, `readiness.recompute` and `cycle.derive` jobs of the commands are queued once per system at the end, for the whole system, under keys of the import.

## Follow-ups

1. **Orchestrator, `apps/web/e2e/shell.spec.js`:** count the page actions that packages add to built-in screens (for example from a list in each screen folder's `meta.json`, or by reading `extraPageActions`), then remove `ctx.mode === 'api' &&` from `apps/web/src/screens/import/actions.ts`. The test "every screen has working page actions" then expects `Import` on Controls & requirements and Document register, which opens the Import screen instead of a toast.
2. **Commit time and locks (orchestrator: risk table I).** A 5,000-row commit (new risks) takes 50 to 106 seconds on the shared host (10 to 21 ms per row: every command makes its own queries, audit entry and links); the check of the same file takes under half a second. Without `ImportHold`, the commit's first audit entry would lock the organisation's audit chain until the commit ends, and with the 30-second `statement_timeout` of `mscd_app` (Compose, Helm and the dev stack) every other audited write of the organisation would fail while a commit runs longer than 30 seconds, which any file above about 1,500 rows does. With `ImportHold` the chain lock is held only for the commit's last statements: in two runs of the 5,000-row test, 276 and 187 other audited writes of the organisation under a 30-second timeout ran during commits of 77.6 and 50.3 seconds, and the longest waited 1.6 and 2.0 seconds (the commit's last statements); with the hold switched off, the same kind of write fails with "canceling statement due to statement timeout" (checked once by hand). What still waits for the commit is a write to the same records: a person who edits an applicability entry the import is changing, or creates a document, risk or evidence code the import is creating, waits until the commit ends and gets a server error after 30 seconds. A second `imports.commit` of the same import (another tab, a retry, an API client) does not wait: the worker's transaction holds the import's row until the commit ends, and `imports.commit` locks that row with NOWAIT, so it answers 409 `imports.not_waiting` ("This import is being committed.") at once (tested). Risk table I ("Import commits large files in one transaction") can name this narrower consequence and `ImportHold` as the mitigation. A later package can still lower the per-row cost in the command services.
3. **`enqueueFreshness`** (Milestone 1, `implementation/command-support.ts`): several commands in 5 seconds keep only the first job and its record ids (deviation 8). Not only imports meet this; a job without record ids, or a key per record set, would fix it.
4. **Old imports.** Nothing deletes `import_run` rows; `cleanup.expired` could remove checks that were never committed after a week.
5. **M2-11, M2-12, M2-13:** the forms can link to Import (`ctx.go('import', {params: {kind}})`).
6. **MOT-03 and M2-16:** the Import screen's empty states (no system, no kind to import) take an `illustration` once the library is in.

## Orchestrator decisions

- Started early with the owner's approval (wave 3a before wave 2b was committed). The first runs stopped part way (session ends, machine restarts and an expired login); the workflow resumed from its finished steps. The second independent check passed with minor findings, and the polish step fixed the two that belong to this package.
- Deviations 1 to 10 are accepted. Deviation 10 keeps the audit chain whole: the entries of a commit stay in its transaction, name the importer and carry the time the commit started; only their place in the sequence moves after entries other people wrote meanwhile.
- Follow-up 1 (`apps/web/e2e/shell.spec.js` counts the page actions of built-in screens, so "Import" shows in API builds only) is an orchestrator item before the end of wave 3; it also concerns any page action M2-09 adds to a built-in screen. Follow-ups 3 and 4 go to the Milestone 2 backlog in M2-STATUS. Follow-ups 5 and 6 were passed to M2-11, M2-12 and M2-16.
- The failures the last check saw in the common acceptance belong to packages still being built (M2-S09: `m2-stubs.test.ts`, `program.test.ts`, one lint error; M2-10: the shared menu tests and one dark-theme contrast). They go back to those packages.
