# M2-S09 handoff: operator commands and organisation lifecycle

The platform operator now runs the whole life of a customer organisation on SaaS: detail, status changes along the machine of J.8 with their history, the sessions and emails that go with them, a plan preset and a region at creation, the same steps from the command line, an allow-list wrapper on the server, a GitHub workflow that runs it with the owner's approval, and an offline diagnostics command.

## Decisions

- **`seed demo --reset` removes a demo organisation together with its status history** (orchestrator note from M2-06). Demo organisations are throwaway data; the audit entries of the changes stay in `platform.audit_log`. The append-only trigger is turned off for that one statement inside the reset transaction (the migrator owns the table; `ALTER TABLE` is transactional). Events of other organisations stay; one that names a demo user as its actor stops the reset with the existing message. The change is in `src/seed/seed-demo.ts`, which this package does not own: see the patch below. Checked with temporary copies of `seed-demo.ts` and `seed-command.test.ts` in this package's folder (5 of 5 pass with the patch, the reset fails without it), then removed.
- **The plan preset is written before the invitation**, in the same transaction, so the first administrator counts against the plan (D.2).

## Deviations

1. **No session cache listener.** The session resolver reads `platform.session` on every request and keeps no cache of its own, so a revoked session ends at its next request in every process. The only cached organisation data on that path is `TenantResolver`, which now drops its entry on the change notice. `identity/session-resolver.ts` is unchanged.
2. **Response schemas.** `ops.organizations.status` answers `OrganizationStatusChangeResult` (a `CommandResult` with `data`) and `ops.organizations.create` adds the optional `data.plan`. Both are schema changes in the area file this package owns (R-14).
3. **Moving to the same status is refused** with 409 `invalid_status_transition`, because the machine has no such row and `platform.organization_status_event` forbids `from = to`.
4. **Sessions ended are those whose current organisation is the one changed** (`session.organization_id`), as the brief says. A session opened through this organisation's sign-in and moved to another organisation keeps working. The revoke reasons `organisation_suspended` and `organisation_archived` are new strings of the `varchar(40)` column; `SessionRevokeReason` of `session.service.ts` (not owned) does not list them, so `org-sessions.ts` has its own type.
5. **The status email goes out directly**, not through `notifications.dispatch`, which emails only active and offboarding organisations. The in-app notice is written with `email_status` `skipped` so nothing is sent twice. The email names no person, not even the recipient (stricter than the M2-S04 note).
6. **Commands in single tenancy.** `tenant list` and `tenant show` read there too; `tenant set-status` and `tenant onboard` refuse like the routes. So no change notice is needed in single tenancy and `license/tenant-change.ts` is unchanged (M2-S10 deviation 3).
7. **Offline diagnostics.** `logs.ndjson` holds the command's own log lines: the api's ring buffer lives in the api process. When the database cannot be reached the archive is still written, without the audit entry, and the command says so; `ops.health` lists the migration state as `down` instead of failing.
8. **`ops-cli.yml` encodes the values itself** (`NAME=<base64>` lines, as `saas_encode_input` does) and needs no checkout and no third-party action. It reads the personal fields from the run's event file, so they never appear in a step's env block in the log. The values typed into the form stay in the run's event, which anyone with read access to a public repository may be able to see through the API; `docs/saas/operator.md` says to prefer the console for customer data (GL-50).
9. **`saas-ops.sh` takes no lock of the install folder.** The workflow shares the concurrency group of `deploy-prod.yml`, so a command never runs during a deploy of the same server; a lock would also block commands for the whole nightly backup.
10. **Region.** The operator routes and commands (`ops.organizations.create`, `tenant onboard`, `tenant create`) pass `tenancy.default_region`; the seed and the test fixtures create organisations without a region, as before.
11. **Retention of the server files of `saas-ops.sh`.** `lib/saas.sh` belongs to M2-S05 and M2-S07, so `saas-ops.sh` prunes its own files instead of adding a pattern to `saas_prune_logs`: run logs after 90 days (the default retention of GitHub run logs, so the full output of a command can be looked up as long as its run is listed) and diagnostics archives after 14 days. They are removed by age (file time), not by count, so the retention period can be written down. Nothing runs between two commands: a file older than its period stays until the next command.
