It adds the data lifecycle run on the SaaS test stack, the notification links of the Milestone 3 kinds, and the documents for the lawyer, the operator, the user flows and the UI contract, written from the code as built. ## What was built

### The data lifecycle run

`npm run lifecycle -w @mscd/smoke` runs `tools/smoke/run-saas.mjs --lifecycle`: the SaaS test stack of `saas-stack.sh` with release images built from the working tree, then `tests/data-lifecycle.spec.mjs` with `lifecycle.config.mjs`, then `saas-stack.sh down` on success, failure and Ctrl-C.

- **Run overlay.** With `--lifecycle` the overlay of the run (`compose.run.yml` in the state folder, never `saas.yaml`, D.3) sets `MSCD_SAAS_TEST=1` and `MSCD__LIFECYCLE__OFFBOARDING_DAYS`, `_DELETION_GRACE_DAYS` and `_DELETION_MIN_GRACE_DAYS` to 0 on the api and the worker (`LIFECYCLE_ENV` of `run-saas.mjs`). The read-only period then ends at once and a deletion is due as soon as the organisation is archived.
- **Shared browser library.** `tools/smoke/lib/browser.mjs` holds what the SaaS run and the lifecycle run share: one browser session per person, sign-in with password and authenticator, `expectReadableText` on every screen a person sees for the first time and `expectOverlayReadable` on dialogs, and the watch that fails a step on any page error, console error, 5xx answer or 4xx answer the step does not expect. `tests/saas.spec.mjs` now uses it; its steps are unchanged.
- **People.** `tools/smoke/lib/lifecycle-data.mjs` builds on the people of the SaaS run (`saas-data.mjs`): Alpha with Ayu (Tenant Admin, primary Management System Manager), Dimas (Tenant Admin, second manager), Eka (Domain Owner, later also a member of Beta) and Fajar (Domain Owner who leaves); Beta with its administrator. Every person and address is invented (R-19).
- **The thirteen steps,** each on screen in the person's own browser session:
  1. The operator sets a password from the emailed link and enrols an authenticator.
  2. The operator creates Alpha and Beta; their first administrators accept the invitations.
  3. Alpha's Tenant Admin invites a second Tenant Admin and two members, who join.
  4. The ISMS gets two Management System Managers (each grant to an administrator approved by the other Tenant Admin), two Domain Owners and the evidence items of A.5.1 and A.5.18.
  5. Beta gets its QMS; Eka of Alpha accepts the invitation banner and gets a role there.
  6. Read confirmation: POL-01 needs confirmation, Dimas approves its first version, Eka and Fajar open and confirm it, and Ayu closes the request and files the register as a new file of the A.5.1 evidence item.
  7. Retention: a competence record that lapsed 60 days ago; Ayu sets 1 month for "Lapsed competence records"; the daily review opens it; Ayu proposes disposal (her own Approve stays disabled) and Dimas approves it; the disposal register shows it.
  8. Access review: Ayu starts it, Dimas decides Ayu's own access, both Tenant Admins decide the organisation part, Ayu applies the revocation of the leaver's role, signs the ISMS off into the A.5.18 evidence item, completes the review and downloads the report CSV.

  10. Eka's access request is answered with a copy of her data after the system check of the ISMS; the leaver Fajar is erased after the system check, and the organisation's people list no longer holds his email address.
  11. The operator runs `org.lifecycle` from the console's Jobs tab: Alpha is archived; the operator sets the deletion date to today in the Deletion tab, and the "Deletion on" column shows the local day of `scheduledFor` from the deletion route, which the organisation route repeats; `org.lifecycle` runs again and the purge completes; the certificate downloads, names the final export, passes `mscd-server tenant verify-certificate --json` in the stack's `cli` container, and reaches both Tenant Admins by email.

## Deviations

1. **The daily retention review is queued from the worker container.** `retention.review` runs at 03:15 local time and is not among the jobs an operator may start (`OPS_RUNNABLE_JOBS`), so step 7 sends that same job to the queue from the worker container with the server's own queue driver (`startRetentionReview`, test stack only). Every other step uses the screens; `org.lifecycle` runs from the operator console.
2. **The run keeps away from the hourly `org.lifecycle` schedule.** The schedule runs at minute 20 UTC and, with the periods at 0 days, would archive Alpha before its final export is downloaded. Before the offboarding step the run waits until the next scheduled run is at least 15 minutes away (at most about 18 minutes of waiting, added to that step's time limit), so the operator's own runs from the console do each move.
3. **The browsers use the time zone Asia/Jakarta.** The deletion date form takes its earliest day from the installation's local date and builds the instant in the browser's time zone; with the browser in UTC near midnight the two disagree. Alpha's time zone and the installation's default are Asia/Jakarta, so the run's browsers use it too.
4. **"Alpha's sign-in shows no organisation"** is checked where the app decides it: the organisation discovery of the sign-in page answers Alpha's slug exactly as a slug that never existed, and the email and password of Alpha's anonymised Tenant Admin open nothing.
5. **`tests/saas.spec.mjs` moved its browser helpers into `lib/browser.mjs`** so both runs share one watch and one sign-in. The SaaS run's steps and checks did not change.
6. **The system check waits for its drawer to come back.** After "Mark checked", Personal data checks reads its list again: the drawer goes while the list loads (the open row is looked up in the list) and comes back with the done status. The first lifecycle attempt of the fix round closed the layers in that gap, found none, and the returning drawer then caught the next click. The step now waits for the done status in the drawer, closes it and checks that it is gone.
