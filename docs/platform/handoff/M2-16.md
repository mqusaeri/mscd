# M2-16 handoff: Getting started, account, notifications and operator console

M2-16 builds six web folders on the screen host of M2-01: "Getting started" (the onboarding checklist of D.5), "Organisation" (the settings and the installation id), "My account" with its top bar entry, the notification bell and its panel, the invitation banner of the host layer, and the "Operator console" of the platform operator. It also extends the Licence screen of M2-01 with the installation id panel and the follow-up 3 of M2-S10 (the entitlement of a multi tenancy service). No server code, shared contract, generated view or shared web file changed.

## What was built

### Notifications (`apps/web/src/screens/notifications/`)

No screen: `actions.ts` adds the bell to the top bar (`topbarItems`, order 10), in the sample build and for API sessions with an organisation (a platform operator without a membership has no notifications). The bell reads `GET /notifications?unread=true&pageSize=1` when the app opens, after an organisation switch, after the panel closes, and on a timer (`poll.ts`): every minute only while the page is visible and the person pressed a key, clicked, scrolled or touched the screen in the last five minutes (`IDLE_AFTER_MS`; mouse movement alone does not count). After a quiet spell the timer reads nothing, and the first input reads the count at once. Every request with a session moves the session's idle expiry forward (F.1, at most once a minute), so a timer alone would keep an unattended session alive until its absolute limit of 8 or 12 hours; with the gate, a session left alone expires at most five minutes after the idle timeout of F.1 (60 minutes for staff, 30 for guest auditors) would have ended it; the count shows inside the button (99+ above 99), and the label names it for screen readers. The panel (`Panel.tsx`, lazy) is a drawer: notifications newest first, 20 per page, "New" badge, system and time, "Mark read" (`POST /notifications/{id}/read`), "Mark all read" (`POST /notifications/read-all`), "Show unread only", and "Open", which marks the notification read and goes to the record (the bell reads the unread count once that Mark read is answered, `refreshAfter`): the record key of the sample, or in API mode the snapshot key whose reference has the record's uuid, opens the list screen in that system with the record's drawer (Controls on the record's tab, Document register, Evidence freshness, Chain stages); else the screen of the entity type or of the notification kind; a host screen the session cannot open gives no "Open". Empty: the `all-done` scene with "You are all caught up".

## Deviations

1. **My account opens in a drawer for a session without a system.** The host offers no permission that every session holds: `canOpenHost` checks an `ms` screen in the selected system and an `org` or `platform` screen against `Me.permissions.org`, and a Domain Owner holds no organisation permission while an administrator without a business role and a platform operator have no system. The screen therefore uses scope `ms` with `ms.read` (every business role), and the top bar entry opens the same page in a drawer when the session cannot open the screen (`Entry.tsx`, `mayOpenScreen` repeats the host's rule for an `ms` screen). Follow-up 4 removes the drawer path.
2. **Preferences are applied at once through the controller's header controls.** The host context has no setter of language, theme or density, and `MscdApp.jsx` may not change in this package. `display.ts` clicks the controller's own EN or ID button and theme button when they differ, and sets `data-density` on the app root (the controller takes density from the boot settings only and never sets it again, so the attribute stays until the next start, where boot applies the saved value). Follow-up 5 offers a host setter.
3. **The Getting started counts are labelled values,** for example "Administrators: 2" and "People who can verify: 3", so one and several read correctly in both languages, and so do counts above the two that a step needs (the server counts every verifier and every Stage 1 and Stage 2 event, including a rescheduled one).
4. **Multi tenancy in the console is read from the platform rights of licences and packs.** The system profile does not name the tenancy mode. The organisation list confirms it: a 409 `single_tenancy` shows the single tenancy text.
5. **The pack installation is followed in the installed list.** No route reads the state of a `pack.install` task; the import answers the install id and the pack and version, and the console polls `admin.packs.list` for that row.
6. **The diagnostics archive is read with `fetch`.** `ApiClient.request` reads a body as text, which breaks a gzip archive, so `ops/api.ts` sends that one request with `fetch`, the client's CSRF token and language, and reads the problem of a refusal with `toApiError` of the client (an exception to R-17). Two limits follow, until follow-up 8 lands: a 401 of the archive does not raise the client's `unauthenticated` event by itself, so the adapter then reads `GET /ops/health` through the client, which answers 401 too and shows the sign-in page as for any other request (one extra request, only after a 401); and the client's `baseUrl` is not used (the path is same-origin). The web app creates its client without a `baseUrl` (`auth/boot.tsx`), so this has no effect today.
