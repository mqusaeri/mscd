# M2-13 handoff: Registers screen

M2-13 adds the screen "Registers" (`registers`, `/ms/:ms/registers`, group Implementation, `ms.read`) on the screen host of M2-01. One tab per register kind of `packages/shared/src/api/risk-registers.ts`: Context issues, Interested parties, Assets, Risks, Metrics, Objectives and Competence. Each tab is a paged list from `registers.list` with a search, a drawer per row, and the Add and Edit forms with the fields of the kind. Risks carry their treatments with the C.13 moves, BR-04 and the residual acceptance by the risk owner; metrics take a value per period; competence records keep a proof file from the repository picker; shareable records are linked to other systems. Everything is in `apps/web/src/screens/registers/`. No server code, shared contract, generated view, shared web file or Milestone 1 test changed.

## Deviations

1. **Treatments are read as chain records of the risk.** No route lists the treatments of a risk with their status. The screen reads the stage whose records are `risk_treatment` rows (`treatment` in ISO/IEC 27001, `action` in ISO 9001) with `readmodel.audit.stage-records`; its records whose upstream names the risk are the treatments, with their uuid, ETag, owner, due date and target. The status comes from the pending action: the server's texts give proposed, approved, in progress and delayed; another text (demo seed) shows as "Open" with the moves of an open treatment; no pending action shows as "No open action" (implemented, residual accepted or closed), with Close offered and the server deciding (BR-04 or the C.13 refusal shows). A move made on screen is known exactly until the record changes again. The stage is found from an open treatment in the snapshot, else by reading each entity stage once, and kept per organisation and system.
2. **"Make primary" and "Remove link" change `linkedMs` with `registers.update`.** `entity-links.make-primary` and `entity-links.remove` take the link id, which no route returns for an existing link. `registers.update` with `linkedMs` gives the same result (first system primary, a missing system unlinked) and needs the kind's manage permission in full and `entity_link.manage` here; it is sent with `confirm: true` after the screen's own confirmation, which names the change. The link of the open system itself is removed from the other system. "Link to another system" uses `entity-links.create` in the target system (`entity_link.manage` there); a competence record has no code to link by, so it is linked with `linkedMs` as well.
3. **The proof file of a competence record is kept with an evidence record of competence, whose current file it replaces.** `ctx.openPicker` resolves with a repository item or an upload intent, and `proofObjectId` needs a stored object; an upload intent and the picker listing need an evidence or document record. The form offers only the evidence records linked to clause 7.2 Competence (7.2.1 in ISO 37001) or to control A.6.3 of ISO/IEC 27001 (awareness, education and training), those without a file first (`proofHoldersOf` in `model.ts`; A.7.2, physical entry, and every other control are left out). It opens the picker for the chosen record. On Save (`trySaveRow` in `Forms.tsx`) the register is written first: the create, or the patch of the changed fields; when only the proof file changes, a patch that sends the role unchanged, so the server checks the ETag, the permission and BR-22 and changes nothing. A refused or cancelled save (the BR-22 confirmation, a stale ETag, a field error, a person who is not a member) stops there and no evidence record changes. Only then is the file attached with `evidence.files` (`relink` when the record's pinned file can no longer be verified, as the evidence drawer does), and a second patch sends the stored object id as `proofObjectId`, with the ETag the first write answered and `confirm: true` when the person confirmed BR-22. When the attach or the second patch is refused after the register write went through, the record stays saved and the list shows a warning that the proof file was not kept, with the reason (and, when the file was attached, that it is now the current file of the evidence record). When only the proof changes and the second patch is refused, the form stays open and the next try reuses the attached file. When the second patch is refused after the register write, the screen keeps the stored file for that record (`unlinkedProof` in `cache.ts`, per organisation, person, system and record, for the browser session), and the next Edit of the record starts with that file chosen, says that saving links it, and sends the same stored object id without a second `evidence.files` call. Side effect: `evidence.files` makes the picked file the record's current file, with today as its production date, a new file sequence and a fresh freshness and integrity check; a record that had a file shows the competence proof in its place. The form says so when the chosen record has a file ("EV-0217 already has a file. Saving puts the chosen file in its place, and EV-0217 shows it as produced today."). In the demo ISMS the only record offered is EV-0217 "Awareness training attendance" (A.6.3), which has a file; the demo QMS offers EQ-0133 (clause 7.2); the demo BCMS and ABMS have none, so the form says to add an evidence record of competence first. This needs `evidence.file.submit`. The proper fix is the contract item of item 2 of "Needs from the orchestrator"; the sample build changes no evidence record.
4. **Scales and treatment options come from the packs.** No route returns the risk profiles or the `treatment_option` lookup values. Every pack has one profile with likelihood and consequence from 1 to 5 and the options modify, retain, avoid and share, so the forms offer those; the server checks the profile in use and its refusal (`risk.scale`, `register.unknown_lookup`) shows in the form. The profile is not chosen on screen: the server takes the edition's only profile. Impact dimensions are not edited on screen.
5. **One control per treatment.** `TreatmentCreate` has one `targetType` and `targetCode`, so "linked controls" is one control or requirement per treatment; a risk treated through several controls gets one treatment per control. The treatment option belongs to the risk: Add treatment changes the risk's `treatmentOption` first when it differs (with `confirm: true` for a shared risk, which the form says), then adds the treatment. These are two writes: when the create is refused (a used code, an unknown target), the risk keeps the new option. The dialog keeps the risk with the ETag the change answered and the drawer reads the risk again, so the next try sends the create only and never a stale `If-Match`.
6. **The implementer is known only for a move made on screen.** The api does not return `implemented_by`. "Accept residual risk" is disabled for the implementer when the screen made the move (and in the sample); otherwise the server's BR-04 refusal shows in the form.
7. **Top Management** gets other people's rows with the owner `none` (F.7), so those rows show "Unassigned" as the owner.
8. **One extra read when a system opens.** The drill walks of `e2e/display.spec.js` and `e2e/i18n.spec.js` open the first row of a list the moment the screen's title shows. A list read from the api after the screen opened made the English and Indonesian walks of the API project differ ("Registers, drawer" was present in one walk and missing in the other). The layer item of `actions.ts` therefore reads the first page of Context issues in the background when a system opens (at most once a minute per system), so the screen has its rows on its first render (and opens without a wait for people too). It costs one `registers.list` read per system opened by a person who may read registers.

No dependency was added.

## Needs from the orchestrator

1. **Shared web tests.** `test/screens/host.test.tsx` and `test/api/controller.test.ts` belong to the orchestrator in this wave. After the commits of M2-10, M2-12 and M2-14, `npm test -w @mscd/web` fails 1 test there, on this package's new sidebar entry: "the sidebar inserts host screens into their group by order and drops empty groups" in `host.test.tsx` (line 90). With no built-in entries a Domain Owner now also gets Registers (sample personas `manager`, `owner`, `auditor` and `top`, order 50, after Required documented information), so the expected list becomes `[['impl', ['documented-info', 'registers']], ['audit', ['findings']]]`. `controller.test.ts` passes. The layer item `registers-prefetch` (order 92) renders nothing, so no slot test changes for it.
2. **A contract item needed before release** (R-14, no route added here): a way to store a picked file without an evidence or document record, for example `ctx.openPicker` answering the stored object id of an upload, or an upload intent of kind `competence` for the competence record itself. Until then a competence proof replaces the current file of the evidence record of competence it is kept with (deviation 3). The screen limits the damage (only records of clause 7.2 or A.6.3 are offered, and the form says the current file is replaced), but an auditor reading that evidence record sees a person's certificate as its current file. Once the item exists, the form sends the stored object id directly and offers no evidence record.
3. **Contract items for a later milestone** (R-14, no route added here): a list of a risk's treatments with status, implementer, target, target date and ETag (or treatments on the risk's `RegisterItem`) would replace deviations 1 and 6; the link ids on `RegisterItem.ms` (or a list of a record's links) would let the screen use `entity-links.make-primary` and `entity-links.remove` (deviation 2); the risk profiles and lookup values of the edition in a route or the snapshot would replace deviation 4.

## Follow-ups

- Other screens can open a register with `ctx.go('registers', {params: {tab: 'risks'}})`.
- Bulk import of risks (M2-08) can link to this screen once the import result names it; the import screen links risks to Chain stages today.
- A file kept for the next Edit lives in the browser session only (`cache.ts`). After a page reload the Edit form starts without it, and choosing the file again attaches it to the evidence record once more. The contract item of item 2 of "Needs from the orchestrator" removes this case.
- Sample personas hold no own-record grants (`SAMPLE_GRANTS` of `host.tsx`), so the Domain Owner persona reads only in the sample build; own-row editing is covered by unit tests and the API project.
