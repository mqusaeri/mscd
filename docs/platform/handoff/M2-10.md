# M2-10 handoff: people, roles and sign-in

M2-10 builds four web screen folders on the screen host of M2-01: "People and roles" (members, invitations, administration roles, role grants, open items held, company sign-in pre-registration, sign-in factor reset, disable and enable, and the roles and responsibilities CSV), "Pending approvals" (role grants and routing changes waiting for a second approval, with a sidebar badge), "Handover" (the open items of one person in a system, moved to a successor) and "Company sign-in" (OIDC and SAML identity providers and the local sign-in policy). No server code, shared contract, generated view or shared web file changed.

The first implementer of this package was stopped by an expired login after it wrote `users/{text,routes,model,api,sample}.ts`. This run kept those files (with the fixes listed under "Deviations") and built the rest.

### Pending approvals (`apps/web/src/screens/approvals/`)

Screen `approvals`, path `/admin/users/approvals`, group `admin`, order 42, perm `user.manage` or `storage.routing.manage`. "Role grants": person (with an Administrator badge, "Administrator" in Indonesian too, as on People and roles), role and system, who asked and when (audit trail metadata), who can approve, and Approve or Reject (Reject asks first). The buttons are disabled with the reason for the grantee ("This grant is for you; another Tenant Admin decides on it."), the requester ("You asked for this grant; ...") and a session that is not a Tenant Admin. "Routing changes": the pending routing rules of M2-09 (system, what they apply to, repository and mode, who asked) with the decision rules of `routing/model.ts` (A-50). The sidebar badge (`count`) is the number waiting: `badge.ts` keeps it, the layer item of `actions.ts` loads it when the app starts, when the organisation or person changes and when the person moves between screens (at most every 30 seconds, at once on People and roles and Pending approvals), and the screens set it after each load and change. In API builds the badge reads the `pending_grants` step of `admin.onboarding` (one request, `ms.admin`) and the routing rules (`storage.repository.read`).

### Handover (`apps/web/src/screens/handover/`)

Screen `handover`, path `/ms/:ms/handover`, group `audit`, order 80, scope `ms`, perm `record.assign` (MS Manager, Programme Owner; H.13). Pick the person, see the open items per kind (with a tick each) and the items (kind, code, title, due date), choose the successor, then "Move all items" or "Move the chosen kinds", each after a confirmation. A 409 `confirmation-required` of BR-22 (records shared with other systems) asks again and sends `confirm: true`. The warnings of the rules (BR-41, BR-16, BR-17, AUD-INDEP) are listed per record after the move; the list and the snapshot of the changed systems are reloaded (D2-08). The sample adapter moves the items for the session and changes the owners of requirements, documents and evidence in the sample data source, so the built-in screens follow. A sample document shared with the other systems (IMS-01 to IMS-04) asks for the BR-22 confirmation first, as the api does ("This change also applies to: ABMS, BCMS, QMS. Continue?"), and after it moves in every system that uses it.

The person who holds the items may have left. The snapshot's `PEOPLE` lists only active members with an active business role (`read-model.service.ts`), so a member who is disabled, or whose last role is revoked, drops out of it while still holding items, and `records.holdings` still answers for them. The person picker therefore has two groups: "Active members with a role" (the snapshot's people) and "Former members and people without a role": every handle the snapshot names as a holder in the system (requirement, document, evidence and activity owners, document approvers and pending holders, chain, gate and register holders, audit preparation and certification cycle people; `snapshotHolders`) that `PEOPLE` lacks, plus the person People and roles opened the screen with and any typed user name. People and roles passes the person's display name along with the handle, so such a person is named; otherwise the user name is shown. "Not in the list? Type the user name" takes a user name (checked against the `Handle` pattern on the screen; a name nobody has gets the api's 404 message). A note says when the chosen person is not an active member with a role. The successor is always chosen from the active members with a role. The Disable dialog of People and roles now adds that Handover lists the person under former members after disabling.

### Company sign-in (`apps/web/src/screens/identity-providers/`)

Screen `identity-providers`, path `/admin/sign-in/identity-providers`, group `admin`, order 46, perm `idp.manage`. Providers: button label and short id (and the JIT domains), protocol with the issuer and, for SAML, the link to the service provider metadata (`GET /auth/saml/:slug/metadata`), state with the second factor rule, last test of this browser session, and Test, Disable or Enable. "Add OIDC provider": button label (the short id follows it until typed), short id, icon, issuer, client id, client secret (write-only), scopes, the account id rule (`sub` or Entra object id with the tenant id), second factor (accept the provider's factor, fallback to the MSCD authenticator code or refuse; refusing needs the provider factor, F.5) and JIT on verified email domains; the redirect address to register at the provider is shown. "Add SAML provider": the same common fields, "Paste metadata XML" with "Fill from metadata" (entity id, the HTTP-Redirect or HTTP-POST sign-on address, the signing certificates as PEM; read without a DOM), sign-on address, identity provider entity id, certificates, service provider entity id (defaults to the metadata address and follows the short id), authentication contexts that count as a second factor, and the note that SAML never creates accounts at first sign-in (F.9). Field checks follow `IdentityProviderRequest`, and the server's field errors are shown next to the fields. "Test" shows the issuer and endpoints found, or why it failed. "Disable" warns that every session signed in through the provider ends, and more strongly for the only enabled provider. "Local sign-in" (`admin.organization.get` and `.update` with `If-Match`): everyone, administrators only, nobody; any limit warns to test company sign-in first (and that no provider is enabled and tested yet, and to keep administrators allowed); a 412 reloads the policy and says so.

## Deviations

1. **Path of Company sign-in.** The registry requires a path that ends with the screen id (D2-14), so `/admin/sign-in` became `/admin/sign-in/identity-providers`; the id stays `identity-providers`, clear of the sign-in pages of `src/auth`.
2. **The mock identity provider of the API spec.** `tools/mock-providers` has no OpenID Connect discovery, and its folder is owned by M2-S11 in wave 3b. `e2e/api-only/identity-providers.spec.js` serves the discovery document of an issuer on `127.0.0.1` from the spec process; the test profile accepts plain-HTTP issuers, and single tenancy does not limit issuers on the local network. Follow-up 1.
3. **Who asked for a grant.** `UserView.roles` carries no requester, so the screens read it from the audit trail metadata (`role.grant_requested`, `role.granted`, `role.grant_approved`, `role.grant_rejected`; `audit_trail.metadata.read`, Tenant Admins). Without it the decision buttons still show and the server refuses the requester (`SOD-SELF-GRANT`), whose message is shown. Follow-up 2.
4. **"Granted by" and "Since" in the CSV** come from the same audit entries: the person whose action made the grant apply (the approver of a four-eyes grant, else the person who granted it) and that date. Seeded grants have no such entry, so both cells stay empty for them. The CSV also has an Email column, so two people with one name can be told apart, and one row per administration role ("Whole organisation").
5. **The Handover link of Revoke and Disable** shows only when the session may open Handover in that system (`record.assign`); a Tenant Admin without a role there sees counts only (H.13) and the sentence that asks the primary MS Manager to move the items in Handover.
6. **The badge in API builds** reads the `pending_grants` step of `admin.onboarding`: one request for any number of members. It counts every waiting grant and routing change of the organisation, including those the session itself may not decide on, so a second administrator sees what waits for someone. A Storage Admin without `ms.admin` sees the routing changes only.
7. **Last test** is kept for the browser session only: the api stores no test history (`IdentityProviderView` has no test date). Follow-up 3.
8. **The search field of People and roles** has the placeholder "Name, email or job title" under the label "Search": `e2e/display.spec.js` treats any `main` input whose placeholder starts with "Search" or "Cari" as the list of a generated screen and expects its "Showing n items" line there.
9. **The sample build** keeps changes for the browser session. Its user limit is the sample licence (86 of 150), so the `LIC-USERS` message is covered by unit tests and the server's own rule; the API project cannot reach the limit of the test licence (150) in a spec either.
10. **Approvals reuses M2-09**: it imports `routing/adapter.ts`, `routing/model.ts` (`decisionBlock`) and `storage-admin/labels.ts`, so the decision rules of routing changes stay in one place. Both packages are in wave 3a.
11. **Former members in Handover** come from the snapshot; no new api read is needed. They are the handles the snapshot names as holders in the system that `PEOPLE` lacks, the person People and roles passes (with the display name) and typed user names. A person who left and holds only items the snapshot does not carry (a management review or a task, for example) is reached by typing the user name. Follow-up 5.

12. **The certificate helper of the API specs** (`tools/mock-providers/dist/certs.js`) is loaded with a dynamic import when a SAML test runs, as in `storage-admin.spec.js` of M2-09. Only the API stack builds `tools/*/dist/` (it is ignored by git), and the sample project collects the `api-only` specs before it filters them, so a static import would stop the whole sample suite on a fresh checkout such as the CI job `e2e-sample`.

No dependency was added.

## Second follow-up run of 29 Oct 2026 (review findings)

The review after the first follow-up run left one major and one minor finding open. This run fixed both, inside the folders of the package and this note.

1. **Major: a change of your own roles left the page with an old CSRF token.** Two actions of People and roles change the roles of the session user: an Edit of your own administration roles, and the revocation of your own active grant. The server then gives the session a new id (F.1), and the CSRF token, an HMAC of the session cookie, changes with it. The screen never read `GET /me` again, so every later change in the same page was refused with 403 `csrf`, and the permissions and the sidebar stayed as they were. Now:
   - `renewsOnEdit` and `renewsOnRevoke` (`users/model.ts`) name the two cases as the server does: an Edit whose administration roles differ from your current ones, and the revocation of your own grant while it is active (a waiting grant renews nothing).
   - `saveEdit` and `revokeGrant` (`users/dialogs.tsx`) run the change and then, in those cases, `renewSession`: `GET /me` through the host's client (`renewSession` of the adapter, route `me.get`). `ApiClient` takes the new token from that answer. The dialog stays busy until it has, so the next change in the same page carries the new token.
   - After that, the screen loads the snapshot again: the organisation snapshot and, for a revocation, the system of the grant. `/ui/org` carries the permissions, the systems of the session and the host screens of the sidebar, so they follow the new roles without a new page load.
   - The shell keeps the `Me` it read when it started, and `ctx.reload` does not read `/me`. So when a role the shell read from `Me` changed, the app loads again after the toast (1.2 seconds, with the busy bar). These roles are: whether the session holds an administration role at all, whether it is a Tenant Admin, and the business roles and UI role in a system it still holds. `sessionRestart` decides this. The app also loads again when `GET /me` fails, because the token may then be the old one. Adding Storage Admin to a Tenant Admin, or revoking your only role in a system, needs no new load.
   - The sample build has no session, and its `renewSession` renews nothing.
