# M2-S13 handoff: SaaS end-to-end run, CI jobs and go-live evidence

M2-S13 proves the SaaS service end to end: the boundary suites of the server run again with tenancy `multi`, a browser run takes two customer organisations through their whole life on one stack of release images, CI runs both, and the go-live checklist gets its evidence. It also finishes four items the orchestrator assigned from earlier packages (the legal links on SaaS, the mock DNS in the API E2E stack, the Grafana test in CI, and three M2-S09 follow-ups).

## What was built

### SaaS integration run (`npm run test:int:saas -w @mscd/server`)

| File | Content |
|---|---|
| `apps/server/vitest.int-saas.config.ts` | The integration configuration (`vitest.int.config.ts`) with the suites `security`, `rbac` and `contract` (tenancy `multi`) and `saas-ops`, `entitlements` and `domains` (the operator's organisation lifecycle), the setup file `test/setup/saas-run.ts`, and `MSCD_TEST_TENANCY=multi` for the global setup and every worker |
| `apps/server/test/setup/tenancy.ts` | The tenancy of a test run: the variable of the SaaS run, the overrides of `profiles/saas.yaml` (`MSCD__TENANCY__MODE=multi`, `MSCD__TENANCY__ISOLATION=schema`), the two suite lists, `isSaasRun()`, `testTenancy()` (the mode the configuration of the current file reads) and `suiteOf()` |
| `apps/server/test/setup/saas-run.ts` | Runs before each test file: the boundary suites get the multi-tenancy overrides in their environment, so every application and configuration they build runs like a SaaS server; the operator suites keep the single tenancy of the test profile as their default (each of their tests sets tenancy `multi` itself, and their single-tenancy tests check the on-premise refusals). A file of any other suite stops the run |
| `apps/server/test/setup/global-db.ts` | In the SaaS run the demo template is the multi-tenancy template: `seed demo` runs with tenancy `multi` and schema isolation, and the setup checks that the template holds at least two active organisations, each in a schema of its own that exists (it holds four). A SaaS run whose template cannot be built stops, so its suites never run without the template |
| `apps/server/test/setup/keycloak.ts` | The two CodeQL alerts of this file (12 `js/double-escaping`, 10 `js/incomplete-multi-character-sanitization`): entities are decoded in one pass, and tags are removed until none is left |
| `apps/server/package.json` | Script `test:int:saas` (build information, then the configuration above). The lockfile is unchanged |

The route-generated sweeps cover every route of the contract, the 17 operator routes (`ops.*`) included: each is one generated RBAC test over every role of F.6, and the contract suite checks every route.

## Deviations

1. **Operator suites keep single tenancy as their default** in `test:int:saas`. Their tests set tenancy `multi` themselves and also test the on-premise refusals in single tenancy, which a forced `multi` would break.
2. **The multi-tenancy template is the demo seed under tenancy `multi`** with its four organisations. The brief asks for two organisations; the security and rbac suites address the demo organisations by id, so the template keeps all four.
3. **"Sign-in shows the inactive message" (step 6):** the sign-in itself succeeds, because the account is not locked (a person may belong to other organisations), and the app then shows the full-page message with the server's reason "The organisation is not active" on every page of Beta. The run checks the 403 `organisation-inactive` of the first load and the readability of the message.
4. **Discovery for Alpha's administrator (step 3)** answers `{ local: true, providers: [] }`: Alpha has no company sign-in, and D-S10 gives every email without one the same answer. The password sign-in then opens Alpha, which the run checks through `/api/v1/me`.
5. **Extra steps in step 4:** a second Tenant Admin and the Management System Manager role (four eyes) are needed before a system can start its implementation and take evidence; the readiness report export gives the isolation step a real export URL.
6. **The user limit (step 8)** is lowered through custom limits (no preset, users 2), the path the console offers for a limit below the preset.
7. **`saas-static` runs the format check of the checklist** (the default mode of `check-golive.mjs`). `--agent-items-done` stays a manual check: GL-13 depends on the daily state of the security scans and would turn every push red.

## Build host memory (the WSL stops of 28 and 29 October 2026)

The build host is WSL 2 on a Windows 11 PC with 31.7 GiB of RAM. Its virtual machine (VM) stopped nine times on 28 and 29 October; eight of these stops came 3 seconds to 3 minutes after Windows reported a low virtual memory condition, two of them while this package ran its tests (21:12 and 23:20 on 29 October, UTC+7). Windows ran out of commit memory and stopped the VM. The kernel logs of the stopped VMs are lost with them (this WSL keeps no journal and no `kern.log`, and the ring buffer of a VM ends with it), so the cause rests on the Windows events below. The VM that runs since 29 October 23:25 has no out-of-memory kill in its ring buffer.

- **What Windows logged.** Event 2004 of Resource-Exhaustion-Detector ("Windows successfully diagnosed a low virtual memory condition") was logged 68 times from 20 to 29 October. Before Windows restarted on 26 October at 03:12, 25 of these events named svchost.exe first (2.0 to 3.1 GiB, growing day by day): Windows was then short of commit memory even with WSL at about 2 GiB. Since the restart, all 31 events name vmmemWSL, the WSL VM, first, at 9.4 to 15.9 GiB (the 15 events of 28 and 29 October at 11.8 to 15.9 GiB). Hyper-V removed the VM's network port (VmSwitch event 69, "Port ... successfully deleted - switch ... WSL (Hyper-V firewall)") nine times on 28 and 29 October: 28 October at 13:19, 13:27, 13:41, 14:03 and 22:26, and 29 October at 14:08, 18:43, 21:12 and 23:20. Eight of them came 3 seconds to 3 minutes after an event 2004, with vmmemWSL at 11.8 to 15.4 GiB; the one at 13:41 came 15 minutes after one. Each time WSL started again with a new VM.
- **Why WSL can outgrow Windows.** Windows backs every page the VM uses with commit memory, and the commit limit is RAM plus page file. Only the page file on C: is in use (set to 1 to 4 GiB, 2 GiB now), so the limit is 33.7 GiB. A second page file on D: (4 to 32 GiB) is set, but Windows has not created it; Windows has not restarted since 26 October. The WSL settings file in the Windows user profile sets no `memory` limit, so Linux sees 15.5 GiB (MemTotal 16,215,944 kB), with an 8 GiB swap file and `autoMemoryReclaim=Gradual`. Windows and its desktop apps commit about 20 GiB on their own. When Linux fills its memory with processes and page cache (image builds, layer extraction, `node_modules`, test databases), vmmemWSL grows, the sum reaches the commit limit, and Windows stops the VM because it cannot back it.
- **Headroom now.** On 30 October at 04:00 (UTC+7), with no stack running, Windows had 29.3 GiB committed of 33.7 GiB (vmmemWSL 9.2 GiB), so about 4.4 GiB were free. One Compose stack or one suite fits in that; two at once do not.
- **What ran at the two stops of this package.** At 21:12 the first implementer ran `test:int:saas`. From 23:14 to 23:20 these ran together: the product owner's preview SaaS stack (10 containers); this package's SaaS run (three release image builds, then the stack with the monitoring overlay, 14 containers); the full server integration suite; the bootstrap tests; and the host's own services.
- **Measured one at a time.** The SaaS stack with the monitoring overlay uses 0.73 GiB in its 14 containers and the run's Chromium up to 1.6 GiB. Under the memory guard (below), which drops the page cache, the whole SaaS run, release image builds included, peaked at 7.9 GiB of Linux memory with page cache, `test:int:saas` at 7.4 GiB and the sample web E2E suite with 6 workers at 8.9 GiB; Windows free commit went down to 2.3 GiB. Without the guard, the SaaS run with the monitoring overlay peaked at 9.8 GiB (10,012 MiB) and Windows free commit fell to 2.8 GiB (2,872 MiB), measured by the verifier of this package.
- **Damage found.** The stop at 23:20 left two empty files in Playwright's compile cache (`/tmp/playwright-transform-cache-0/c6/c69409dc78_e1bda34_saasspec.js` and `.map`), so the next SaaS run reported "No tests found". They are removed. On 30 October `git fsck` reports nothing, and no empty file is left in the Playwright compile cache or the `node_modules` caches.

How this package ran after that: one Compose stack or suite at a time, the page cache dropped before each run, and a guard script kept outside the repository (`/var/tmp/m2-s13/memguard.sh`). Every 10 s it reads Windows free commit with `typeperf`; it drops the Linux page cache when free commit falls below 2.4 GiB or the Linux footprint passes 8.8 GiB, and it stops the current run after two readings below 1.2 GiB. Its logs are `/var/tmp/m2-s13/mem-watch.log`, `mem-watch-followup.log` and `mem-watch-fu2.log` (the last round).

What the owner can change on the PC (none of it is in the repository). On 30 October at 04:00 (UTC+7) neither of the first two is in place: Windows has not restarted since 26 October, so D: still has no page file (C: has 2,068 MiB allocated), and `.wslconfig` still has no `memory` line.

Linux then handles a shortage itself (it drops page cache, then swaps, then the out-of-memory killer stops one process) and the VM keeps running. With today's limit, 12 GiB for WSL and about 20 GiB for Windows leave under 2 GiB of headroom, so do this together with step 1.
