# M3-M01 handoff: open follow-ups of the installer and the bundle

M3-M01 closes the last three open follow-ups of `CLAUDE.md` (MILESTONE-3 K.1): the installer saves the Docker Compose project name of an installation, `install.sh --yes` creates a default organisation when no slug is given, and every bundle and both release images carry a third-party notices file that CI keeps current.

## What was built

### Compose project name saved in `.env` (`deploy/scripts/lib/common.sh`, `install.sh`, `upgrade.sh`, `uninstall.sh`)

- `lib/common.sh`: `MSCD_PROJECT` is no longer read-only. New `MSCD_DEFAULT_PROJECT` (`mscd`) and `MSCD_ENV_PROJECT` (the value of `COMPOSE_PROJECT_NAME` in the caller's environment). The SaaS and backup scripts keep working as before: they export `COMPOSE_PROJECT_NAME` from their `.env` before they source the file and never call the new functions.
- `resolve_project INSTALL_DIR` sets `MSCD_PROJECT` and exports `COMPOSE_PROJECT_NAME` with it, so every `docker compose` call and every container, network and volume lookup of the script use one name. Order: the `COMPOSE_PROJECT_NAME` saved in `INSTALL_DIR/.env`; the environment (a new install); for an installation made before this change, the project of the containers that Compose made for that directory (label `com.docker.compose.project.working_dir`); then `mscd`. A saved name and a different environment value give `FAIL The installation in <dir> uses the Compose project <saved> (saved in <dir>/.env), but COMPOSE_PROJECT_NAME is set to <other>` with a `Fix:` line, and the script stops before it changes anything (the usual "check(s) failed ... Nothing was changed"). An invalid name in the environment or in `.env` fails the same way. The function prints one `PASS Compose project <name> (...)` line that says where the name came from.
- `save_project ENV_FILE` writes `COMPOSE_PROJECT_NAME=<name>` with a three-line comment the first time (do not change it, or the data volumes are not found). Compose reads the variable from `.env` too, so `docker compose ps` in the install directory finds the project without the variable.
- `install.sh` calls `resolve_project` among the host checks (before the container owner check), shows "Compose project" in the settings summary and saves the name in `write_env`; `restore_previous` saves it again after putting back the settings of an older installation. `upgrade.sh` resolves the name in `check_installation` (upgrade and rollback), saves it right after the confirmation (so the settings kept for a rollback hold it too) and again in `restore_files`. `uninstall.sh` resolves it among its checks. Help texts and file headers say where the name comes from.

### Default organisation (`install.sh`)

- `install.sh --yes` on a new installation (no `--org-slug`, no slug saved in `.env`) uses the slug `default` and the name "Default organisation", or the name of `--org-name` when one is given. Before installing it prints that no slug was given, the slug and the name, that the slug cannot change, and that the name can change in the app (Administration, Organisation); the summary at the end says it again. Without `--yes` the installer still asks for both. `--org-slug` without `--org-name` still stops (the message now shows an example). The organisation screen (`admin.organization.update`, screen "Organisation") is where a Tenant Admin changes the name.

### Third-party notices (`tools/scripts/third-party-notices.mjs`, `THIRD-PARTY-NOTICES.md`, `build-bundle.sh`, both Dockerfiles, `ci.yml`)

- The generator walks the production tree of `package-lock.json` from the workspaces the release images run: `apps/server`, `packages/shared` and `packages/pack-tools` (the `npm ci --omit=dev` of `server.Dockerfile`) and `apps/web` (bundled by Vite). It follows `dependencies`, `optionalDependencies` and non-optional `peerDependencies`, resolved through the `node_modules` folders of the lockfile as Node.js does; `devDependencies` are never followed and the `@mscd/*` workspaces are left out. One row per name and version (478 packages today) with the licence of the lockfile entry, the image (server, web or both) and a link to its licence text. The texts come from each package's licence files (`LICENSE`, `LICENCE`, `COPYING`, `UNLICENSE` with any suffix) and `NOTICE` files, normalised (no BOM, LF, no trailing spaces) and printed once per distinct text (235 texts). 14 packages hold no licence file; they are listed in their own table with the licence their `package.json` declares and their source address. The SecLists notice is read from the header of `apps/server/src/modules/identity/common-passwords.txt` (from `Source:` to the first empty line); the generator fails when it is missing.
- Platform builds (optional packages limited to an operating system or processor, such as `@node-rs/argon2-linux-x64-musl`) are listed when they can run in a Linux image on x64 or arm64, with the licence text of the package they belong to when both declare the same licence. Their folders are never read, because npm installs only the builds of the machine it runs on, so the file is the same on every machine.
- `--check` writes nothing and exits 1 when the file is missing or out of date (it names the first differing line). Exit 2 means a wrong option, or `node_modules` does not match the lockfile (run `npm ci`). Exit 3 means the file cannot be generated: `package-lock.json` cannot be read, has no entry for a package of the tree or does not resolve a dependency, or the password list has no SecLists notice (the message names which). Exit 1 is used for nothing else, so a caller can name the cause. `--out FILE` writes another file. No new dependency (R-03).
- `THIRD-PARTY-NOTICES.md` (534 KB) sits at the repository root, outside `docs/`, so the licence texts are not held to the writing rules. The text MSCD wrote around them follows them.
- `build-bundle.sh` copies the file into the bundle (it is then in `SHA256SUMS`) and, in a new check step of both modes (bundle and `--images-only`), compares it with the lockfile when Node.js and `node_modules` are present. It prints the generator's message and then one line that follows the exit code: "is out of date" (1), "could not be compared with package-lock.json (run npm ci)" (2) or "could not be generated (exit N, cause above)" (3 or any other code, with a fix line that points at the lockfile or the password list). Each of them stops a `--release` build and is a warning for a test build; without Node.js or `node_modules` it prints an `INFO` line, because CI checks it.
- `server.Dockerfile` copies it to `/app/THIRD-PARTY-NOTICES.md` in the `runtime-base` stage (so the release and demo targets carry it), `web.Dockerfile` to `/usr/share/doc/mscd/THIRD-PARTY-NOTICES.md`, outside the folder NGINX serves. `install.sh` and `upgrade.sh` copy the bundle's file into the install directory, as they do with `INSTALL-ONPREM.md`.
- `.github/workflows/ci.yml`: one step in the job "Lint, typecheck and unit tests", which runs no browser suite, after `npm ci`: `node tools/scripts/third-party-notices.mjs --check`. The browser jobs that M2-21 is changing were not touched.
