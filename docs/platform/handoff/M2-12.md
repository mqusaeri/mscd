# M2-12 handoff: document control screens

M2-12 builds the document control screens of Milestone 2 on the extension points of M2-01 and the routes of M2-07: the New document form, the document control panel below every document detail (Edit, Change owner or approver, Reassign, Attach first version, Upload new version with a change summary, the Versions tab with "Open file"), the review panel of a document in review (Approve, Return to draft) and of a draft, and the screen "Required documented information" with the scope panel of H.9, "Register from template", "Link existing document" and a sidebar badge of the missing items.

## What was built

### Document control forms (`apps/web/src/screens/docs-edit`)

The folder holds no screen of its own (no `index.tsx`); it claims actions, adds the detail extension of `doc` and renders its forms in the host layer.

| File | Content |

## Deviations

1. **Path `/ms/:ms/documented-info`.** The brief names the screen id `documented-info` and the path `/ms/:ms/documented-information`; the registry of M2-01 requires the path to end with the screen id (D2-14), so the path is `/ms/:ms/documented-info`. The api route keeps `/api/v1/ms/{ms}/documented-information`.
2. **The claims keep their Milestone 1 toasts.** `e2e/documents.spec.js`, `e2e/controls.spec.js` and `e2e/shell.spec.js` (Milestone 1, not owned, and not `@sample-only` except the shell check) click "New document", "Open review" and "Continue draft" and expect the toasts of Milestone 1 in both projects (R-15). Each claim shows that toast and then opens its form; the texts say what happens ("New document form opened"). The orchestrator can drop the toasts once those specs expect the forms. No page action was added to a built-in screen, so `e2e/shell.spec.js` counts the same page actions as before.
3. **`mytasks.openDoc` is claimed here.** The brief does not name it; it is the "Open document" of a document task in My Tasks and opens the same review panel.
4. **Document types and templates.** No route lists the `doc_type` lookup or the document templates. The form offers the seven `doc_type` codes that all six packs share (`policy`, `standard`, `procedure`, `plan`, `register`, `record`, `form`; the server refuses another one with 422 `documents.unknown_doc_type`, shown above the form). The templates come from `documented-info.list`: the template code, the title of its documented information row, and the type inferred from the code prefix (`POL`, `SCO`, `QM` policy; `STD` standard; `PRC`, `IMS` procedure; `PLN` plan; `REG`, `SOA` register; `REC` record; `FRM` form), which matches every template of the six packs. These cover about half of each pack's templates, so the output codes of the system's activities that no documented information row names follow (ISO/IEC 27001: IMS-01 to IMS-04, PRC-07, PRC-08, PRC-11, PRC-13, the codes BR-40 checks), typed by their prefix and labelled with the first activity that expects them ("PRC-13, output of activity 5.8 Establish incident management process"); they fill code and type and leave the title to the person, since no route gives the template title. Pack templates that neither a documented information row nor an activity names (for example PLN-02, PRC-05, PRC-09, REG-03 and STD-06 of ISO/IEC 27001) are not offered and are typed by hand. Follow-up 1.
5. **Edit without the current classification.** The snapshot document has no classification and no external facts, so Edit offers "Keep the current classification" and leaves the external fields empty with "Leave a field empty to keep its current value"; only the members that change are sent. Follow-up 2.
6. **Two upload buttons on an approved document.** The generated detail keeps its Milestone 1 "Upload new version" for approved documents (not claimable, no change summary). The panel's button on an approved document is therefore labelled "Upload with change summary"; on drafts and expired documents, where the generated detail has no upload, it is "Attach first version" or "Upload new version". Follow-up 3.
7. **Reassign only for a document in review, with the checks in the browser.** As the brief says. `records.assign` answers BR-41 only, so BR-17 (a person is required; Save stays back) and BR-16 (the submitter of the version in review is named when chosen) are checked in the form.
8. **Sample build and the Milestone 1 overrides.** `SampleDataSource` keeps the changes of its Milestone 1 commands (Start review, the picker's Upload new version) in an override store that wins over `mutate`. When such an override holds the old status, the sample adapter applies the Milestone 1 command with the same effect (Start review for In review, a new approved version for an approval) and refuses, with a message, the two changes no such command makes (Return to draft, and approving a review without a new file after Start review). Follow-up 4.
9. **API spec: the customer code links the risk treatment plan.** The brief's example links `ISP-001` to the policy code. The demo seed holds a policy document in every system and the activities that expect it are verified, so no activity could show the change. The spec registers `RTP-001` and links it to `PLN-01` (risk treatment plan), the open activity (ISMS 4.9) of the seed whose pack code has no document, and checks BR-40 before and after.
10. **Scope panel version from the version history.** The snapshot's `ver` is the label of the stored file (`v1` for a Managed Vault upload), so the panel reads the approved version's label and date from `documents.versions.list` (one request while an approved scope statement exists) and shows the snapshot values until then.
11. **Versions as a list.** The drawer is 560px wide, so each version is a block (label, status, submitter and approver with dates, change summary, rejection note, Open file) instead of a table with nine columns.
12. **Sample evidence of records to retain.** The sample keeps evidence per top clause (`Cl. 9.2`), so a record row of a sub-clause (`9.2.2`) also counts the evidence of its top clause in the sample build; the api resolves sub-clauses as M2-07 built it.
13. **Rows covered only by an implementing document.** `documented-info.list` falls back on the implementing document of the clause's applicability entry when no document has the pack code (M2-07). The row shows that document and its state, as the api answers. Activities resolve only the document with the pack code or the one linked to it (BR-40), so such a row still offers "Register from template" and "Link existing document", and the scope panel does not take an implementing document of clause 4.3 (in the demo, the quality manual QM-01 of the QMS and the policy POL-A01 of the ABMS) for the scope statement.
14. **API spec: rina registers, bagus submits.** The plan's acceptance says the API spec "registers a document as `bagus`". Under F.6 only the MS Manager holds `document.manage` (`packages/shared/src/authz/matrix.ts`: `'document.manage': ms([MM])`), so bagus (Domain Owner) cannot register documents. The spec has rina register SCO-A01 with bagus as owner; bagus attaches and submits the first version, cannot approve it ("You submitted this version"), and rina approves it. The rule the acceptance checks (the submitter cannot approve, another person can, BR-16) is the same.
15. **Template documents of records to retain are found in the browser.** `documented-info.list` lists a record to retain with its evidence and leaves `document` empty, also when its template code is a pack code that activities expect (PRC-04 of ISO/IEC 27001 is named only by the records DI-03 and DI-04; PLN-B01 and IMS-03 of ISO 22301 and IMS-03 of ISO 37001 likewise). The rows of such records offer the actions for the template code, and the adapters find the document that stands for it: the sample adapter as it resolves documents to maintain, the api adapter from the list and the snapshot (the `api.ts` row of the table above). The api build can read a link back only through an activity that expects the code or a row to maintain that names it, so a record whose template code neither covers (ISO/IEC 27001: DI-07 REG-01, DI-08 REG-04, DI-10 REG-02, DI-12 to DI-15 REC-01 to REC-04) offers "Register from template" only, in both builds; the server would accept such a link (`documented-info.link` takes every template code of the pack), but the screen could not show it or remove it after a new page load. Follow-up 9 lifts this.
16. **Indonesian titles in the sample build.** The pack holds English titles only (follow-up 8), and the Indonesian check of `e2e/display.spec.js` (Milestone 1, owned by M2-01) refuses the word "showing" in Indonesian screens, which four ISO/IEC 27001 and ISO 9001 titles contain. The sample rows therefore carry an Indonesian title (the screen shows it in Indonesian, the English title otherwise), so the sample suite passes without a change outside this package (R-15). The api build shows the English pack title in both languages until follow-up 8.

No dependency was added. No file outside the Owns list was changed.

## Follow-ups

1. **Orchestrator, contract (R-14):** add the template's title and `doc_type` to `DocumentedInfoItem` (or a route that lists the `doc_type` lookup and the document templates of the edition). `templatesOf` in `docs-edit/api.ts` and `docTypeOfTemplate` then take them from the api, and New document can offer every template of the edition with its title (today the templates of documented information rows and the activity outputs, deviation 4).
2. **Orchestrator, ui contract:** the snapshot `Document` could carry `classification`, `externalSource`, `externalRef` and `receivedAt`, so Edit shows the values in force.
3. **Orchestrator or M2-17, `MscdApp.jsx`:** make the generated "Upload new version" of an approved document claimable (for example `docs.uploadNew`) or leave it to the panel, then label the panel's button "Upload new version" in every state.
4. **Owner of `SampleDataSource.js`:** let `mutate` win over the Milestone 1 overrides of the same record (or offer a way to clear them), then remove the fallbacks of deviation 8.
5. **Orchestrator, Milestone 1 specs:** once `e2e/documents.spec.js`, `e2e/controls.spec.js` and `e2e/shell.spec.js` expect the forms, the claims of `docs-edit/actions.ts` can drop the Milestone 1 toasts (deviation 2). The toast of Open review names the version in force (`Opening STD-05 v1.1: review workflow`, as `e2e/controls.spec.js` expects for PRC-07), while the review panel that opens shows the version under review (v2.0): drop the toast then, or name the document without a version as `mytasks.openDoc` does, and change `e2e/screens/docs-edit.spec.js` lines 41 and 99 with it.
6. **Shared web tests:** `apps/web/test/screens/host.test.tsx` and `apps/web/test/api/controller.test.ts` list the Administration entries only; the Implementation entry "Required documented information" of this package needs no change there. Their current failures come from the Administration entries of M2-10 and M2-16, the `req` extension of M2-11 and the top bar item of M2-16.
7. **Orchestrator, `e2e/display.spec.js` (owned by M2-01), decision recorded:** the check `not.toMatch(/\bshowing\b|.../)` looks for the leftover key `showing`, and the ISO/IEC 27001 and ISO 9001 packs name four documented information items "Records showing ...". In the sample build the rows now carry Indonesian titles (deviation 16), and "Indonesian renders every ISMS screen" and "every QMS screen" pass (sample run below). The api build still shows the English pack titles in Indonesian, so the same check can fail in the API project once the rows have loaded before it reads the screen. Until follow-up 8 lands, narrow the pattern for the key (for example `/\bshowing \d/i`, the list footer) before the wave's full API suite runs.
8. **Orchestrator, pack format (R-14):** documented information titles have no Indonesian column (`documented_info.csv` has one `title`), so the Indonesian screen of the api build shows the English wording of the standard. A `title_id` column and a `titleId` member of `DocumentedInfoItem` let the screen show both languages: `fromItem` in `documented-info/api.ts` then maps `titleId` (the row type and the screen already take it), and the Indonesian titles of `documented-info/sample.ts` can move to the pack sources.
9. **Orchestrator, contract (R-14):** `DocumentedInfoItem` of a record to retain with a template code could carry the document that stands for the template code (`templateDocument`: id, code, title, linked; the same `resolvePackDocument` the activities use). The api adapter then maps it and drops `documentForCode` and the snapshot reading, and `rowActions` can offer the link actions on every record with a template code (deviation 15).
