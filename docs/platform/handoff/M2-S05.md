# M2-S05 handoff: deploy script and deploy workflow

## What was built

| File | Content |
|---|---|
| `deploy/scripts/saas-deploy.sh` | The deploy script of a SaaS server, actions `deploy`, `rollback` and `check-only`. Sources `lib/common.sh` (unchanged, so `install.sh` and `upgrade.sh` behave as before) and the new `lib/saas.sh`. Options: `--target production\|staging\|test` (required for deploy and rollback), `--install-dir` (default `/opt/mscd`), `--release-dir` (default: the release of the script), `--digests`, `--version`, `--timeout`, `--verify-timeout`, `--min-free-disk`, `--skip-backup`, `--cosign`, `--no-verify-signature` (only for images of a registry on `127.0.0.1`). Secrets and settings come on standard input as `NAME=<base64>` lines; nothing secret is ever an argument. The whole output also goes to `/opt/mscd/logs/<action>-<time>.log` |
| `deploy/scripts/lib/saas.sh` | Helpers: the demo refusals, host checks, standard input, settings and `.env`, signatures and pulls, key files, the off-site backup and monitoring files, the installed files and the state, `saas_stage_release` (the file list of a release folder, shared by the workflow and the rehearsal) and `saas_encode_input` (standard input as the workflow builds it) |
| `.github/workflows/deploy-prod.yml` | `workflow_dispatch` with `version`, `action` (`deploy`, `rollback`), `target` (`staging`, `production`) and `skip_backup`; environment `${{ inputs.target }}`; job concurrency `deploy-${{ inputs.target }}` with `cancel-in-progress: false` (shared with `bootstrap-prod.yml`); permissions `contents: read`, `packages: read`. Steps: check the inputs; check out the tag and check its commit; install cosign (`sigstore/cosign-installer` v4.1.2 by SHA, cosign v3.1.3, as `release.yml`); download `digests.json` of the GitHub Release and check names and digests; `cosign verify` of both digests with the identity `https://github.com/mqusaeri/mscd/.github/workflows/release.yml@refs/tags/<tag>` and the GitHub OIDC issuer; one SSH connection (ControlMaster) with the pinned host key; rsync of the release folder (and the runner's cosign to `/opt/mscd/bin/cosign`); `docker login ghcr.io --password-stdin` with the job token, `saas-deploy.sh` with every value on standard input (its output fenced with `::stop-commands::`, so no line of a service log acts as a workflow command; its WARN lines then become warnings of the run and lines of the summary), `docker logout`; `https://<domain>/healthz` and the version from the runner; a summary with versions and timings only; close the connection and delete the key (`always()`) |
| `deploy/scripts/test/saas-rehearsal.sh` | The rehearsal of the brief, plus two more broken versions and the refusals (see Tests). `--workflow` runs the SSH, copy and deploy steps of `deploy-prod.yml` against a test server; `--down` removes what a run left |
| `docs/saas/deploy.md` | How an agent starts a run and the owner approves it, every value of the GitHub environment and where it goes, what a deploy does step by step, the first deploy with the Let's Encrypt staging CA, the release order (staging, migration rehearsal of M2-S07, production), what users see, automatic and manual rollback, restoring the database by hand, keys, the server folder, commands on the server, the rehearsal and troubleshooting |

### Deploy order on the server (`saas-deploy.sh deploy`)

1. Lock the install folder (`flock`).
2. Refusals before any other check, also in `check-only`: image names ending in `-demo` (environment, `digests.json`, `.env` in place) "demo images are refused"; `demo.yaml` or `test.yaml` profiles and any `MSCD_DEMO*` setting (environment, `.env`, example) "demo and test profiles are refused"; `config/demo-secrets` or `docker-compose.demo.yml` in the release folder or the install folder "demo files are refused". Every refusal is reported, then the script stops.
3. Docker, memory (7.4 GB or more), free disk for Docker data (`--min-free-disk`, default 10 GB) and the install folder (1 GB), and the tools it uses.
4. `digests.json` of the release: version, image names, digests, refs. A version older than the running one is refused (rollback is the way back).
5. Standard input: all lines checked (known names, base64, no repeats, the four required secrets present).
6. The new `.env`: `.env.saas.example` of the release, then every setting from standard input, else the environment, else the `.env` in place, else the example; worked out by the deploy: the images and `MSCD_VERSION` (from `digests.json`), `MSCD_PUBLIC_URL`, `MSCD_EDGE_IPV6` (true when the server has a global IPv6 address), `COMPOSE_PROJECT_NAME`, `COMPOSE_FILE`, `MSCD_SECRETS_DIR`, `MSCD_METRICS_DIR` and `MSCD_SITE_DIR`. Checks: host names, placeholders of the example refused on staging and production, `MSCD_TLS_MODE=internal` only with `--target test`, ports, subnets inside `172.31.0.0/16`, the `saas.yaml` profile, `COMPOSE_PROFILES` with `bundled-db` and `bundled-s3` (`grafana` is added when `OPS_DOMAIN` is set), and no character that `.env` cannot carry literally. `docker compose config -q` with the release's Compose files.
7. Images: `cosign verify` of both digests (identity of `release.yml` at `v<version>`), pull by digest when missing, the server image must carry `com.cyberlentera.mscd.flavor=release` ("demo images are refused" for `demo`), then `--help` once. Images pulled for a refused release are removed again.
8. Secrets: `platform.key`, `storage.key` and `audit-anchor.key` from standard input (written when missing; an existing file must hold the same key, compared without white space, read through a short-lived container as the file's owner when the deploy account cannot read it; any difference stops the run before anything is written); `audit-anchor.pub` derived with `openssl pkey -pubout` (the SPKI PEM of `keys generate`); then `ensure_database_secrets`, `ensure_key_secrets`, `ensure_certificates`, `set_smtp_password`, `fix_secret_owners`; then one file per backup and monitoring value in `secrets/backup` and `secrets/ops` (mode 0400, folders 0700); a value sent empty removes its file.
9. Pre-deploy `pg_dump --format=custom` of `mscd` into `/opt/mscd/backup/pre-deploy/<time>-<from>-to-<to>.dump` (mode 0600, checked for the `PGDMP` header and free space first, last 3 kept); `deploy/backup/backup.sh --pre-deploy <file> --install-dir <dir>` when the release has it.
10. Save the files in place to `state/saved/<time>-<version>` (the rollback point), install the release's `deploy/` tree, site and `.env`; start PostgreSQL and SeaweedFS when they do not run yet (first deploy).
11. `docker compose run --rm --no-deps migrate` alone, time limit 600 s plus 20 s per `org_` schema, log in `/opt/mscd/logs/migrate-<version>-<time>.log`, printed back with `org_<slug>` and email addresses hidden.
12. `up -d --no-deps --wait` one service at a time: postgres and objectstore (recreated only when their settings changed), storage-gateway, api and worker (recreated every time), web, caddy (`--remove-orphans`; `caddy reload` when only its configuration files changed), then the services of the overlays (recreated every time; long-running ones healthy or running, one-shots such as `ops-init` waited for until they end with code 0), then `caddy reload` when `ops-init` ran, so Caddy reads the Grafana host it writes. A failure in this last part is a warning, recorded as `overlay=problem` in `history.log`; the healthy app is not rolled back.
13. `/readyz` of api, worker and storage-gateway inside their containers; `/healthz` and `/api/v1/system/profile` (version and `deploy: saas`) through Caddy with `--resolve <domain>:<port>:127.0.0.1`.
14. State: `state/current.env`, `state/previous.env`, `state/history.log`; the same release deployed again does not count as a rollback point; images of the last 3 releases kept (current and the 2 newest saved), release folders of the saved releases kept, logs pruned.

A failed step 10 to 13 puts the saved files back and starts the previous digests (pulled again when missing), then checks them the same way: after a failed migrate without recreating anything, after a failed service or check with the server services recreated. A first deploy that fails has nothing to go back to and says so.

`rollback` goes back to the newest saved release (`--version` must name it, and `digests.json` of the release folder must name the same images when it is there), with the same refusals, signature check, pulls, key check, a pre-rollback dump, no migrate, the restart with the server services recreated and the checks. A failed rollback returns to the release it started from.

## Deviations

| # | Brief | Built | Why |
|---|---|---|---|
| 1 | Steps 3 to 6: `.env`, keys, generated secrets, then the image pull | The new `.env` is checked first (step 6 above) and installed in step 10; the images are verified and pulled (step 7) before any secret is written | The key comparison and `fix_secret_owners` run short-lived containers of the server image when the deploy account cannot read the files. The image must be verified before it touches the secrets. The keys are still written before any other secret, and the old containers keep running throughout |
| 2 | "Write `.env`", Compose files in the release folder | Install layout: `/opt/mscd/.env`, and the release's `deploy/` tree copied in place to `/opt/mscd/deploy`; `deploy/compose` is the Compose project folder and its `.env` is a link to `../../.env` | The monitoring overlay of M2-S08 mounts `../ops/...` relative to the Compose folder, so the `deploy/` layout of the repository must stay. Fixed paths mean a deploy does not recreate PostgreSQL only because the release folder changed, and bind mounts keep their folders (in-place copy). `cd /opt/mscd/deploy/compose && docker compose ps` works by hand |
| 3 | `--no-verify-signature` "skips cosign" | The server checks both signatures again with `cosign verify` (the runner's cosign copied to `/opt/mscd/bin/cosign`); `--no-verify-signature` is refused unless both images come from `127.0.0.1` | The brief's flag implies a cosign step in the script. Checking on the server too means a run by hand cannot start an unsigned image either |
| 4 | Verify `/healthz`, `/readyz` and the version through Caddy | `/healthz` and `/api/v1/system/profile` through Caddy; `/readyz` of api, worker and storage-gateway inside their containers | NGINX does not route `/readyz` to the api: through Caddy it answers 200 with the app page, which proves nothing. The profile request goes through Caddy, NGINX and the api |
| 5 | Rehearsal rc.3 (web image as server image) "so migrate fails", then the automatic restore | rc.3 is refused at the image check of step 7 (the web image has no release label, and its NGINX entrypoint also fails `--help` with "illegal option"), before anything changes. Added rc.4 (the rc.2 server image plus a migration that fails) and rc.5 (the rc.1 server image, also as web image, so the services are replaced and the health check fails) | The image check of step 6 of the brief stops rc.3 before migrate. rc.4 and rc.5 prove the automatic restore for both triggers of the brief |
| 6 | Secrets on standard input "and the mail variables as values" | Every value on standard input, one `NAME=<base64>` line each: the four secrets, the settings of `.env` and the backup and monitoring values; settings may also come from the environment (manual runs, `check-only`) | `SMTP_USER` is a secret in K.2, and a remote command line is visible in the process list. | 9 | Restart "with `--no-deps --wait`" | Plus `--force-recreate` for storage-gateway, api and worker, and for the overlay services | Secret files written again (for example `smtp.password`) are new inodes; a container keeps the old file until it is recreated. Monitoring services read their configuration files only at start |
| 10 | (not in the brief) | `--min-free-disk` (default 10240 MB) | The build host of this run had 2 GB free; the rehearsal passes 1024 |
| 11 | "A service does not become healthy" rolls back | Only the app services (data services, storage-gateway, api, worker, web, Caddy) and the checks of step 13 roll back. A monitoring or backup service that fails, or a Grafana host that Caddy refuses, ends the deploy with a WARN line and exit code 0 | M2-S08 asked for it (its handoff, follow-ups for M2-S05): a monitoring fault such as a missing `ALERT_EMAIL_TO` should not take a healthy release away. The run still shows the warning, and the fix is a deploy of the same version |

## Tests

### `saas-rehearsal.sh`

Runs as root (it uses `setpriv` to run each deploy as uid 61005 with the docker group, like the deploy account, and reads the secret files to check them). The images are built with the throwaway key set of `saas-keys.sh`, pushed to `registry:3.0.0` on `127.0.0.1:5000` and removed locally, so every deploy pulls by digest. Release folders are made with `saas_stage_release`, as the workflow makes them. With `MSCD_REHEARSAL_OVERLAYS=none` it also deploys rc.2 again with a stand-in `docker-compose.ops.yml` whose `ops-init` stops with code 3, an empty `TELEGRAM_BOT_TOKEN` (an old token file is in place) and an `OPS_DOMAIN`: the deploy must end healthy with a warning and no rollback, reload Caddy, note `overlay=problem` in `history.log`, remove the token file and add `grafana` to `COMPOSE_PROFILES`. Results: see Acceptance.

### `saas-rehearsal.sh --workflow`

A runner container and a server container of the pinned Ubuntu image of M2-S03 (`openssh-client`, `openssh-server`, `rsync` from the Ubuntu archive), sshd on port 2222, the deploy account with a `restrict` key, and a stand-in `docker` on the server that answers the host checks, records the registry login and refuses the pull. The run scripts of `deploy-prod.yml` are taken from the YAML with test inputs, secrets and variables, and run in order like GitHub runs them. 16 checks: a server with another host key is refused before any login; port 2222 works with the port-22 `known_hosts` lines through `HostKeyAlias`; one SSH login for the whole run and no terminal; rsync copies the release without demo files and with `digests.json` and the site; the job token reaches `docker login` on standard input and the server logs out; `saas-deploy.sh` gets 26 values on standard input, runs the copied cosign and pulls by digest; its output sits between `::stop-commands::<token>` and `::<token>::`, and the step reports its exit code; no secret value in the output or on a docker command line; the key and the work folder are gone from the runner.

The steps that need GitHub (checkout, release download, cosign on the runner, the check from outside) were checked by `check-workflows.mjs`, `bash -n` and shellcheck of every run script.
