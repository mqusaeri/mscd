# M2-S05 handoff: deploy script and deploy workflow

## What was built

| File | Content |
|---|---|
| `deploy/scripts/saas-deploy.sh` | The deploy script of a SaaS server, actions `deploy`, `rollback` and `check-only`. A run does not depend on its SSH connection: when the connection ends it carries on to its end and writes its whole log, and `state/history.log` records its start and its result. Sources `lib/common.sh` (unchanged, so `install.sh` and `upgrade.sh` behave as before) and the new `lib/saas.sh`. Options: `--target production\|staging\|test` (required for deploy and rollback), `--install-dir` (default `/opt/mscd`), `--release-dir` (default: the release of the script), `--digests`, `--version`, `--timeout`, `--verify-timeout`, `--min-free-disk`, `--skip-backup`, `--cosign`, `--no-verify-signature` (only for images of a registry on `127.0.0.1`). | `deploy/scripts/lib/saas.sh` | Helpers: the demo refusals, host checks, standard input, settings and `.env`, signatures and pulls, key files, the off-site backup and monitoring files, the installed files and the state, `saas_stage_release` (the file list of a release folder, shared by the workflow and the rehearsal) and `saas_encode_input` (standard input as the workflow builds it) |
| `.github/workflows/deploy-prod.yml` | `workflow_dispatch` with `version`, `action` (`deploy`, `rollback`), `target` (`staging`, `production`) and `skip_backup`; environment `${{ inputs.target }}`; job concurrency `deploy-${{ inputs.target }}` with `cancel-in-progress: false` (shared with `bootstrap-prod.yml`); permissions `contents: read`, `packages: read`. ### Deploy order on the server (`saas-deploy.sh deploy`)

1. Lock the install folder (`flock`), remove the work folders of runs that were stopped hard (with their key copies), and print the last line of `state/history.log`.
2. Refusals before any other check, also in `check-only`: image names ending in `-demo` (environment, `digests.json`, `.env` in place) "demo images are refused"; `demo.yaml` or `test.yaml` profiles and any `MSCD_DEMO*` setting (environment, `.env`, example) "demo and test profiles are refused"; `config/demo-secrets` or `docker-compose.demo.yml` in the release folder or the install folder "demo files are refused". Every refusal is reported, then the script stops.
3. Docker, memory (7.4 GB or more), free disk for Docker data (`--min-free-disk`, default 10 GB) and the install folder (1 GB), and the tools it uses.
4. `digests.json` of the release: version, image names, digests, refs. A version older than the running one is refused (rollback is the way back).
5. Standard input: all lines checked (known names, base64, no repeats, the four required secrets present).
6. The new `.env`: `.env.saas.example` of the release, then every setting from standard input, else the environment, else the `.env` in place, else the example; worked out by the deploy: the images and `MSCD_VERSION` (from `digests.json`), `MSCD_PUBLIC_URL`, `MSCD_EDGE_IPV6` (true when the server has a global IPv6 address), `COMPOSE_PROJECT_NAME`, `COMPOSE_FILE`, `MSCD_SECRETS_DIR`, `MSCD_METRICS_DIR` and `MSCD_SITE_DIR`. Checks: host names, placeholders of the example refused on staging and production, `MSCD_TLS_MODE=internal` only with `--target test`, ports, subnets inside `172.31.0.0/16`, the `saas.yaml` profile, `COMPOSE_PROFILES` with `bundled-db` and `bundled-s3` (`grafana` is added when `OPS_DOMAIN` is set), and no character that `.env` cannot carry literally. `docker compose config -q` with the release's Compose files.
7. Images: `cosign verify` of both digests (identity of `release.yml` at `v<version>`), pull by digest when missing, the server image must carry `com.cyberlentera.mscd.flavor=release` ("demo images are refused" for `demo`), then `--help` once. Images pulled for a refused release are removed again.
8. Database: PostgreSQL runs and is healthy, and the disk has room for a dump (a first deploy has no database and takes no dump). Then the line `<time> deploy started <version> from=<old>` in `state/history.log`.
9. Secrets: `platform.key`, `storage.key` and `audit-anchor.key` from standard input (written when missing; an existing file must hold the same key, compared without white space, read through a short-lived container as the file's owner when the deploy account cannot read it; any difference stops the run before anything is written); `audit-anchor.pub` derived with `openssl pkey -pubout` (the SPKI PEM of `keys generate`); then `ensure_database_secrets`, `ensure_key_secrets`, `ensure_certificates`, `set_smtp_password`, `fix_secret_owners`; then one file per backup and monitoring value in `secrets/backup` and `secrets/ops` (mode 0400, folders 0700); a value sent empty removes its file.
10. Pre-deploy `pg_dump --format=custom` of `mscd` into `/opt/mscd/backup/pre-deploy/<time>-<from>-to-<to>.dump` (mode 0600, checked for the `PGDMP` header and free space first, last 3 kept); `deploy/backup/backup.sh --pre-deploy <file> --install-dir <dir>` when the release has it.
11. When the `.env` in place names other digests than `state/current.env`, an earlier run was stopped hard while it switched the files: put back the copy of the current files that run saved (`state/saved/` or `state/rollback-undo-*`) and delete it. Then save the files in place to `state/saved/<time>-<version>` (the rollback point), install the `.env` first, then the release's `deploy/` tree and site; start PostgreSQL and SeaweedFS when they do not run yet (first deploy).
12. `docker compose run --rm --no-deps migrate` alone, time limit 600 s plus 20 s per `org_` schema, log in `/opt/mscd/logs/migrate-<version>-<time>.log`, printed back with `org_<slug>` and email addresses hidden.
13. `up -d --no-deps --wait` one service at a time: postgres and objectstore (recreated only when their settings changed), storage-gateway, api and worker (recreated every time), web, caddy (`--remove-orphans`; `caddy reload` when only its configuration files changed), then the services of the overlays (recreated every time; long-running ones healthy or running, one-shots such as `ops-init` waited for until they end with code 0), then `caddy reload` when `ops-init` ran, so Caddy reads the Grafana host it writes. A failure in this last part is a warning, recorded as `overlay=problem` in `history.log`; the healthy app is not rolled back.
14. `/readyz` of api, worker and storage-gateway inside their containers; `/healthz` and `/api/v1/system/profile` (version and `deploy: saas`) through Caddy with `--resolve <domain>:<port>:127.0.0.1`.
15. State: `state/current.env`, `state/previous.env`, the result line in `state/history.log`; the same release deployed again does not count as a rollback point; images of the last 3 releases kept (current and the 2 newest saved), release folders of the saved releases kept, logs pruned.

A failed step 11 to 14 puts the saved files back and starts the previous digests (pulled again when missing), then checks them the same way: after a failed migrate without recreating anything, after a failed service or check with the server services recreated. A first deploy that fails has nothing to go back to and says so.

`rollback` goes back to the newest saved release other than the running one (`--version` must name it, and `digests.json` of the release folder must name the same images when it is there), with the same refusals, signature check, pulls, database check, key check, a pre-rollback dump, the same repair, no migrate, the restart with the server services recreated and the checks. Its copy of the current files is `state/rollback-undo-<time>` (outside the work folder, so a repair finds it). A failed rollback returns to the release it started from.

`state/history.log` holds one line per event: `<time> <action> <result> <version> <details>`. Results: `started` (before the first change), `done`, `restored`, `failed`, `restore-failed`, `stopped` (written by the exit trap when a run ends after `started` without a result, with `exit=<code> phase=<phase>`), and `repair done` lines. While no run holds the lock, the `.env` in place names the digests of `state/current.env`: `lib/saas.sh` writes the `.env` first when it moves away from that release and last when it moves back, so a run stopped hard during a switch always leaves a `.env` that differs.

## Tests

### `saas-rehearsal.sh`

Runs as root (it uses `setpriv` to run each deploy as uid 61005 with the docker group, like the deploy account, and reads the secret files to check them). The images are built with the throwaway key set of `saas-keys.sh`, pushed to `registry:3.0.0` on `127.0.0.1:5000` and removed locally, so every deploy pulls by digest. Release folders are made with `saas_stage_release`, as the workflow makes them. With `MSCD_REHEARSAL_OVERLAYS=none` it also deploys rc.2 again with a stand-in `docker-compose.ops.yml` whose `ops-init` stops with code 3, an empty `TELEGRAM_BOT_TOKEN` (an old token file is in place) and an `OPS_DOMAIN`: the deploy must end healthy with a warning and no rollback, reload Caddy, note `overlay=problem` in `history.log`, remove the token file and add `grafana` to `COMPOSE_PROFILES`. Since fix round 1 it also checks: the deploy with a wrong `PLATFORM_KEY` says "Nothing was changed" and ends `history.log` with `deploy stopped ... phase=secrets`; the upgrade reports the database check before the secrets; before rc.4 it leaves the state of a deploy stopped hard right after the switch (the saved files of rc.2, the `.env` of rc.4 and a stray file in the deploy tree, a `started` line without a result, work folders with a key copy), and the rc.4 run must warn about it, put the files of rc.2 back before saving its own rollback point, remove the work folders, write `repair done` and keep only the rollback point of rc.1, then fail at migrate with the new database message and roll back; rc.5 runs with its output read by `head -n 12`, as when the SSH connection ends, and must still exit 1 after rolling back, with its whole log on the server and `deploy restored 1.1.0-rc.5 reason=health running=1.1.0-rc.2` as the last line of `history.log`. Results: see Acceptance.

### `saas-rehearsal.sh --workflow`

A runner container and a server container of the pinned Ubuntu image of M2-S03 (`openssh-client`, `openssh-server`, `rsync` from the Ubuntu archive), sshd on port 2222, the deploy account with a `restrict` key, and a stand-in `docker` on the server that answers the host checks, records the registry login and refuses the pull. The run scripts of `deploy-prod.yml` are taken from the YAML with test inputs, secrets and variables, and run in order like GitHub runs them. 20 checks: a server with another host key is refused before any login; port 2222 works with the port-22 `known_hosts` lines through `HostKeyAlias`; one SSH login for the whole run and no terminal; rsync copies the release without demo files and with `digests.json` and the site; the job token reaches `docker login` on standard input and the server logs out; `saas-deploy.sh` gets 26 values on standard input, runs the copied cosign and pulls by digest; its output sits between `::stop-commands::<token>` and `::<token>::`, and the step reports its exit code; no secret value in the output or on a docker command line; the key and the work folder are gone from the runner. A second run uses an older release whose `lib/saas.sh` does not take `MSCD_SITE_DOMAIN`: the deploy step leaves that name out with a notice, and the older `saas-deploy.sh` reads the other 25 values.

The steps that need GitHub (checkout, release download, cosign on the runner, the check from outside) were checked by `check-workflows.mjs`, `bash -n` and shellcheck of every run script.
