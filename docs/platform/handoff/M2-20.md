# M2-20 handoff: screen addresses

The product owner asked after the staging review: "when I refresh I always go back to the first screen". M2-20 gives every screen an address. The address names the screen, the selected management system, the organisation of a person who belongs to several and the tab of a host screen with tabs. A refresh opens the same place, Back and Forward move between screens, and a copied address opens the same place for another person who may see it. No screen shows or does anything else than before. The first screen of an API session now follows the landing of the role, as a persona switch lands; the product owner signed this off on 31 October 2026 (deviation 1).

## What was built

### Address format

| Part | Value | Present |
|---|---|---|
| Screen | The screen id (D2-14): one of the 14 built-in ids or a host screen id | Always |
| `ms` | Slug of the selected management system | When the person has a system in the organisation |
| `org` | Slug of the organisation | When the person belongs to several organisations |
| `tab` | Tab id of a host screen with tabs | When a tab was chosen, or the screen was opened with `params.tab` |
| `persona` | Sample persona other than the manager | Sample build only |

| Build | Form | Example |
|---|---|---|
| API (`VITE_DATA_SOURCE=api`) | Path and query | `/controls?ms=isms&org=ndt`, `/registers?ms=isms&org=ndt&tab=risks` |
| Sample | The path of `index.html` stays, the address is in the hash | `/?lang=id#/controls?ms=isms&org=ndt&persona=owner` |

The display settings of the address (`lang`, `theme`, `density`, `drill`, `layout`, `font`, `deploy`) stay as they are. The sample start query `?screen=<id>&persona=<role>` (C.2), which the E2E helpers use, still works: the app reads it once and replaces it with the hash form.

### Rules

- A change of screen or organisation adds a history entry; a change of system, tab or persona replaces the current one. The same place writes nothing.
- An address of an unknown screen, or of a screen the session cannot open (the sidebar rule: `visFor` for built-in screens, `canOpenHost` for host screens, the C.3 rules without a system), opens the start screen and the address is replaced. An unknown system, organisation or tab is ignored and the address corrected.
- The start screen is the landing of the role (`landing()`), in both builds, as a persona switch lands (deviation 1, signed off by the product owner on 31 October 2026): a Domain Owner opens My Tasks, an Internal Auditor of a single-system organisation Audit readiness, Management System Managers, Top Management and an Internal Auditor of several systems the portfolio (the overview with one system). The sample build opened this landing before M2-20 too (its start query of C.2). A person without a system gets the landing of C.3.
- An address that names another organisation of the person switches to it. At start the switch happens before the first snapshot (`firstLoad` passes the slug to `ds.load`), because `PUT /me/org` replaces the session id and a screen still loading with the old session would get a 401 and end the session (deviation 2). The first load runs once per instance, also when React StrictMode mounts the app twice in development, so no plain load runs next to that switch. When the organisation asks for a new sign-in (D-26), the boot router shows the sign-in page and returns to the same address afterwards; when the person presses Cancel there, the app keeps the old organisation and corrects the address. The slug of the switch under way is kept in the memory of the page (`src/routing/memory.ts`) so the app that the boot router opens again after Cancel, without loading the page, does not ask again in a loop. A new page (a typed or pasted address, a reload, a return from another site) starts without it, and a start address that names no organisation, or another one, forgets or replaces it, so a tried switch never outlives its sign-in page and nothing is left in the tab's storage. The organisation menu writes the new organisation's address (`/?org=<slug>`) before it switches, so a sign-in asked for by that switch also returns to the new organisation; a switch that fails goes back one history entry.
- The sign-in pages keep their addresses and stay with the boot router: the controller never reads or writes an address of `/login`, `/login/mfa`, `/login/enrol`, `/forgot-password`, `/reset-password`, `/invite` or `/guest`. An application address opened without a session already went to sign-in and back (`storeReturnTo` and `safeReturnTo` of `src/auth/routes.ts`: a relative path of the site only, never another host); with the address it now returns to the same screen, system, organisation and tab. `keptSearch` keeps `org` on the sign-in page, so `/registers?org=bsd` opens `/login?org=bsd` with that organisation's sign-in methods.
- The API build: NGINX (`deploy/nginx/site.conf`, `location /` with `try_files $uri $uri/ /index.html`) and `vite preview` already serve `index.html` for every path without a file extension. No screen id has a dot, and none is a sign-in path, `api`, `assets` or `healthz` (unit test). An application path with a folder part is written without it before anything renders (`main.jsx`, `tidyScreenPath`): the generated sidebar loads its logo with the relative path `assets/cyberlentera-logo.png`, which from `/controls/` would ask for `/controls/assets/...` and get a 404 from NGINX. `/controls/` becomes `/controls`; a deeper path (`/controls/x`) names no screen and becomes `/`, the start screen it would open anyway; the query and the fragment stay.
- The sample build never changes its path, so it works from any static file server without a fallback; a typed hash (or an anchor of the address bar) opens its place without loading the page again. A fragment that is no address (`#top`) is left alone.

### Code

- `apps/web/src/routing/` (new): `address.ts` (read and write an address in both forms, the history rule, `tidyScreenPath`; pure functions), `tab.ts` (`useScreenTab(ctx, ids, fallback)` and the tab access the controller adds to the host context), `memory.ts` (the tried organisation switch, in the memory of the page), `index.ts`.
- `apps/web/src/MscdApp.jsx` (navigation state only): the state `htab` (`{s: screen, id: tab}`), the start from the address (`startRoute`, `firstLoad` once per instance, `startOrg`, `afterFirstLoad`, `startScreen`), `applyRoute` and `openPlace` for the start and for Back and Forward (`onPop`, listening to `popstate`, and `hashchange` in the sample build), `syncAddress` in `componentDidUpdate`, `setHostTab`, and the tab rules in `go`, `setMs`, `setRole` and the organisation switch (`setOrg` and the shared `switchOrgTo`). `shownScreen` and `builtinOpen` hold the existing rules of `buildVals` (the portfolio of one system, a host screen the session may not open, the built-in entries of the role), which now calls them, so the address and the screen use one rule. The old sample start (`sampleStart`, `afterFirstLoad`) runs through the same code: the persona of the start address is applied when the source is created, as before.
- `apps/web/src/screens/host.tsx`: `createHostContext` adds `tab` and `setTab` (`withScreenTab`) when the controller offers `setHostTab`; `HostApp.state.htab` and `HostApp.setHostTab` are optional, so a hand-built app (tests) keeps working. `tabOfState` is exported.
- Tab state of the host screens: `findings` (`findings`, `actions`, `self`), `registers` (the register kind), `routing` (`rules`, `files`), `auditor-access` (`grants`, `packs`) use `useScreenTab`. A context without the tab access (the screen unit tests) keeps the tab in the component, as before. `ops` belongs to M2-19 and gets its tab from the patch below. The `Tabs` of the import result filter, the document panel and the organisation drawer of the operator console are not screen tabs and stay local.
- `apps/web/src/main.jsx`: the API build tidies an application path with a folder part before the boot router starts (`tidyScreenPath` leaves the sign-in paths to the boot router).
- `registry.ts` and `ui/host-context.ts` needed no change.

## Deviations

1. The first screen of an API session follows the landing of the role, as a persona switch lands, where it was the portfolio for every role before M2-20: a Domain Owner of several systems opens My Tasks, an Internal Auditor of a single-system organisation opens Audit readiness, Managers and Top Management open the Portfolio. The brief asks for no change to what any screen shows, so the first follow-up round had taken this back. **Signed off by the product owner on 31 October 2026**: keep it. The second follow-up round restored it (`startScreen()` in `MscdApp.jsx`).
2. The organisation of the start address is switched by the first load instead of after it (see Rules), so no old-organisation screen loads with the session the switch replaces. A switch by Back or Forward runs while the app is open, as the organisation menu does.
3. Only host screen tabs are in the address, as the brief says. The summary cards that filter the built-in lists (Controls, Chain stages, Evidence freshness, the Phase board stepper), the chips, the search and an open detail are not part of the place, and a refresh resets them as before.

## Follow-ups

- Back or Forward across an organisation switch, and the organisation menu, replace the session id (`PUT /me/org`) without waiting for the reads under way; a read of the old organisation that is still running at that moment answers 401 and the boot router shows "Your session has ended". This was already so for the menu; the address adds Back and Forward as a second way to switch. M2-20 does not fix it, because every fix lies outside its paths: an abort signal for the reads under way in `apps/web/src/data/api/ApiClient.ts` (M2-19 owns it; `request` already takes a `signal`) that `ApiDataSource.switchOrg` fires before `PUT /me/org`, or a short grace period for the previous session id on the server. Proposed as a small follow-up package after wave 7.
- The language, theme and density switches do not write the address; a link with `?lang=id` still opens in Indonesian after the person switched to English (as before M2-20).
- `docs/DEVELOPMENT.md` could name the address format for developers (this package owned only `docs/platform/ui-contract.md`, section 3.8).
