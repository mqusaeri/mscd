# M2-07 handoff: document control and register server additions

M2-07 builds the server side of the D.1 and D.2 changes marked M2-07: the applicability targets, freshness thresholds per system, the documented information list with pack code links, external documents and the change summary of a version, the version history of a document, holdings and handover, the register kinds `objectives` and `competence` with the competence reminder, the management review PATCH and the `APPL-ASSESS` rule. The read model loader gives clause entries of catalogue systems the key `cl-<code>`, passes stored readiness rows through with their nulls and four dimensions, and loads the certification cycles with their certificate for M2-05. The follow-ups that named M2-07 are closed: item 5 of M2-02 (`assertKindBuilt` is gone, `m2-pending/M2-07.json` is deleted), the clause entries of M2-01, the mapping sources of the M2-03 orchestrator note and follow-up 3 of M2-05 (document and metric commands queue `readiness.recompute` and `cycle.derive`).

## What was built

### Shared contract (`packages/shared/src/api`, schemas only)

| File | Content |
|---|---|
| `documents.ts` | `ExternalSource` (1 to 200 characters) and `ExternalRef` (1 to 120). `DocumentCreateRequest` takes `origin`, `externalSource`, `externalRef`, `receivedAt`: the three external facts only with `origin: 'external'`, and an external document needs `externalSource`. `DocumentPatch` takes `origin` and the three facts, each nullable. Examples cover both origins |

Examples of both kinds |

## Deviations

1. **Two files outside Owns, waiting for the orchestrator's approval (R-01).** `read-model/build/system.ts` uses `entryKey` and adds `documentOriginFields` to each document; `read-model-api/screens.ts` reads `readiness.get(clause)?.readiness`, since the loader now passes the stored row (one line, with a comment). Without them the server does not compile or the `cl-` keys never reach the snapshot. Follow-ups 1 and 2 of M2-05 change the same two files and go on top of these lines.
2. **Management review PATCH audits `register.updated`.** There is no `management_review.updated` action and R-14 does not let a package add audit actions.
3. **Competence code.** `competence_record` has no code column, so the code shown in holdings, tasks and audit entries is `CMP-` and the first 8 hex digits of the id, in upper case.
4. **BR-40 resolves the link at completion time** and does not store `output_document_id` on the activity. An activity whose output document is found only through `document_code_link` therefore gets no BR-47 warning (output document status that contradicts the activity); one whose document carries the pack code does. `implementation/activity.service.ts`, which stores the id and runs BR-47, is not in the Owns list; the change is a follow-up for the orchestrator.
5. **Retired rows.** Entries on retired rows are marked `retired` in the loader and in `applicability.targets?retired=true` (`hasEntry` true). The snapshot `Requirement` (`packages/shared/src/ui`, not owned) has no member for it yet, so the label "No longer in the standard" is not in the snapshot.
6. **Admin holdings** leave out systems where the person holds nothing.
7. **Lapse notification key.** `RecordRef` has no member for the lapse date and `notification` has no data column, so the competence lapse notification stores `validUntil` as an extra member of `entity_ref`. Every reader parses `entity_ref` with `RecordRef`, which drops the extra member, so the API and the email link are unchanged.
8. **Holding kinds.** `HOLDING_KINDS` stays as the brief lists it: drift results count as `task` (follow-up work with a holder and a due date) and management reviews as `register_row`.
