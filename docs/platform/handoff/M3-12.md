# M3-12 handoff: Hardening follow-ups

M3-12 closes seven open items that earlier packages left in `docs/platform/M2-STATUS.md` and `docs/platform/M3-STATUS.md` (M2-19 follow-up 8, M3-02, M3-06 and M2-21). The orchestrator added it to the free slot of wave 4 at the product owner's request on 2026-11-01. It changes no route, no permission and no screen layout; the two correction migrations are additive (R-14).

Audit terms in plain words: an audit trail anchor is a signed note of the newest audit entry and its hash; it proves later that nobody rewrote the trail before that entry. A retention period is how long a record is kept; the disposal register is the evidence of what was decided for each record when its period ended (ISO/IEC 27001 A.5.33, clause 7.5.3 of every standard).

### 3. One snapshot for the organisation export (M3-02)

| File | Change |
|---|---|
| `apps/server/src/modules/tenancy/tenant-scope.ts` | `withTenant(ctx, fn, options)`: `{ snapshot: true }` runs a REPEATABLE READ, READ ONLY transaction. Kysely sets both in the statement that starts the transaction (`start transaction isolation level repeatable read read only`), so they apply before `set_config`, and the first statement takes the snapshot. `idleTimeoutSeconds` (0 to 86400) sets `idle_in_transaction_session_timeout` for that transaction only. Callers without options keep READ COMMITTED with writes. Verification round 1: `holdSnapshot(fn, { idleTimeoutSeconds })` holds one snapshot for many short transactions. A REPEATABLE READ, READ ONLY transaction on a connection of its own runs `pg_export_snapshot()` and reads no table, so it holds no table lock; `withTenant(ctx, read, { snapshot: held })` imports it with `SET TRANSACTION SNAPSHOT` (before `set_config`). Each import first runs a statement in the holder, so the holder's idle limit applies between two reads. A table that was rewritten or emptied after the snapshot (TRUNCATE, an ALTER TABLE that rewrites it, VACUUM FULL) shows no rows to an older snapshot, so before such a transaction commits it compares, for every table it holds a lock on, the file `pg_class` names in the snapshot with the current one (`pg_relation_filenode`) and fails with `SnapshotTableRewrittenError` when they differ. A held snapshot cannot be imported after `holdSnapshot` ends |
| `apps/server/src/modules/org-export/builder.ts` | Every database read of a build (the plan with the file list and the migrations, every tenant table, the platform rows, the audit trail, the anchors and the list of external files) reads one held snapshot, so the export shows the organisation as it was at one instant: a record written while the build runs is in none of its files, and every reference between the files holds. Verification round 1: each dataset is read in a short transaction of its own that imports that snapshot, and its spools go into the archive after that transaction ends, as before M3-12. A table is locked only while it is read, so an upgrade migration that alters a table (`upgrade.sh` runs migrations while the old services keep running) waits for one table's read at most, never for the whole database part of an export, and the api's queries on that table do not queue behind it. The holder allows `SNAPSHOT_IDLE_SECONDS` (3600) between two reads, because closing a part in the worker includes its upload of up to 2 GiB. A table rewritten by a migration during the build fails the build instead of exporting it without rows. The Managed Vault content is streamed from the gateway after the snapshot is released (vault objects never change once written) |

### 6. Scratch files of a stopped export build (M3-02)

## Deviations

1. **Function name.** The brief names `platform.apply_tenant_grants`; the function that grants the tenant rights in this code base is `platform.secure_tenant_schema` (platform 0001, redefined in 0007), so 0009 redefines that one. The grant is applied only when the schema has its `kysely_migration` table.
2. **Where the installation's anchor keys come from.** No profile key was added: the checks read the `.pub` file beside `audit.anchor_key_file`, the file the installer, `restore.sh` and the SaaS deploy already keep, in the format of `mscd-server keys generate`. Retired keys stay trusted as further PEM blocks in that file (on-premise) or as `anchor-*.pub` files in the release's `MSCD_TRUSTED_KEYS_DIR` (SaaS, compiled in), as INSTALL 19.3 already asks for `export verify`.
3. **Idempotency for every principal without an organisation.** The scope applies to any signed-in principal without an organisation, which today means the platform operator in the console; a request without a principal still has no key.
4. **The snapshot holds one connection for the database part of a build.** The holder keeps PostgreSQL from removing row versions newer than its snapshot until the database part ends (exports are rare, one at a time per installation, and the vault files are streamed after it ends). A build uses two pool connections at a time for it (the holder and one short read), plus the build lock's. The holder's idle limit is 3600 seconds between two reads instead of 60. It holds no table lock (verification round 1), so it never makes a migration wait.
5. **A migration that rewrites a table during a build fails the build.** The old snapshot would show such a table without rows, so the build stops with `SnapshotTableRewrittenError` and the export can be requested again. The check also stops a build after a VACUUM FULL of a table it had not read yet, which would have been harmless; nothing in MSCD runs VACUUM FULL. An upgrade also restarts the worker, which stops a running build anyway.
6. **The drawer test calls components outside a renderer.** The web unit tests have no DOM (R-03 allows no new npm dependency such as jsdom), so the harness swaps React's internal hook dispatcher (`__SECRET_INTERNALS_DO_NOT_USE_OR_YOU_WILL_BE_FIRED`, with the React 19 name as a fallback) while it calls a component. It covers the hooks the findings screens use (state, refs, effects, memo, callback, context); a React upgrade that changes those internals breaks only this test file.
7. **The replay of an answer with a one-time link carries no link** (verification round 2). The finding offered a route flag in the contract; `packages/shared` is outside the Owns of M3-12 (and M3-10 edits it), so the list of members is a server table in the tenancy module, and the contract check in `idempotency.test.ts` keeps it complete. The replay answers with the result of the first request without the link and with a message that says how to get a new one; the console shows that message in place of the link. The audit entries already recorded only that a link was made.
