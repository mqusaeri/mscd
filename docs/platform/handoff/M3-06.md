# M3-06 handoff: Retention and disposal review

M3-06 builds D.8 of `docs/platform/MILESTONE-3.md`: each management system keeps a retention period per record type (36 months by default, H.8), a daily job opens a disposal review when a period ends, a Management System Manager keeps, extends or proposes the disposal of each record, a second person approves a disposal, which then runs at once, legal holds keep records whatever their period says, and the disposal register lists every decision as audit evidence. The eleven routes of `packages/shared/src/api/retention.ts` replace the M3-01 stubs, and the web app gains the host screen `retention` with five tabs and a retention panel in the details of documents and evidence.

Audit terms in plain words: a retention period is how long a record is kept; a disposal review is the check, when that period ends, of whether the record may now be destroyed; a legal hold keeps a record whatever its period says, for example during a dispute or an investigation. ISO/IEC 27001:2022 control A.5.33 (protection of records) and clause 7.5.3 of every standard ask the organisation to decide how long it keeps records and what happens to them afterwards; the disposal register is the evidence that it does.

## What was built

### Server (`apps/server/src/modules/retention/`)

| File | Content |
|---|---|
| `retention.controller.ts` | The eleven routes. `retention.register` answers a page, or with `format=csv` the whole register as a formula-safe CSV attachment with the F.13 headers, audited `file.downloaded` (entity type `retention_register`) |
| `retention.service.ts` | Rules: the value in force per class and, for earlier document versions, per document type of the pack lookup (`doc_type`, with its label in both languages), marked `default` (36 months) or `set`; set is an upsert, a null period a reset (soft delete); "Nothing to change" when equal; audited `retention_rule.changed`. Reviews: the list by status, class and record code, with the open reviews of held items left out (D.8). Decisions on several reviews at once, all or nothing: keep until a date after today (`kept`), extend by months from the current end, which must then lie after today (`extended`), or dispose (`awaiting_approval`), refused with `RET-HOLD` (a hold in force), `RET-CURRENT` (a document's current or unapproved version, an evidence item's current file), `RET-NOT-DUE` (the period under the rule in force today has not ended: a longer period set after the review opened moves the end, and the message names the date) and `records.open_dependants` (open corrective actions of a finding, open findings of an audit event, as `records.delete` refuses them); audited `retention_review.decided`; a disposal sends `disposal_approval_pending` to the system's other Management System Managers and Programme Owners. Approval: refused for the proposer with `SOD-SELF-APPROVE`, every dispose check again, then the disposal; audited `retention_review.approved`. Rejection: back to `open` with the note (`retention_review.rejected`). "File removed": records that the owner deleted the file in the customer's repository and closes the owner's task (`retention_review.file_removed`). Holds: list (in force first), create by item id or by the record's code, refused with 409 when the item is already held, release with a reason (`retention_hold.created`, `retention_hold.released`). Register: the period shown is the one in force at the decision (or, for a disposal, at the approval), which `retention_review.decided` and `retention_review.approved` record as `retainMonths` (deviation 8) |
| `retention-items.ts` | One query per record class, in two modes (the candidates of the daily review; given items whatever their state): code, title, home system (the record's own system, or the primary system of a shared record; a document without a link falls back to the first system, an evidence item without a link to its first target), document type, period start (null when the item does not qualify now), current flag, owner, and the storage objects a disposal acts on. Period starts as D.8: a superseded version from the approval of the version created after it; an earlier evidence file from `replaced_at` (its evidence item from the latest `evidence.file_uploaded` or `evidence.file_linked` entry that replaced it); the current file of a deleted evidence item from the deletion; an evidence pack from its build; an audit event with a result from its last day; closed findings and management reviews from their closing date; closed corrective actions from their verification date; competence records from `valid_until`, or their deletion when a proof file is left. Also the lookup by code for the hold form and the open dependants |
| `retention-disposal.ts` | What an approved disposal does, in the approval's transaction: vault content deleted with `gateway.objects.delete` (every stored version) and the object marked `content_disposed_at` and `content_disposed_by` (the row keeps its name, dates and hash, every open path answers 404 `content_disposed`); a file in a customer repository marked the same way (MSCD no longer opens or checks it) and its owner given a task (`manual` source, entity `retention_review`, due in 30 days) to delete it there; a record marked deleted with `writeRow` of `registers/command-support.ts`; audited `record.disposed`. A vault version that a bucket retention rule still protects makes the gateway answer `forbidden`: the approval is refused with 409 `retention.kept_by_bucket_rule`, which names the date, and may be repeated then. The vault delete is idempotent, so a disposal whose transaction fails after the delete can be approved again. An item with several vault objects (an evidence pack) deletes them one after the other: when a later delete fails, the approval rolls back, and the objects whose content is already gone are marked disposed in a transaction of their own (`markContentDeleted`, audited `record.disposed` with `completed` false and the failure's message key), so they answer 404 `content_disposed` while the review waits; the next approval deletes the rest and lists the earlier objects as `earlierVaultObjects` |
| `retention-review.service.ts`, `retention-review.job.ts` | The daily `retention.review` (03:15 local, run ledger, on its run date): the `replaced_at` backfill of older replacements from the evidence file audit entries (the time of the first entry that replaced each file; idempotent, so every run may do it), then a review in `open` for every item whose period ended, unless it is held, waits for a decision or approval, was disposed of, or a "keep until" date or an extended end lies ahead; then the digest `retention_review_due` to each system's Management System Managers |
| `retention-model.ts`, `retention.module.ts`, `README.md` | Default period, class names, month arithmetic (a month later than 31 January is the last day of February, as PostgreSQL computes it), the module wiring (imports `StorageModule` and `JobsModule`) |

`apps/server/src/modules/files/file-commands.service.ts` (D.2): the file that a new evidence file replaces gets `replaced_at`, in `evidenceFile` (submit and relink) and in `fileGeneratedEvidence` (which now locks the evidence row first); an object that is still another live item's current file is not marked.

`packages/shared/src/api/retention.ts` (schemas only, deviations 1 to 3): `docTypeLabel` on rule items, the `code` filter of the review list, and `itemCode` as an alternative to `itemId` in the hold body.

## Deviations

1. **`docTypeLabel` on rule items.** The Rules tab and the document panel need the name of each document type (the pack lookup `doc_type`); the item now carries it as a pair (null for the other classes).
2. **`code` filter of `retention.reviews.list`.** The document and evidence panels ask for the reviews of one record: items whose code is the record's code or starts with it and a space (`ISP-001 v1.0`, `EV-0313 v2`).
3. **Holds by code.** A hold is often needed before a record is due, when no review lists it, and the screens know records by their codes. The hold body takes `itemCode` instead of `itemId` (exactly one of them): `NC-2025-01`, `ISP-001 v1.0` for a document version, `EV-0313 v2` for an evidence file, `PACK-` or `CMP-` and the first eight characters of the id for packs and competence records, an audit event's short label (409 when several events of the system share it). The record must belong to the system of the path.
4. **An item that was kept or extended opens again as a new review.** J.8 lists "`kept` or `extended` to `open`: system on the new date". The job opens a new review on that date instead and the earlier review stays `kept` or `extended`, so the disposal register keeps every decision as D.8 asks; the audit trail has every step either way.
5. **A rejection keeps the proposal on the review.** The review returns to `open` with `decision` null and the note; the proposer, date and reason stay until the next decision, so Due for review can say why it came back.
6. **The owner is asked through a task.** J.4 has no notification kind for "delete this file in your repository", and R-14 allows no new enum value, so the owner of the record (document owner, evidence owner, pack requester, competence record owner) gets a stored task (`source_rule` `manual`, entity `retention_review`) in My Tasks; "File removed" closes it, and so may "Mark done". An owner who is no longer a member leaves it unassigned.
7. **A disposed file in a customer repository is marked disposed in MSCD too.** MSCD does not delete it there, but sets `content_disposed_at` on its object, so MSCD stops opening it and the link check stops checking it (no "missing" alarm when the owner deletes it).
8. **The register's period comes from the audit entry of the decision.** `retention_review` has no column for the period at decision time (J.7). Each `retention_review.decided` entry records `retainMonths`, the period in force at that decision, and each `retention_review.approved` entry the period in force when the disposal ran (the one `RET-NOT-DUE` checked); the register and its CSV show the latest of them, so a later rule change does not rewrite the evidence. A review decided before this entry existed falls back to the period in force today. The proper place is a column (Needs from the orchestrator, 1).
9. **Bucket retention.** A vault version that a bucket retention rule still protects refuses the approval with 409 `retention.kept_by_bucket_rule` and its date (M3-01 follow-up): nothing is disposed until the bucket allows it.
10. **Audit events: attached files are not disposed with the event.** D.8 says attached files of an audit event "follow the file rows above": its report document's versions and evidence files are items of their own classes and get their own reviews; the event's disposal marks the event deleted only.
11. **Competence records.** A lapsed record is marked deleted at disposal and the content of its proof file goes with it (vault deleted, or the owner asked). A record that was already marked deleted is due only while its proof file is left, and its disposal acts on that file. The review's title is the role only, never the person's name.
12. **The API E2E cannot open the decision form.** The API stack runs no worker, so no review exists there until the M3-10 seed writes one ("retention rules with one due review", section E). The decision form, the approval confirmation, the reject dialog and "File removed" are therefore not opened in the API build, so `expectOverlayReadable` does not run on them there (C.2, R-22); the sample spec opens each of them in both themes, and the server tests cover the routes, as the evidence pack spec of M2-15 does for ready packs.
