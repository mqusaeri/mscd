# M2-05 handoff: certification, internal audit and readiness server

M2-05 builds the certification lifecycle of D.4 (cycles, the certificate record, the manual cycle moves, `certificate.expiry` and the new derivation kinds of `cycle.derive`), the internal audit behaviour of D.1 and D.2 (internal audit events with scope and report, auditor and target of audit activities with the `AUD-INDEP` warning, the programme coverage view, finding target codes) and the clause readiness of D.6 (`readiness.recompute`, its queueing and schedule, the overview and card fields that read the stored dimensions, the seed). The five route stubs of M2-02 are replaced and `m2-pending/M2-05.json` is deleted.

## What was built

### Routes

| Route | Service | Behaviour |
|---|---|---|
| `ms.cycles.list` | `management-systems/certification.service.ts` | Cycles of the system newest first, with dates, certificate number, issue and expiry dates, issuing body, certified scope, the audit events of each cycle, its item counts (total and done) and its `etag` for `ms.cycles.transition`. Each event carries `scopeText` and `reportDocumentId` (D.2). The report's code and title are not returned, because the scope policy decides who sees that document: the client finds it among the documents of the snapshot. The ETag is a plain field: a nested `RecordRef` on a GET route counts as a record of someone for the owner-scope sweep of J.5, and a cycle has no owner |
| `ms.cycles.create` | same | Starts a cycle (`cycleEnd` defaults to the same day three years later): activates the `planned` cycle of the system with the dates of the request, or inserts a new `active` cycle; 409 `conflict` (`certification.cycle_open`) while a cycle is active (the unique index `certification_cycle_open_uq` is the backstop); 409 for an archived system; copies the cycle items and links the events without a cycle; audits `certification_cycle.created` |
| `ms.certification` | same | Needs status `implementing` (first certificate) or `certified` (recertification), else 409 `transition-not-allowed`; an `active` cycle, else 409 `conflict` (`certification.no_active_cycle`); a `stage2` or `recertification` event of that cycle with outcome `recommended` or `recommended_with_conditions`, else 422 `business-rule` (`certification.no_recommendation`, both languages). Sets the cycle to `certified` with number, issue date, expiry date, issuing body and scope (default: the system's scope statement), the system to `certified` and its certification body to the issuing body, closes the previous certified cycle (audited `certification_cycle.closed`), refreshes the certificate label and audits `ms.certified` |
| `ms.cycles.transition` | same | Only the rows of J.8 whose `via` is this route: `certified` to `suspended`, `suspended` to `certified` or `withdrawn`, `active` to `closed`; any other move 409 `transition-not-allowed`; the reason is required by the schema (400); `If-Match` with the cycle's ETag (`etag` of `ms.cycles.list`, or `ref.etag` of the last command result) is optional as everywhere in D.1, and a stale one answers 412 `precondition-failed` (R-18); a reinstatement while a newer certificate is in force 409 (`certification.newer_certificate`); 404 for a cycle of another system; audits `certification_cycle.transitioned` with the reason; the system status does not change |
| `internal-audit.programme` | `audit-registers/internal-audit.service.ts` | For the cycle asked for (404 when it is not a cycle of the system), else the open cycle, else the newest: every clause row of groups 4 to 10 of the edition and every applicable control (a live entry not marked not applicable), each with the `internal_audit` events of the cycle (linked to it, or unlinked and dated within it) whose activities covered it and the number of those activities; `covered` is false and `audits` empty for the others. An activity covers its `targetCode` (else its template `clause_ref`), the sub-clauses of a clause it names and the parent clauses of a sub-clause it names; cancelled activities and retired rows do not count |

### Changed behaviour of existing routes (D.2)

| Route | Change |
|---|---|
| `audit-events.create` | `scopeText` and `reportDocumentId` (schema in `packages/shared/src/api/audit-events.ts`, also on the patch). The first `stage1` or `recertification` event of a system without an open cycle starts one, from the earlier of today and the event date, for three years; the first `stage1` event of a system with a `planned` cycle activates it and keeps its dates. The result names the cycle (`message`, `data.cycle`). An internal audit with a report queues `cycle.derive` |
| `audit-events.update` | The interim checks of M2-02 stay: without `audit_event.manage` the caller changes internal audits only and never their event type (403). Takes `scopeText` and `reportDocumentId` (null removes it); a change of the event type into the first opening event starts the cycle as on create |
| Report document | A live document of the system (its own, shared, or organisation-wide) of type `record`: 404 for an unknown document, 422 (`audit.report_not_record`) for another type |
| `audit-activities.generate`, `audit-activities.update` | The interim event type checks stay. `auditorHandle` (a member, `none` clears it) is stored in `auditor_user_id`, `targetCode` (a clause or control code of the edition, null clears it) in `target_code`; an unknown code answers 422 `audit.unknown_target`, a code no longer in the standard 422 `audit.target_retired`. When the auditor or the target changes and both are set, `AUD-INDEP` (a `@BusinessRule` warning provider in `internal-audit.rules.ts`) warns when the auditor owns an entry of the target (or of its sub-clauses), a document that implements one, or evidence linked to one |
| `audit-activities.list` | Items carry `auditor` and `targetCode`; Top Management sees the auditor only when it sees the auditee (or is the auditor) |
| `findings.create`, `findings.update`, `findings.list` | `targetCode` checked as above and stored in `finding.target_code`; `findings.list` filters by it; items carry it; the audit entries name it |
| Finding and corrective action commands | Queue `readiness.recompute` and `cycle.derive` for the system (finding insert, update, transition; corrective action create, update, transition) |

### Jobs and schedules

| Item | Content |
|---|---|
| `readiness.recompute` (`implementation/readiness/`) | `ReadinessService` per system (or every system that is not archived), D.6: `implemented` share of entries implemented or not applicable (requirement entries by `clause_group`, catalogue entries by the clause group of their item's requirement, else 8); `documented` share of the edition's `ref.documented_info` rows in place (to maintain: an approved document of the system not past its review date, found as the documented information list of M2-07 finds it: by template code, by `document_code_link` of the template or row code, or among the implementing documents of the requirement entry of the clause or its sub-clauses; to retain: a fresh evidence item of such an entry); `evidenced` share of the group's evidence items that are fresh; `measured` (group 9 only) share of the system's metrics with a value whose period ended within one period of today (period of the metric's frequency, 365 days without one); readiness the rounded mean of the dimensions that have rows, null when none has. Retired rows and entries are left out. `manual` rows are never written; the others are written as `computed` with `computed_at` |
| Queueing (`readiness-queue.ts`) | `enqueueReadiness` (`rr:<org>:<ms>`, 60 seconds, the key `applicability.sync` and `admin.ms.create` use) and `enqueueDerived` (with `cycle.derive`, `cd:<org>:<ms>`, 60 seconds). The three command helpers (`implementation/command-support.ts`, `registers/command-support.ts`, `risk-registers/support.ts`) call `enqueueDerived` inside `enqueueFreshness`, so every caller of `freshness.recompute` queues both |
| `certificate.expiry` (`management-systems/certification.expiry.ts`, handler `notifications/certificate-expiry.job.ts`) | Daily: a certified cycle whose certificate expires within 90, 30 or 7 days gives one `certificate_expiring` notice per tier to each active MS Manager and Programme Owner of the system (a run that missed days sends the tier the date now falls in, once; idempotent by title, recipient and cycle); a certified cycle past its expiry date moves to `expired`, audited `certification_cycle.expired` (actor system), and the label shows "Certificate expired" |
| `cycle.derive` | New kinds: `corrective_actions_closed` (one corrective action verified and closed within the cycle, none open), `metrics_current` (every metric of the system current, as `measured`), `documents_reviewed_on_time` (approved documents, none expired or past review), `bia_approved` (business impact analyses, all approved and not past review), `due_diligence_current` (`months`, default 12: completed or expired records, all completed and valid today, or performed within the window when they name no end). `internal_audit_done` also counts an `internal_audit` event of the cycle with its report. The job skips demo organisations |
| `jobs/schedules.ts` | `readiness.recompute` at 02:30 local for every system (`rr:<org>:all`), `certificate.expiry` at 06:00 local (`ce:<org>:<date>`) |

## Deviations

1. **Files outside the Owns list.**
   - `apps/server/test/int/jobs/scheduler.test.ts` lists the local times of `DAILY_JOBS`; the two schedule entries of this package add 02:30 and 06:00 to that list (one line). The hours the test dispatches (00, 01, 03) are unchanged, which is why `certificate.expiry` runs at 06:00.
   - Two new files of the internal audit sub-module: `apps/server/src/modules/audit-registers/internal-audit.service.ts` (the `internal-audit.programme` coverage and the auditor and target checks of audit activities and findings) and `apps/server/src/modules/audit-registers/internal-audit.rules.ts` (the `AUD-INDEP` warning provider). The Owns list names the controller and the module of the sub-module; D.3 registers its services there, so the service and the rule provider are new files next to them. No other package touches them.
2. **The certificate label is stored as well as derived.** D.4 says the label comes from the newest certified cycle. `read-model/build/system.ts`, which calls `deriveManagementSystem`, has no owner in this wave, so the certification commands and `certificate.expiry` keep `display.certLabel` in step with that cycle (the G.4 stored display value the read model already shows). `deriveManagementSystem` derives the same label from the cycles once the glue passes them (follow-up 1).
3. **Cycle dates.** A cycle opened by an event starts on the earlier of today and the event date, so internal audits held before Stage 1 belong to it. Recording the certificate does not move the cycle dates; the label takes its years from the certificate's issue and expiry dates.
4. **Activation of a planned cycle.** Only a `stage1` event activates a `planned` cycle (D.4); a `recertification` event while a planned cycle exists starts nothing.
5. **Cycle items.** Owner the primary MS Manager; due the day before the next audit event of the cycle after today (never before today), else at the cycle end. `applicability.sync` (M2-03) uses the event date itself.
6. **`internal_audit_done`** counts an internal audit with its report or, as in Milestone 1, a finding of source `internal_audit` raised within the cycle, so the Milestone 1 behaviour stays.
7. **`cycle.derive` skips demo organisations** (`demo_deploy_label` set), as `applicability.sync` does, so the demo keeps matching the sample when the packs carry derivations (G.9). The test organisation `tst` has no label and is derived.
8. **Event links keep the event version.** Linking the events without a cycle to a new cycle does not change their `updated_at`, so the ETags clients hold stay valid.
9. **The certification body of the system** follows the issuing body of the newest certificate (audited in `ms.certified`).
10. **A card without a stored label** shows "Not yet certified" (was `-`).

## Follow-ups

1. **Orchestrator (no owner in wave 2a): `read-model/build/system.ts`.** Pass `cycles: system.cycles, today` to `deriveManagementSystem` in `systemFields` (the M2-07 loader already loads the cycles). The card then shows a certificate past its expiry date as expired before the daily job runs.
2. **Orchestrator or M2-07: `read-model-api/screens.ts`.** `implementationSummary` still computes every maturity row with the Milestone 1 formula over `readiness ?? 0`. Replacing the map body with `clauseMaturity(clause, d.system.readiness.get(clause), open[clause] ?? 0)` (from `derive/overview.ts`) shows the stored dimensions of computed rows, null for rows not computed yet, and the Milestone 1 values for the demo.
3. **M2-07 files: document and metric commands.** `registers/documents.service.ts` (document transitions, approval) and the metric value command in `risk-registers/registers.service.ts` do not call `enqueueFreshness`, so they do not queue `readiness.recompute` and `cycle.derive`. Calling `enqueueDerived` of `implementation/readiness/readiness-queue.ts` there makes `documented`, `measured`, `documents_reviewed_on_time` and `metrics_current` move within a minute; until then the daily 02:30 and 03:15 runs pick the changes up.
4. **Orchestrator, before the wave commit: the two M2-04 patches.** With the E.2 content of M2-04 (derivations and review inputs in the packs), five tests of `test/int/audit-registers/management-reviews.test.ts` (Milestone 1, no owner in wave 2a) have new expected values: the demo template now has derivations (the `tst` organisation is derived), and the ISMS and QMS editions define review inputs. `m2-04-management-reviews-test.patch` updates them (R-15: the expected values change with the content step). `m2-04-outside-owns.patch` carries M2-04's prep-template fallback in `apps/server/src/seed/org-writer.ts`, a file of this package that this package leaves to that patch, and M2-04's seed and management system test values. Both patches apply cleanly to the current tree (`git apply --check`, this round). After applying them, rerun acceptance lines 2 and 4.
5. **M2-06: `admin.ms.create`** writes seven `computed` rows with readiness 0 and then queues `readiness.recompute`, which replaces them within a minute. Writing no rows (or null rows) shows "Not computed yet" in that minute.
6. **Module READMEs** (`management-systems/README.md`, `audit-registers/README.md`, `implementation/README.md`) are not in the Owns list and do not describe the new parts yet.
7. **M2-15** builds the certification timeline on `ms.cycles.list`, `ms.cycles.create`, `ms.certification` and `ms.cycles.transition`, and the internal audit screens on `internal-audit.programme`; the messages of the commands are in both languages. The certificate panel sends `If-Match` with the cycle's `etag` from `ms.cycles.list` (or `ref.etag` of the last command result) and shows the conflict message on 412.
8. **M2-14 (event drawer) and M2-07 (snapshot loader): scope text and report of an internal audit.** `ms.cycles.list` returns them on each event of a cycle (`scopeText`, `reportDocumentId`; the drawer takes the report's code and title from the snapshot documents, which the scope policy filters). The audit events of the snapshot (`UiMsSnapshot`, loader of M2-07) and the audits of `internal-audit.programme` do not carry them. The drawer can read them from `ms.cycles.list`, or M2-07 adds `scope_text` and `report_document_id` to the loader's audit events so the snapshot shows them; the report link then follows the scope policy of the snapshot's documents.
