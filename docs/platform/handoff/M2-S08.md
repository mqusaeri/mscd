# M2-S08 handoff: monitoring and alerts

## What was built

| File | Content |
|---|---|
| `deploy/compose/docker-compose.ops.yml` | The monitoring overlay. Services `ops-init` (one-shot), `prometheus`, `alertmanager`, `node-exporter`, `postgres-exporter`, `blackbox-exporter` and `grafana` (profile `grafana`), each pinned by version and index digest, with a memory limit (768M, 128M, 64M, 64M, 64M, 384M; `ops-init` 128M; about 1.5 GB together with Grafana), `read_only`, `cap_drop: [ALL]`, `no-new-privileges`, `init`, the `local` log driver (20 MB times 10) and no published port. Networks: Prometheus, node-exporter and postgres-exporter on `mscd` only; Alertmanager and the blackbox exporter on `mscd` and `egress`; Grafana on `mscd` and `ops-web`. Caddy stays off `mscd`: the overlay adds it only to `ops-web` (new, `internal: true`, Docker picks the range, Caddy and Grafana only) and mounts the `ops_caddy` volume at `/etc/caddy-ops`. node-exporter leaves out the container's own mounts (`/etc/hostname`, `/etc/hosts`, `/etc/resolv.conf`, `/textfile`). Volumes: `prometheus_data`, `alertmanager_data`, `grafana_data`, and the volumes `ops-init` writes: `ops_state` (the `mscd_monitor` password), `ops_prometheus` (probe target), `ops_alertmanager` (configuration and its secret files), `ops_caddy` (Grafana site), one per reader |
| `deploy/ops/ops-init.sh` | POSIX shell, run by `ops-init` as root with only `CHOWN`, `DAC_OVERRIDE` and `FOWNER`, every start, idempotent. Checks every setting first (host names, https addresses, port, email list, Telegram token and chat id together, bcrypt hash, one line, no control characters) and stops with a clear message before writing anything. Then: (1) role `mscd_monitor` (`LOGIN`, member of `pg_monitor`, no other rights, `CONNECTION LIMIT 5`, `default_transaction_read_only = on`, `statement_timeout = 15s`), its random password made once and kept in `ops_state` (owner 65534, 0400), passed to `psql` in the environment and quoted by `format(%L)`; (2) `probe-targets.yml` (file service discovery) from `MSCD_PUBLIC_URL` or `MSCD_OPS_PROBE_URL`; (3) `alertmanager.yml` rendered from the template, with `smtp.password`, the Telegram token and the heartbeat address copied to separate files only Alertmanager reads (owner 65534, 0400); (4) `grafana.caddy` when `OPS_DOMAIN` and `OPS_BASIC_AUTH_HASH` are set, removed otherwise. Never prints the alert address, the heartbeat address or a secret. `--render-only` skips the database and owners (tests) |
| `deploy/ops/prometheus/prometheus.yml` | Scrape every 30 s, rules every 30 s, retention 30 days and 8 GB (the `storage.tsdb.retention` block of Prometheus 3; the flags are deprecated). Jobs `prometheus`, `alertmanager`, `api`, `worker`, `storage-gateway` (port 9464), `node`, `postgres`, `blackbox`, and `public-url` (blackbox probe, module `https_healthz`, targets from `/etc/prometheus/rendered/probe-targets.yml`). Every target carries the label `service`, the Compose service behind it (`node-exporter`, `postgres-exporter`, `blackbox-exporter` for `blackbox` and `public-url`, otherwise the job name). The MSCD processes label job runs `job`, which Prometheus moves to `exported_job`; a metric relabelling renames it to `job_name`. Caddy is not scraped (fix round 1, finding 6) |
| `deploy/ops/prometheus/rules/*.yml` | 19 alert rules in 8 files, each with `severity`, a plain `summary` and an `action` that names the section of `docs/saas/monitoring.md`: services (TargetDown 2m, PublicUrlDown 2m, DatabaseDown 2m, HttpErrorRateHigh over 2 percent 5xx for 10m, AlertDeliveryFailing), audit and licences (AuditChainBroken, LicenceExpiringSoon under 30 days), jobs (JobFailuresRising 3 in 30m, counting the first failure that creates a series; JobQueueStuck over 55 minutes for 5m, deviation 9; JobOutboxStuck over 0), security (MfaLockSpike 3 in 15m, AccessDeniedSpike over 50 in 10m counting the first refusal that creates a series, `category: security`), host (HostDiskFull over 80 percent, HostMemoryPressure under 10 percent available or memory stall over 20 percent, HostRebootNeeded after 7 days per the M2-S03 follow-up), certificates (CertificateExpiringSoon under 14 days), backups (BackupTooOld over 26 h, BackupMissing for 26 h), Watchdog (always). The api and the worker both publish the collected metrics, so the rules take `max`/`min` per chain, organisation or queue |
| `deploy/ops/prometheus/tests/alerts.test.yml` | Promtool unit tests for every rule (31 test groups): when it must stay quiet, when it fires, the exact labels and text. The labelled counters first appear at their first event (value 1, after `_` samples), as the server creates them; a restart, a gap in the scrapes and the scheduler's lead time of daily jobs have their own tests |
| `deploy/ops/alertmanager/alertmanager.yml.tmpl` | The template: global SMTP (`smtp_auth_password_file`, `smtp_require_tls`, `smtp_hello` = domain), routes (Watchdog to `heartbeat` with group interval 30 s and repeat 1 m; critical repeats every 1 h, the rest every 4 h; group by `alertname`), receiver `owner` (email with subject `[MSCD <domain>] Alert: <name>`, and `telegram_configs` with `bot_token_file` when set up), receiver `heartbeat` (`webhook_configs` with `url_file` when set up, otherwise sends nothing), and one inhibit rule: AlertDeliveryFailing with `integration="email"` mutes the Watchdog, so the heartbeat stops while alert emails fail. Lines `#@smtp-auth:`, `#@telegram:` and `#@heartbeat:` are kept only when the part is set up |
| `deploy/ops/alertmanager/alertmanager.yml.example` | The template rendered by `ops-init` with the example values (email, login, Telegram, heartbeat). `test-ops.sh` fails when it differs from a fresh render |
| `deploy/ops/alertmanager/templates/mscd.tmpl` | Email (HTML at 16 px with dark-on-light colours of 7:1 contrast or more, and text) and Telegram message (plain text): title, per alert the name, severity, summary, first step and start time in UTC |
| `deploy/ops/blackbox/blackbox.yml` | Module `https_healthz`: GET, only 200, TLS required and verified against the image's public CAs, no redirects, IPv4 |
| `deploy/ops/grafana/**` | Provisioned Prometheus data source (uid `prometheus`), dashboard provider (folder MSCD, no changes from the browser), an empty alerting folder (Grafana sends no alerts), and the dashboard "MSCD overview" (`dashboards/mscd-overview.json`: stat tiles for targets, public address, certificate days, backup age, firing alerts; time series for requests, 5xx share, p95 latency, queue age, job failures, licence days, refused requests, lockouts, processor, memory, disks, database) |
| `deploy/compose/config/caddy/conf.d/ops.caddy` | (1) No metrics site any more (fix round 1, finding 6: Caddy is off `mscd`, so Prometheus could not reach it); (2) snippet `mscd_ops_grafana <user> <hash>`: `import mscd_tls`, `import mscd_log`, HSTS without `includeSubDomains`, `nosniff`, no `Server`, `basic_auth`, `reverse_proxy grafana:3000` with `X-WEBAUTH-USER {http.auth.user.id}` set by Caddy and `Authorization` removed, and `handle_errors` with the same headers; (3) `import /etc/caddy-ops/*.caddy` (no match without the overlay, which Caddy accepts) |
