# M3-13 handoff: Erasure, disposal and restore fixes

M3-13 fixes the findings of the three read-only reviews of Milestone 3 (security, ISO lead auditor and UU PDP, screen texts) that touch the erasure of a person, the disposal of records, the organisation export and the restore, and builds product owner decision 18 (a disposal really deletes a record's content). The brief is in `docs/platform/MILESTONE-3.md`, section M3-13; the ids below (security 1, ISO M3 and so on) are the ids of the review reports.

Audit terms in plain words: an erasure removes a person's personal data from an organisation and leaves a pseudonym ("Former user 7F3A") in the records, which stay as audit evidence; an attestation is the audit entry that records which entries were redacted and why, so the audit trail stays verifiable; a disposal destroys a record after its retention period ended; a legal hold keeps a record whatever its period says.

### Erasure receipts in the worker and the command line

- `apps/server/src/modules/ops/deletion/erasure-receipts.ts` (new): the api cannot read the audit anchor key, so the worker signs each unsigned receipt with the anchor key (as it signs a deletion certificate) and emails it, attached, to every platform operator and every active Tenant Admin of the organisation (template `erasure_receipt` in `identity/mail-templates.ts`, both languages). A receipt is signed once and marked sent when at least one recipient got it (or the organisation has none); when every send fails it is tried again in the next run; a failed send never fails the job. One run at a time works the receipts of an organisation: a run holds a session advisory lock per organisation (class 7005, key `hashtext` of the organisation id, on one pinned connection) from the selection of the receipts until they are marked sent, and a run that finds it held counts the organisation as `busy` and sends nothing, so overlapping runs never email a receipt twice; the lock ends with the connection if the worker dies, and the receipts it had not marked sent go out in the next run. When it runs, in single and multi tenancy:
  - the erasure queues an `org.lifecycle` run in its transaction (`privacy-erasure.service.ts`, singleton key `erasure-receipt:<request id>`); the handler of that job runs the receipt step first in both modes (`org-lifecycle.job.ts`), so the receipt goes out within minutes. Single tenancy (on-premise) has no hourly schedule of `org.lifecycle` (`worker-runtime.ts` leaves it out), so without this run no receipt would ever be sent there;
  - the daily `privacy.deadlines` run of each organisation runs the step for that organisation (`privacy-deadlines.job.ts`, both modes): the retry of a failed send on-premise. `PrivacyModule` imports `DeletionModule` for `ErasureReceiptSender`;
  - in multi tenancy the hourly `org.lifecycle` schedule runs it as well.
- `apps/server/src/cli/tenant.ts`: `tenant erasure --reapply <receipt> --confirm <slug> [--json]` checks the signature against the trusted anchor keys (the release's and the installation's `audit-anchor.pub`) and that the receipt names the organisation id of the slug, then `PrivacyErasureService.reapply`. Outcomes: erased again (exit 0, "is erased again"), already erased (exit 0, skipped), open items (exit 1, the count per system: hand them over, then run it again), the last active Tenant Admin (exit 1), the account missing (exit 1), and for a person without an account a restored copy older than the request (exit 2, the request number for the Tenant Admins to record and erase again). `tenant erasure --print-receipts <slug>` prints every signed receipt of the organisation, one receipt file per line (the text of the email attachment), oldest first, and a summary on stderr that names each request and any receipt the worker has not signed yet: the way to keep the receipts when email does not work (email is optional on-premise) or a receipt email was lost. `restore-test.sh --local` now takes its receipt from this command instead of SQL.
- `deploy/backup/restore.sh --reapply-erasures <folder>`: step 7c runs the command for each `*.json` receipt after the services start (beside `--reapply-deletions`), with the installation's public anchor key mounted, and reports erased, skipped and to-record-again counts. `restore-test.sh --local` gains step 8 (below).

## Deviations

1. The receipt is signed by the worker, not in the erasure's transaction: the api has no anchor key (the deletion certificate is signed by the worker for the same reason). The erasure writes the receipt into `privacy_request.erasure_receipt` and queues an `org.lifecycle` run, which signs and emails it within minutes; the daily `privacy.deadlines` run (both modes) and the hourly `org.lifecycle` schedule (multi tenancy) try again after a failed send. The four receipt columns on `privacy_request` are not named in the brief.
2. `tenant erasure --reapply` has three outcomes beyond the brief: the restored person is the last active Tenant Admin (refused, exit 1), the account does not exist in the restored database (refused, exit 1), and exit code 2 for a request the restored copy does not hold, which `restore.sh` reports as "record again". A member whose request the restored copy does not hold is still erased with the receipt (the `erased_person` row then has no request id).
3. `apps/server/test/unit/cli/program.test.ts` lists the new `tenant erasure` command; the file is not in the Owns list but tests only the command files this package owns.
4. `apps/web/test/screens/ops-accounts.test.tsx`: `roleTenantAdmin` joins the texts that may be equal in both languages, because A4 makes the Indonesian "Tenant Admin".
5. The disposal register keeps the file action `none` ("No file") when the only file of a disposed item was kept because another record uses it (`record.disposed` lists it under `keptInUse`). See follow-up 1.
