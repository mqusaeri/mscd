# M2-19 handoff: operator accounts

The platform operator now helps people with their accounts from the operator console. The Accounts tab lists every account of the service with search, filters and paging; "Manage" opens a drawer with the account's facts, memberships, open sessions and recent activity, and the actions: reset the second factor, send a password link, send an invitation again, end all sessions, disable or enable. Each action names the account, lists what happens and asks for a reason. Below the list, the platform operators with "Add operator" and "Remove". The form that asked for an email address to reset the second factor is gone. A refusal without a message pair (such as `mail_required`, which the product owner saw as the single word "Conflict" on staging) now shows the server's sentence.

## What was built

### Routes (`packages/shared/src/api/ops.ts`, owner M2-19, both tenancy modes)

| Route | Permission | Body and answer |
|---|---|---|
| `GET /ops/accounts` (`ops.accounts.list`) | `ops.read` | Query `q` (name, email or handle), `org`, `status`, `kind`, `page`, `pageSize`. Page of `OpsAccountItem`: id, handle, email, display name, kind, status, `mfaEnrolled`, `locked` (password or second-factor lock in force), `lastSignInAt`, `createdAt`, `platformOperator`, `memberships` (org slug and name, membership status, admin roles) and `etag` (weak ETag of the account row) |
| `GET /ops/accounts/{id}` (`ops.accounts.get`) | `ops.read` | `OpsAccountDetail`: the row, `sessions` (open ones, at most 50, latest active first: start, last seen, method, state, network cut to /24 or /48 in SQL, browser and system from the user agent, current organisation) and `audit` (the latest 20 platform audit entries whose entity is the account, its membership or one of its invitations: time, action, actor kind and actor, organisation, and the reason of operator entries only). 404 for an unknown account |
| `POST /ops/accounts/{id}/reset-mfa` (`ops.accounts.reset-mfa`) | `ops.users.manage` | `{reason}` (3 to 500). `OpsAccountActionResult`. 403 `own_account` for the operator's own account (the reset ends every session; the person replaces their own authenticator on My account); 409 `no_second_factor`, `system_account`. The reset does not wait for mail: the security email `mfa_reset` is sent after the commit, and `emailed` and the message say whether it went out ("tell the person yourself" when it did not). Audited `auth.mfa_reset` |
| `POST /ops/accounts/{id}/password-reset` (`ops.accounts.password-reset`) | `ops.users.manage` | `{reason}`. A token of kind `reset` (30 minutes of F.4, older unused ones end), emailed with `password_reset`. 409 `guest_account`, `account_not_active`, `no_membership`, `local_login_not_allowed`, `system_account`, `mail_required`. The link is in the answer only when mail is not required and the email did not go out. Audited `auth.password_reset` with `step: link_sent` |
| `POST /ops/accounts/{id}/invitations/{org}/resend` (`ops.accounts.invitation-resend`) | `ops.users.manage` | `{reason}`. For an `invited` membership: unused invitations of the membership revoked, a new one (72 hours) emailed. 404 `unknown_organisation` or `membership_not_found`; 409 `membership_not_invited`, `account_disabled`, `organization_archived`, `mail_required`. Audited `user.invited` (organisation of the membership, entity the invitation, `resent: true`) |
| `POST /ops/accounts/{id}/sessions/revoke` (`ops.accounts.sessions-revoke`) | `ops.users.manage` | `{reason}`. Every open session ends (reason `operator_revoked`). 403 `own_account`, 409 `system_account`. Audited `auth.session_revoked` |
| `POST /ops/accounts/{id}/status` (`ops.accounts.status`) | `ops.users.manage` | `{status: active or disabled, reason}`, optional `If-Match` (412). `disabled` ends every session (`user_disabled`); `active` checks the user limit of each organisation where the account is an active member (422 `LIC-USERS`). 403 `own_account`; 409 `status_unchanged`, `account_invited` (an invited account is neither enabled nor disabled: it becomes active when the person accepts, and can be disabled after that, as a Tenant Admin disables an invited membership only after it is accepted), `last_operator`, `system_account`. A disable locks the active operator accounts before its target, the order of the operator removal. Audited `user.updated` |
| `GET /ops/operators` (`ops.operators.list`) | `ops.read` | `OpsOperatorItem[]`: the accounts with an active `platform_operator` role, second factor, `passwordSet`, last sign-in, granted at and by, `self` |
| `POST /ops/operators` (`ops.operators.add`) | `ops.users.manage` | `{email, name, reason}`, 201, idempotent. The steps of `admin create-operator` with the operator as actor and `granted_by`. 409 `system_account`, `account_disabled`, `already_operator`, `mail_required`; 503 without the database owner role. Audited `ops.operator_created` |
| `DELETE /ops/operators/{id}` (`ops.operators.remove`) | `ops.users.manage` | `{reason}` in the body. The role and every session end (`roles_changed`). 403 `own_account`, 409 `last_operator`, 404 `not_operator` when the account holds no active role, 503 without the database owner role. Audited `ops.operator_revoked` |

The action routes are marked idempotent in the contract and the console sends an `Idempotency-Key`, but the key has no effect for a platform operator without an organisation, which is the normal SaaS operator and the operator of every M2-19 integration test: the shared interceptor (`apps/server/src/common/api-route.interceptor.ts`, `idempotencyScope`) keys the store by organisation and returns no scope without one, so a double submit or a network retry runs the action again (a second email or link). `ops.organizations.create` has the same gap; see follow-up 8. The rule refusals of these routes (403, 404, 409) carry a message key and the message in English and Indonesian, the 404 answers included (`unknown_account`, `unknown_organisation`, `membership_not_found`, `not_operator`), and the 422 of the user limit carries the licence rule's own key and message pair. Two answers carry neither: the 412 of a stale `If-Match` (`PreconditionFailedError`; the console shows its own text, "changed meanwhile") and the 503 of adding or removing an operator without the database owner role (`DependencyUnavailableError` from `withOwner`; the console shows the server's detail through `problemText`). A request that fails the shared schema answers 400 as every other route does. `POST /ops/users/reset-mfa` stays unchanged for `saas-ops.sh`.

### Problem text (`apps/web/src/data/api/ApiClient.ts`)

`problemText` decides the text of a problem: its message pair; without one, its `detail`; the title only when the problem carries neither. The English slot is the detail; the Indonesian slot is "Pesan dari server: " and the detail, because the detail is English. `detail` stays on the error. `untranslated(message)` tells a text without its own Indonesian. Unit test in `apps/web/test/auth/api-client.test.ts`.

## Deviations

1. **Files outside the Owns list.** Adding route ids makes three shared contract checks fail unless their tables know the routes, and the acceptance runs them: the ten rows of J.1 in `docs/platform/MILESTONE-2.md` (owner M2-19), the J.1 count 38 to 48 in `packages/shared/test/routes.test.ts`, and the ten lines of `apps/server/test/int/contract/__snapshots__/routes.test.ts.snap`. Nothing else in those files changed.
2. **No new audit actions.** `AUDIT_ACTIONS` (`packages/shared/src/enums.ts`, J.5) is not in the Owns list, so the routes reuse existing actions: `auth.password_reset` with `step: link_sent` for the password link (the completed reset keeps its own entry), `user.invited` with `resent: true`, `auth.session_revoked`, `user.updated`, `ops.operator_created` and `ops.operator_revoked`. Every entry carries `by: platform_operator` and the reason.
3. **Session revoke reason.** `operator_revoked` is written by `revokeAllSessions` in the ops module, because the reason union of `SessionService.revokeUserSessions` (identity module) does not list it. The other actions use `revokeUserSessions` with its reasons (`mfa_reset`, `user_disabled`, `roles_changed`).
4. **Adding an operator repeats `adminCreateOperator`.** The command writes its audit entry without an actor and without a reason, and `src/cli/admin.ts` is not in the Owns list, so `OperatorsService.add` has the same steps with the operator as actor and `granted_by`. Same rules, token kind, validity and email templates.
5. **Both tenancy modes.** The plan does not limit the account routes to SaaS. An on-premise installation has a platform operator too, so the routes work in single tenancy; only the organisation filter of the screen hides there.
6. **Statuses of the refusals.** The operator's own account answers 403 `forbidden` (`own_account`), as the Tenant Admin's own-account refusals do; the other rule refusals answer 409 `conflict` with their message key; enabling an account over a user limit answers 422 `LIC-USERS` (D-15).
7. **Password link validity.** The link is the F.4 reset link (30 minutes, template `password_reset`), because it replaces a password that exists. The 72-hour set-password link stays for new operators.
8. **Other screens and the problem text.** Screens that add the detail after a title-only message (`errorText` of users, storage-admin, registers, handover, identity-providers, approvals) now show the detail sentence alone for a problem with a detail and no message pair, where they showed "Title: detail" before. No file of those screens changed.
9. **Index.** The removal of `apps/web/src/screens/ops/Accounts.tsx` is staged in the git index (a `git rm --cached` during the work); the working tree has the same removal.
10. **Sweep data file.** `apps/server/test/int/rbac/expectations/M2-19.ts` (new) holds the RBAC sweep entries of the ten routes, the per-package pattern of G.1. It makes the M2-02 acceptance check that counts the sweep data files print 15 where `docs/platform/MILESTONE-2.md` expects 14 (follow-up 9).
11. **Invited accounts and the status action.** The status route refuses an invited account in both directions (409 `account_invited`). An invited account that could be disabled and then enabled would become active without an accepted invitation, with no password and an invited membership. The refusal follows the Tenant Admin rule for an invited membership ("It can be disabled after that"); the screen does not offer Disable for an invited account and says why.

Scope platform keys by user (for example `organisation_id` null or a platform sentinel in the idempotency store) and add a replay test for these routes.
9. **For the orchestrator: the M2-02 count.** Update the M2-02 acceptance in `docs/platform/MILESTONE-2.md` (`test "$(ls apps/server/test/int/security/record-tables/M2-*.ts apps/server/test/int/rbac/expectations/M2-*.ts | wc -l)" -eq 14`) to 15, or make it a minimum, when the wave is committed.
