# M2-15 handoff: certification timeline and auditor workspace

M2-15 builds three web folders on the screen host of M2-01: `timeline-edit` (the forms of the built-in Certification timeline: audit events, results, activities, preparation tasks, cycle items, the certification cycle and its certificate), `auditor-access` (the screen "Auditor access" with guest auditor grants and evidence packs, and the override of "Auditor access" on Audit readiness) and `audit-trail` (the screen "Audit trail"). No server code, shared contract, generated view or shared web file changed; `e2e/api-only/guest.spec.js` was updated for the new grant form (deviation 4).

Audit terms in plain words, as the screens use them: a certification cycle covers about three years. It starts with the Stage 1 audit (is the management system ready?) and the Stage 2 audit (does it work?), after which the certification body issues the certificate; a surveillance audit follows each year and the recertification audit renews the certificate. The certification body can suspend a certificate (it stays on hold until the body lifts the suspension) and then reinstate or withdraw it (a withdrawn certificate ends). Preparation tasks get the team ready for the next audit; cycle items are what the auditor checks across the cycle. Guest access lets the certification body's auditor read the audited system for a few days without an account of the organisation. An evidence pack is the set of evidence files copied for an audit, with a manifest that lists each file, its version and its hash. The audit trail records every change with who made it and when; each entry carries a fingerprint of the one before it (a hash chain) and the chain head is signed regularly (an anchor), so a changed or removed entry shows up when the chain is verified.

### Certification timeline forms (`apps/web/src/screens/timeline-edit/`)

An extension package without a screen of its own (C.5): claims, page actions, detail extensions and a layer item of the built-in screen `timeline`.

### Sample builds

Each sample adapter keeps its state per organisation and is loaded through a dynamic import (R-13). The timeline adapter changes the sample snapshot through `mutate` and `insert` of the sample data source (events, preparation tasks, cycle items), so the built-in timeline shows every change; it keeps the certification cycles (as the demo seed writes them: certified from the "Certified <date>, cycle <year> to <year>" label with the seed's expiry rule, else planned for 2026 to 2029), the event types, results and lead auditors, and the activities from the ISO/IEC 27001 Stage 1 and Stage 2 templates of the pack. It applies one active cycle, the certificate after a recommended result, the moves of J.8 with a reason and the cycle's ETag (412 on a stale one, 409 on a move J.8 does not allow, as the server answers), BR-42 and BR-43. The auditor access adapter starts the ISMS with the grant of its certification body's lead auditor and a revoked one, grants and revokes against the sample date, and has one ready evidence pack per system with a CSV manifest made in the browser. The audit trail adapter makes a trail from the snapshot (controls implemented, documents approved, evidence linked, the audit event, reminders, a nightly job, sign-ins), with a CSV and anchors made in the browser.

## Deviations

1. **The claims keep their Milestone 1 toasts in the sample build.** `e2e/timeline.spec.js` ("Add audit event from the empty lane and the page action" clicks the lane, then the page action, each time expecting the toast), `e2e/audit.spec.js` and `e2e/shell.spec.js` pin the toasts of "Add audit event" and "Auditor access" (R-15). A form opened by the first click would cover the page action of the second, so the sample build keeps the toasts, as M2-09 and M2-11 do; there the grant form opens from the Auditor access screen and the other timeline forms from the event panel, while "Add audit event" opens its form in API builds only. In API builds both claims open their forms; the orchestrator applied the matching patch of `e2e/timeline.spec.js` ("Needs from the orchestrator" item 2).
2. **The page actions of the timeline show in API builds only.** `e2e/shell.spec.js` counts the page actions of each built-in screen in the sample build (M2-08 deviation 1). The sample build reaches both from the certification cycle panel of an audit event, which every build shows: "Start certification cycle" while no cycle of the system is active and the shown cycle is planned, certified, withdrawn, closed or expired (not while its certificate is suspended), and "Record certificate" for an active cycle. The page action of API builds follows the same rule for the newest cycle of the system (`cycleMayStart` in `model.ts`), so it is hidden while that certificate is suspended. After a withdrawal the sample build starts the next cycle from the panel, and the audits after its start date then show that cycle. A system without any audit event has no panel (deviation 6), so in the sample build its cycle starts only once an event exists; in API builds the page action covers it.
3. **Path `/ms/:ms/audit/auditor-access`.** The plan writes `/ms/:ms/audit/access`; the registry of M2-01 requires the path to end with the screen id (D2-14), as M2-12 deviation 1.
4. **`e2e/api-only/guest.spec.js` changed.** It answered the browser prompt that this package replaces with the grant form, so it now fills the form. The journey and its checks are unchanged; the plan lists it in this package's acceptance.
5. **Action and person filters work on the loaded entries.** `audit-trail.list` takes the system, the entity and a date range only (its query is strict, R-14), so the screen filters the entries it has loaded by action and person, says so, and loads older pages with "Load more" (follow-up 1).
6. **The certificate panel sits in the audit event's panel.** The timeline has no slot of its own for the cycle; the detail extension of `event` shows the cycle of the selected audit. A system without any audit event has no event panel, so in API builds its cycle starts from the page action "Start certification cycle" or with its first Stage 1 audit (follow-up 2).
7. **"Start certification cycle" shows while no cycle is active.** A planned cycle counts as open in D.4, but `ms.cycles.create` starts it (M2-05), which is how a seeded planned cycle with its Stage 1 event already in place becomes active. The form says when it starts the planned cycle.
8. **"Record result" waits for the audit date.** A result is recorded after the audit; for an audit in the future the panel says so. Moving the date with Edit is the way to record an audit held earlier than planned.
9. **Reassign of preparation tasks and cycle items uses their own routes.** `prep-tasks.update` and `cycle-items.update` take the holder and the due date with `If-Match` and check BR-43, so the forms use them rather than `records.assign`. "Reassign or change due date" is for the MS Manager; a holder with the own grant marks the item done.
10. **The preparation window of an event other than the next one is not known.** No route returns it (the event detail has none, the next event carries it), so Edit shows it for the next audit and otherwise leaves the field empty with "Left empty, the current window stays".
11. **The audit trail is an `ms` screen with both permissions in `perm`.** The host checks `perm` in the screen's scope only, so a session opens it with `audit_trail.read` in the system; the organisation view is offered inside to a session that also holds `audit_trail.metadata.read` (rina). A Tenant Admin without a business role does not reach it (follow-up 3).
12. **"Record withdrawal" is offered for a suspended cycle only.** The brief lists it for a certified or suspended cycle, but J.8, D.1 and the rows of `ms.cycles.transition` in `packages/shared/src/machines.ts` allow certified to suspended, suspended to certified or withdrawn, and active to closed; the server refuses any other move with 409 (`apps/server/test/int/certification/cycles.test.ts`). A certified cycle therefore offers "Record suspension", and the withdrawal is recorded once the certificate is suspended (follow-up 6). The sample adapter follows the same rule.
