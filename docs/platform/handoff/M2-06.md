# M2-06 handoff: onboarding, accounts and operator server

M2-06 builds the server side of onboarding a new customer: the organisation settings and the onboarding checklist of the Tenant Admin, the account routes of every signed-in user (pending memberships, decline, security overview, new recovery codes, read-all), the invitation of an existing active account, the operator routes of multi tenancy (organisation list and create, factor reset), the seeding of applicability entries when a system is created, the daily jobs after a time zone change, the operator commands of the CLI, the slug confirmation of `install.sh` and the optional admin Job of the Helm chart. It writes the platform tables only in platform scope (M2-02 follow-up 9).

## Deviations

1. **`sign_in` is done when someone signed in through an enabled provider.** The connection test of `admin.idp.test` stores no result, so the step uses `user_identity.last_login_at` of a linked identity as the proof that the provider works. Without one it stays `optional` with the count of enabled providers.
2. **`local_login` is done once an administrator set the policy.** A policy other than `allowed`, or any `org.settings_updated` entry, marks it done; setting it back to `allowed` keeps it done. The default needs no action, so the step is `optional`.
3. **`repository` counts the Managed Vault of a new organisation** when the installation enables `managed_vault`; another repository counts once a connection check recorded it (`last_checked_at`) and its status is `ok`. A fresh organisation therefore starts with this step done.
4. **The email to an existing active account links to the app root.** The account accepts or declines in the app after signing in; a deep link waits for the URL routing of D2-14.
5. **`ops.users.reset-mfa` repeats the steps of `MfaService.resetFactor`** in `ops/operator-accounts.service.ts`, because that method has no reason parameter and the identity service is not owned here. The two must stay alike (see the follow-ups).
6. **`admin revoke-operator` ends every session of the account** with reason `roles_changed`, the reason of a role change in `SessionRevokeReason`; its memberships stay.
7. **`preset` is checked, not applied.** `ops.organizations.create` refuses a preset that `license.plans` does not name; the entitlement row is M2-S09 (D.2).
8. **Recovery code refusals are 422 `business-rule`,** with the message keys of enrolment, because a 401 would end the session in the web app; the route lists 409, 422 and 429.
9. **`RecoveryCodesService` takes `TenantScope` and `Clock` as optional,** like `IdentityInfra`, so an application without `TenancyModule` (the HTTP unit tests) still starts.

## Follow-ups

1. **Orchestrator: `apps/server/src/modules/identity/auth.service.ts` (WP-11).** `resetPassword` (`POST /auth/password/reset`) selects the token with `.where('kind', '=', 'reset')`, so the `set_password` link of `admin create-operator` cannot be redeemed yet. Changing it to `.where('kind', 'in', ['reset', 'set_password'])` (and the doc comment) lets a new operator open the link, choose a password and enrol TOTP at the first sign-in. The patch was handed to the orchestrator with the final report.
2. **Orchestrator: `apps/server/test/int/admin-users/admin-users.test.ts` (WP-39).** Its 202 test expects no email for an existing active account; D.2 changes that. The new expectation: the account gets one email of kind `account:membership_invited` without an `/invite#token=` link, the member and the disabled account get none. A patched copy passed (14 tests); the patch was handed to the orchestrator.
3. **Orchestrator: `apps/server/test/unit/cli/program.test.ts`.** `admin` now has `create-user`, `create-operator` and `revoke-operator`; the expected list of `sub('admin')` changes to these three.
4. **M2-S03 or M2-S04 (SaaS Compose): the api needs `db-migrator.url`.** `ops.organizations.create` runs `TenantProvisioner` as the database owner. The `api` service of `deploy/compose/docker-compose.yml` mounts no `db-migrator.url`, so the route answers 503 there until the SaaS overlay gives it to the api (on-premise single tenancy does not use the route).
5. **Identity owner: `MfaService.resetFactor` with a reason,** so `ops.users.reset-mfa` can call it instead of repeating its steps (deviation 5).
6. **M2-01, M2-12, M2-16 (web):** the Settings screen on `admin.organization.get` and the PATCH fields, the checklist on `admin.onboarding` (`screen`, `doneBy`, `assignee`), the pending memberships of `Me` with accept and decline, the security page on `me.security` and `me.recovery-codes`, read-all, and the operator console on the three ops routes.
7. **`admin.idp.test` could store its result** (time and outcome), so `sign_in` can be done before anyone signs in (deviation 1).
