# M2-21 handoff: faster browser tests

The product owner asked on 31 October 2026 for much shorter browser suites, with the machine at or below 12 GB of memory in use. M2-21 runs the API suite on parallel lanes, resets a lane's database only when something wrote, keeps the template database and the builds in a cache, replaces every fixed wait with a wait on a condition, splits the long screen walks, sizes lanes and workers from a memory budget, adds one command for both suites and runs each suite as shards in CI. Every test still runs and checks what it checked; both suites have more tests than before.

## Second round (31 October): findings of the verification

The verification found one blocker (the warm API suite above 5 minutes, the plan's line at the time; deviation 1), one major (no automated test of the write tracker) and three minors. What changed:

- **Blocker, warm API suite time.** Profiling the full suite step by step (a reporter that sums every Playwright step by call site, and the CPU of each process kind) showed where the time went and led to these changes:
  - `pageLoaded` and `pageSettled` (`helpers.js`) waited for the page's requests with `expect.poll`, which checks again after 100, 250, 500 and 1000 ms; they now wait for the end of the last request itself (`requestsDone`, which listens for `requestfinished` and `requestfailed`).
  - `openApp` and `switchMs` wait in the page, at every animation frame, until the title is shown or the switch shows the system (`shownSoon`, `textSoon`), then make the same assertion as before. A web-first assertion checks again only after 100, 350, 850 and 1850 ms, so a start of 400 ms was seen at 850 ms. The wait runs as a plain page script, so it installs no Playwright helper script in the page, and it never fails on its own: the assertion after it decides, as before.
  - `expectNoTextOverflow` and `contrastProblems` finish the animations inside their own page script: one round trip per check instead of two.
  - The reset of the lane starts before the browser context and its page are created (the `laneReset` fixture), and the api resets the mock providers while it puts the database back. A reset without a write deletes the minted sessions over an administrator connection it keeps open between such resets.
  - The api and the reset reach PostgreSQL over its Unix socket, and the api, the gateway and the tests reach SeaweedFS and Mailpit on the containers' own addresses: Docker's port proxy carried every query (375 microseconds per query against 105 over the socket, measured on this host) and used about 4 % of the CPU. Where the host cannot reach a container that way (Docker Desktop), the stack falls back to the published ports; `E2E_STACK_DIRECT=off` forces them.
  - Both web servers serve the files of `assets/` from memory with the headers NGINX gives them in production (gzip, a year for hashed names, `tools/scripts/e2e-assets.mjs`), instead of reading and compressing every file again on every request.
  - Both suites run Chromium with `--disable-gpu`: on `display.spec.js` the browser used 11 % less CPU (711 against 798 CPU seconds) for the same pictures.
  - The stack starts its containers at once, looks up their addresses at once, checks and copies the template cache in one helper container and creates the lane databases in one psql call: a warm start of the stack takes 9 to 10 seconds (14 to 17 before).
  - Tried and dropped: pausing the app's endless animations (the browser's CPU hardly changed), V8 tiering flags, 8 lanes instead of 6 (366 s against 375 s: the host is saturated at 6 lanes), a larger PostgreSQL buffer cache.
  - Three specs that failed in parallel runs are fixed without changing what they check (deviation 11).
  The warm API suite still took more than 5 minutes on this host (6.1 and 6.4 min); the plan then moved the line for this host to 7 minutes (deviation 1).
- **Major, test of the write tracker.** The tests belong in `apps/server/test`, outside the paths of M2-21, so they are written and checked but not added to the repository: `/var/tmp/m2-21/proposed/apps/server/test/unit/test-support/write-tracker.test.ts` (11 tests: `isWriteRequest` for every method, the test routes and the writing GET routes; the audit writer and job queue wrappers; `resetDone`; the minted sessions; `MSCD_TEST_RESET_ALWAYS`; nothing wrapped without the test endpoints) and `/var/tmp/m2-21/proposed/apps/server/test/int/test-support/reset-tracking.test.ts` (4 tests against a real database: the first reset recreates; a reset without a write deletes only the minted sessions and leaves a row changed directly in the database; a request through the api and an audit entry each make the next reset recreate). Both pass, with the typecheck and the lint, in a copy of the repository at HEAD with the files of M2-21 (`/var/tmp/m2-21/tree`). The orchestrator copies them into `apps/server/test/`. The test-support README now says that the existing test `a reset restores a changed row` depends on the first-reset rule.
- **Minor, template key.** The key of the template database now includes the key of the server build (every server source, Markdown notes left out), so a change to code the seed runs (the password hasher, the credential sealing, the data keys) builds the template again, in about 16 seconds. `docs/DEVELOPMENT.md` says so and how to remove the older cache volumes.
- **Minor, Mailpit clear.** The fixture clears the lane's Mailpit after the reset has answered, as before M2-21; the session is minted at the same time, since minting sends no mail.
- **Minor, wording.** The two sentences of this note that the writing rules of the project guide forbid are rewritten (deviations 1 and 7).

## What was built

### API suite on lanes (`apps/web/e2e-api/stack.mjs`, `web-server.mjs`, `fixtures.js`)

- The stack runs `E2E_API_LANES` lanes (default: what the memory budget allows, at most 6). Each lane has its own database `mscd_e2e_<lane>` cloned from the template, api (3174 + lane), storage gateway (4311 + 10 x lane, bucket `mscd-vault-<lane>`), mock providers (4310 + 10 x lane) with their DNS responder (UDP 4312 + 10 x lane) and Mailpit. Lane 0 keeps the ports of R-05.
- The lanes share one PostgreSQL container, one SeaweedFS container and one API web build, which `e2e-api/web-server.mjs` serves for every lane from one process (`vite preview` per lane, web port 4174 + lane, `/api` to the lane's api). The api of a lane has its web address as `http.public_url`, so each lane is one origin for cookies and the Origin check.
- The mock providers of every lane read one fixtures file: the demo fixtures with the storage consent callback of every lane's web address added to the Google OAuth client.
- `playwright.api.config.js` runs one worker per lane, fully parallel. `e2e-api/fixtures.js` maps a worker to the lane of its parallel index (`TEST_PARALLEL_INDEX`) and refuses a worker without a lane. `stackState()` answers the addresses of the worker's lane; the `baseURL` fixture of `e2e/helpers.js` is the lane's web address, so pages, `page.request`, `request` and new contexts all reach the lane.
- Every container has a memory limit (PostgreSQL 1.5 GB, SeaweedFS 512 MB, Mailpit 128 MB, helper containers 256 MB). The stack logs the peak memory in use when it stops.
- The host reaches PostgreSQL over its Unix socket (the container's socket folder is shared with the host) and SeaweedFS and Mailpit on the containers' own addresses; where it cannot (Docker Desktop), the published ports on 127.0.0.1 (second round; `E2E_STACK_DIRECT=off` forces them). `web-server.mjs` serves the build's `assets/` from memory with the headers NGINX gives them in production (`tools/scripts/e2e-assets.mjs`, also used by the sample suite's server).
- Leftovers: containers and run volumes of a killed run are removed only once their `mscd.test.expires` label has passed and their name has the run's prefix (the open follow-up of `CLAUDE.md`). Cache volumes have no expiry label and are never removed by a run.

### Reset only when something changed (`apps/server/src/modules/test-support/`)

- `write-tracker.ts` (new): a write is a request other than GET, HEAD or OPTIONS (the test routes excepted), a GET of a sign-in start or callback or of the storage consent callback, an audit entry (downloads, exports and file opens are GET requests that write one), or a job run in the api process. The first reset after start always recreates the database.
- `POST /test/reset` recreates the database only after a write. Otherwise it deletes the sessions `POST /test/session` minted since the last reset (`deleteSessions` in `database-reset.ts`, over an administrator connection kept open between such resets) and answers at once. The mock providers are reset every time, while the database is put back, and the caches after it. `MSCD_TEST_RESET_ALWAYS=1` (the stack's `E2E_STACK_RESET=always`) recreates at every reset.
- The clone uses `CREATE DATABASE ... STRATEGY FILE_COPY` on PostgreSQL 15 and later.
- `test-mode.ts` holds `testEndpointsEnabled`; the request gate shows each request that passes it to the tracker. Without `demo.enabled` and `test.endpoints_enabled` nothing is installed or wrapped, as before; the release flavour still refuses every `test.*` key.
- Measured on 6 lanes resetting at once: 90 ms without a write, 390 ms with one (the old reset recreated every time, about 400 ms on one lane).

### Fast test database

The test PostgreSQL runs with `fsync`, `synchronous_commit` and `full_page_writes` off, and also `jit` and `autovacuum` off, `max_connections` 400, `max_wal_size` 4 GB and `checkpoint_timeout` 30 min. These settings exist only in `stack.mjs`; `deploy/` and the integration test containers are unchanged.

### Cached start (`tools/scripts/e2e-cache.mjs`)

- The migrated and seeded template lives in the Docker volume `mscd-e2e-cache-pg-<key>`: a cluster shut down cleanly with the template, the administrator password and a marker file. The key is a SHA-256 of the migrations, the key of the server build (every server source but Markdown notes and the inputs of the prebuild, so a change to code the seed runs builds the template again), `profiles/test.yaml`, the development secrets, the development licences, `packs/dist`, the PostgreSQL image, the tenancy mode and the layout. A run copies the volume into its own run volume and creates the lane databases from the template; a cold start builds the volume first, under a lock.
- The server and the mock providers build only when the SHA-256 of their sources changed (for the server also the prebuild script, the migrations and the development keys, which the prebuild writes into `src/generated`); the web builds (`api` and `sample`) are kept per source key in `node_modules/.cache/mscd/e2e/`, three per data source. The builds run while the containers start.
- `E2E_STACK_CACHE=off` builds everything again without using or changing the cache.

### Specs

- The 19 fixed waits are gone. `helpers.js` gains `pageSettled(page)` (no request of the page under way, finite animations at their end, the DOM quiet for 150 ms and two more frames) and `framesPass(page, n)` (n frames drawn). Contrast and readability checks wait with `pageSettled`; the motion checks of `auth-motion.spec.js` and `illustrations.spec.js` wait for frames, for a new canvas picture (`expect.poll`), for the frame costs of 90 frames or for the page's animation clock; the debounce check of `sign-in-discovery.spec.js` runs the page's timers on with `page.clock.runFor`.
- `layerAfterAction` and `clickClaimable` of `helpers.js` waited a fixed 2 s and 1.5 s for a dialog that may not come; they now wait with `pageSettled`. `clickClaimable` and `runExtraPageAction` also let the page settle before they press Escape on a form that just opened (a layer listens for Escape from an effect that runs after it shows; a parallel run met the key first).
- The screen walks of `display.spec.js` and `i18n.spec.js` call `pageLoaded(page)` (new in `helpers.js`: no request of the page under way, two frames later still none) after opening each screen, before they decide whether a list has a row to open: a cold run met a Registers list loaded from the api that was still empty in the English walk and full in the Indonesian one.
- `display.spec.js` and `i18n.spec.js`: each walk of every screen of a system runs as two parts (each walks half of the session's sidebar, the parts together every screen), and the host screen walk of `i18n.spec.js` runs as one test per host screen. `test.slow()` is gone from the parts. The font test of `display.spec.js` reads the test's `baseURL` instead of the project's.
- `auth-motion.spec.js` and `illustrations.spec.js` read the API web build of the cache instead of building one in the test (deviation 2); `auth-motion.spec.js` runs its tests in parallel.
- `findings.spec.js`: waits for the page to settle before Close and before it switches the session (deviation 3).
- Second round: `pageSettled` and `pageLoaded` wait for the end of the last request itself (`requestsDone`); `openApp` and `switchMs` first wait in the page with `shownSoon` and `textSoon`; `expectNoTextOverflow` and `contrastProblems` finish the animations in their own page script; `controls-edit.spec.js` and `evidence-edit.spec.js` read a dialog's text without waiting, and `sign-in.spec.js` accepts that the page reaches the sign-in page before the menu click (deviation 11).

### Memory budget and runners

- `tools/scripts/e2e-budget.mjs` (new): memory in use (`MemTotal - MemAvailable`), the budget (`E2E_MEMORY_BUDGET_MB`, default 12288), the measured costs (1.1 GB per API lane after 1.5 GB fixed, 0.6 GB per sample worker after 1.2 GB fixed), lanes and workers that fit (at most 6 lanes, 10 workers, half the CPUs) and a memory sampler.
- `playwright.config.js` takes its workers from the budget (`E2E_SAMPLE_WORKERS`), `playwright.api.config.js` its lanes (`E2E_API_LANES`). The sample suite's web server is `tools/scripts/e2e-web-serve.mjs` (cached build, `vite preview`).
- Every run of either suite ends with the peak memory in use against the budget: the reporter `tools/scripts/e2e-memory-reporter.mjs` samples from the start of the run (before the web server builds), and the API stack logs its own peak when it stops.
- `npm run test:e2e:all -w @mscd/web` (`tools/scripts/e2e-all.mjs`): both suites, side by side when both fit the budget and one after the other otherwise (on this host: one after the other), with a summary of wall time, test count and peak memory per suite and for the run; the summary is also written to `node_modules/.cache/mscd/e2e/last-e2e-all.json`.
- Traces: GitHub Actions keeps them on failure. Locally they cost three times the run (`display.spec.js` on 10 workers: 237 s with traces, 81 s without), so a local run records them only on a retry; `E2E_TRACE` sets the mode.

### CI (`.github/workflows/ci.yml`)

| Job | Content |
|---|---|
| `Web E2E (sample data) shard i/4` | `npm run test:e2e -w @mscd/web -- --shard=i/4`, blob report, traces of failures |
| `Web E2E (sample data)` | merges the 4 blob reports into one HTML report (`e2e-sample-report`), fails when a shard failed |
| `Web E2E (API) shard i/8` | `npm run test:e2e:api -w @mscd/web -- --shard=i/8`, blob report, traces of failures, removes the test containers |

The final jobs keep the names of the old jobs, so the required checks keep working. Each shard restores the web build cache (`actions/cache`, keyed by the web sources). A runner with 4 CPUs runs 2 workers or 2 lanes per shard (half the CPUs). The shard counts come from the CI baseline: the sample job ran about 15 minutes of tests on 2 workers and the API job about 25 minutes on one; with the waits removed, 4 sample shards and 8 API shards (2 lanes each) should take 3 to 4 minutes of tests plus about 3 minutes of setup and, for the API, 1 to 2 minutes of stack start. The YAML parses and `actionlint` 1.7.7 (Docker image `rhysd/actionlint`) reports nothing.

## Measurements behind the design

- Where the time went: the API suite is CPU bound on this laptop. With 6 lanes the CPU was about 62 % busy on average (Chromium about 6 cores, Node about 2.5, PostgreSQL about 2), and on a subset (`display.spec.js` and `portfolio.spec.js`) 4 lanes took 144 s and 6 lanes 132 s: more lanes add little. The sample suite on the heaviest specs: 7 workers 104 s, 10 workers 94 s.
- Disabling the GPU of Chromium did not change the wall time of a subset (133 s against 132 s), but on `display.spec.js` the browser used 11 % less CPU (711 against 798 CPU seconds), which the full suite shares; the second round turned it on (`--disable-gpu`).
- One API test on an idle lane: reset without a write 65 ms (50 ms of it the reset of the mock providers), Mailpit 35 ms, session 45 ms, the start of the app 430 ms.
- Second round, per step over the whole API suite (6 lanes): the start of the app (from the page load to the title) took 0.65 to 0.9 s per test under load, the hooks before a test 0.4 s (page, reset, session) and after it 0.2 s (closing the context); clicks were 30 % of the summed time (5531 clicks, about 110 ms each, which includes the render they cause). By process, Chromium used about 60 % of the CPU, PostgreSQL 15 to 17 %, the api processes 11 %, the test workers 10 % and the mock providers 3 %. In PostgreSQL, the F.10 pool guard query (it reads `pg_settings`, 1.4 ms per checkout, run on every checkout in test profiles) was 23 % of the statement time and planning 40 %.
- Second round, PostgreSQL round trip from the host: 375 microseconds through Docker's published port, 150 on the container's address, 105 over the Unix socket.

## Deviations

1. **The warm API suite takes about 6 minutes against the brief's target of 4.** It went from 24.4 minutes to 6.0 min (357 s) and 5.8 min (351 s) in the warm runs of the follow-up round (6.0 to 6.6 minutes in the earlier rounds). The plan's first pass line was 5 minutes; after the second round's profiling the orchestrator set the line for this host to 7 minutes (commit 23b50ea, the product owner was told), which the suite meets; the line for CI is unchanged. On this laptop the suite is bound by the processor at 6 lanes: 8 lanes took 366 s against 375 s for 6, the processors were 60 to 66 % busy (with 6 performance cores sharing two threads each, that is their limit), and per test the work is spread over Chromium (about 60 % of the CPU), PostgreSQL (about 15 %), the api processes (about 10 %) and the test workers (about 10 %). The second round cut the summed test time by 5 to 9 % on 6 lanes (2068 s and 1975 s against 2167 s) and the warm start of the stack by 5 to 7 seconds; what is left is the tests' own work. Three changes outside the paths of M2-21 would cut it further: a cheaper pool guard query (F.10 reads `pg_settings` on every checkout in test profiles, about 1.4 ms each; it was 23 % of PostgreSQL's statement time in the API suite), a cheaper reset of the mock providers (about 50 ms of CPU per test, on the critical path of every test), and a faster host. The sample suite's target of 3 minutes is not met either (about 3.7 minutes; the pass line is 4).
2. `auth-motion.spec.js` and `illustrations.spec.js` built the API bundle inside the test (about 30 s and 1 GB each, in both suites). They now read the build of `tools/scripts/e2e-cache.mjs`: the same `vite build` of the same sources, kept while the sources stay the same, and only read. `auth-motion.spec.js` dropped its serial mode, which only served the one build.
3. `findings.spec.js` failed twice in parallel runs: once Close met a stale version (the drawer reads the finding again after "Save texts"; a click before that read ends sends the old version), once the session switch cleared the cookies while the page still had a request under way ("Sign-in required"). The spec now waits for the page to settle at both places. The first is a race in the findings screen itself; a person who clicks fast can meet it too (follow-up).
4. The write tracker counts more than the plan's rule (requests other than GET or HEAD, job runs): it also counts audit entries and the sign-in and consent callbacks, which are GET requests that write, and it deletes the minted sessions at a reset without a write. Without that, a test after a download or a sign-in through OIDC would see the previous test's rows.
5. Each lane has its own Mailpit (a shared one would let one lane's "clear the mail" delete another lane's messages) and its own bucket. The plan names only the shared PostgreSQL, object store and web build.
6. The sample suite's build is cached as well (the plan names the API web build only).
7. The cache volume has the name the plan asks for, `mscd-e2e-cache-pg-<key>`, without the run's container prefix: it is shared by every run and never removed by one.
8. In `docs/DEVELOPMENT.md` the old "End-to-end tests" section with its "API end-to-end project" part became the "Browser suites" section (lanes, budget, cache, reports, CI and the default data source of the web app).
9. The tests of the write tracker are written and pass (also in the follow-up round's tree) but are not in the repository: the server's tests live in `apps/server/test/`, outside the paths of M2-21. They are in `/var/tmp/m2-21/proposed/apps/server/test/` (a unit test of 11 cases and an integration test of 4 cases, see the second round above) for the orchestrator to copy. The existing integration test `test/int/test-support` passes; its test `a reset restores a changed row` depends on the first-reset rule, which the module's README now states.
10. From the afternoon of 31 October, Milestone 3 packages (M3-01, M3-08, M3-M01) changed the shared working tree and ran builds, tests and API stacks on the host. The second round therefore built and ran the suites in `/var/tmp/m2-21/tree`: the committed HEAD of that time (cf6c4f5) with exactly the files of M2-21 laid over it and the repository's `node_modules` linked in. The follow-up round did the same in `/var/tmp/m2-21/fix2/tree` at commit 23b50ea, which includes the M3-08 specs (that is why the counts before M2-21 rose from 523 and 399 to 529 and 404): exactly the 38 files of M2-21 and the two proposed server tests laid over it. That is the state M2-21 is committed on, unless the orchestrator commits other work first. Timings vary with the other packages' load: no other stack ran next to the runs in the tables.
11. Three specs that M2-21 does not otherwise touch failed in parallel runs of this round, and are fixed the way `findings.spec.js` was (deviation 3):
    - `api-only/controls-edit.spec.js` and `api-only/evidence-edit.spec.js` polled with `innerText()` on a dialog that may close between two reads; `innerText()` then waits up to the action timeout (15 s) for a dialog that never comes back, longer than the poll (10 s). Both now read the dialog's text without waiting (`allInnerTexts()`); the check is the same (no dialog left, or the dialog shows the message).
    - `api-only/sign-in.spec.js`, "a session that ends on the server sends the user back to sign in with a notice", failed twice under load: after the reset, a read the page itself started once idle (later than `networkidle` on a busy machine) met the ended session and opened the sign-in page while the test clicked the menu. The test still opens the menu and picks its first entry, and now also accepts that the page got to the sign-in page first; it then checks the same end state (the sign-in page with the notice). The three specs passed twice each in a row afterwards, and in every full run since. The menu click still runs whenever the page has not reached the sign-in page by itself; when it has, the page's own read of the ended session caused the redirect before the click.
