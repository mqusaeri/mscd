# M2-09 handoff: storage and management system administration

M2-09 builds three web screen folders on the screen host of M2-01: the repository administration (`storage-admin`, no sidebar entry) with the "Connect repository" wizard and the settings drawer, which also claims `storage.connect` and `storage.settings` on the Storage repositories screen; "Routing rules" with the stored files tab; and "Management systems" with the "Edition transition" page action of the Framework library. No server code, shared contract, generated view or shared web file changed.

### Routing rules (`apps/web/src/screens/routing/`)

Screen `routing`, path `/admin/storage/routing`, group `admin`, order 34, perm `storage.repository.read`. Tab "Rules": system (or whole organisation), what the rule applies to (classification and file kind), repository with the rule's note, storage mode, priority, state (active, waiting for approval, rejected, replaced on request) with who asked and who decided, and the actions. "Add rule" (page action) and "Edit" open a drawer (system, classification, file kind, repository, the repository's modes, priority 0 to 32767, note up to 500); a 409 `confirmation-required` (BR-38) opens the confirmation dialog with the server's message and sends again with `confirm: true`. "Approve" and "Reject" (with a confirmation) show for pending rules, disabled with the reason for the person who asked (A-50) and for a session that is not a Tenant Admin. Edit shows for active rules and for a pending rule of the session's own request. A read-only notice replaces the actions for a session without `storage.routing.manage`. Tab "Stored files" (with `storage.object.metadata.read`): name and folder, repository, system, size, type, hash and the result of the last check, filters by repository and check result, paged by 50; never the content.

### Management systems (`apps/web/src/screens/systems/`)

Screen `systems`, path `/admin/systems`, group `admin`, order 32, perm `ms.admin`. The list shows code with the colour, name and short id, standard and edition (with the edition in transition), status, primary MS Manager (from `admin.users.list`), default repository and the actions; archived systems come last without actions. Before the first system the list shows the `no-systems` scene of the illustration library (MOT-03) in its empty state, with the "New management system" button. "New management system" (page action, `ms.admin` and `pack.activate`): code, short id (suggested from the code), name, standard and edition from the installed packs (one installed version per pack, with "Installed" and "Beta, pre-release" badges and the beta notice), scope statement, certification body, colour from a palette of eight colours that keep 3:1 against the light and dark surfaces, default repository; `POST` with an `Idempotency-Key`. "Edit": scope, certification body, colour (the current colour stays offered when it is not in the palette), default repository; `PATCH` with the changed fields. "Start implementation" (`status: implementing`) and "Archive" (`status: archived`, the code typed to confirm) go through a confirmation dialog that shows the server's refusal, for example "Assign at least one MS Manager before the system moves to implementing.".

`actions.ts` adds the page action "Edition transition" to the Framework library (`extraPageActions`, C.5) for sessions holding `ms.transition` in a system. Its drawer (`Transition.tsx`, lazy, through a layer item) lists the systems the session may transition that have a newer edition installed (`admin.packs.list`) or are in transition: "Start edition transition" with the target edition, or "Finish transition", each with the server's refusal next to the system, and the note that entries keep pointing at the old edition (plan B).

## Deviations

1. **The sample build keeps the Milestone 1 toasts of "Connect repository" and "Settings" on the Storage repositories screen.** `e2e/storage.spec.js` and `e2e/shell.spec.js` (Milestone 1 specs that this package's acceptance runs and does not own) pin those toasts, and a drawer opened by "Settings" would block the next click of that spec. The claims follow the pattern of the other repository commands of the card (H.4): toasts in the sample build, real work in API builds. The sample build reaches the wizard and the settings drawer through the Repository administration screen (`?screen=storage-admin`), and `e2e/screens/storage-admin.spec.js` covers them there.
2. **"Edition transition" shows in API builds only.** `e2e/shell.spec.js` pins exactly one page action on the Framework library of the sample build. The sample already shows the ISO 9001 system in transition with the "Transition" button of its row. The drawer is covered by unit tests and `e2e/api-only/systems.spec.js`.
3. **Edition transition and system status.** The snapshot carries no system status; `MS.ed` shows `2015 to 2026` whenever a target edition is set, and the demo seed sets one on a certified ISO 9001 system. The drawer therefore reads the statuses with `admin.ms.list` when the session holds `ms.admin`: a certified system is offered the start even when a target is set, a system that is not certified gets the start disabled with the reason, and only a `transitioning` system is offered "Finish transition". Without `ms.admin` the drawer falls back to `MS.ed`, and the server's refusal shows next to the system.
4. **The Microsoft 365 tenant.** `RepositoryCreate` has no tenant; the tenant id is part of the credential (`m365_certificate.secret.tenantId`). The wizard asks for it in the settings step (as the brief says), stores it in `display.tenantId` with the card summary in `display.configSummary`, and fills it into the credential step. `RepositoryView` returns no `display`, so the settings drawer asks for the tenant in its credential section.
5. **My Drive.** `GoogleDriveRepositoryConfig` requires `driveId`, but a My Drive has none (WP-15 follow-up). The wizard stores `root` (the Drive API alias of the account's own root), which the gateway ignores for a My Drive, and saves the repository as personal storage with the BR-30 warning (product decision 1).
6. **Stored files: the system column.** `StorageObjectMeta` carries no system. The screen derives it from the folder path and the repository's folder per system (`config.roots`); files outside those folders (for example in the Managed Vault) show "-".
7. **Primary manager.** `ManagementSystemView` carries no manager. The screen reads `admin.users.list` (the Tenant Admin who holds `ms.admin` also holds `user.manage`), 200 members per page and at most 25 pages, and shows "Not shown" without that permission.
8. **Screen orders.** Management systems 32, Routing rules 34 and Repository administration 38 sit after Licence (30), so a Tenant Admin without a business role still lands on Licence until M2-16 adds "Getting started" (C.3).
9. **Layout choices.** The routing table shows classification and file kind in one "Applies to" column and who asked in the State column, so the action column keeps Approve and Reject on one line with the reason below them. Rule, system and repository forms are drawers, so the BR-38 and the Start and Archive confirmations open as dialogs above them. Drawer footers keep 72px clear of the floating Tera button.
10. **BR-38 in the API project.** The test profile is on-premise, so a rule to the Managed Vault never asks for BR-38 there. The confirmation is covered by the sample adapter and its spec (which applies BR-38 as the SaaS deployment of the sample does) and by unit tests with a 409 `confirmation-required` answer.
11. **An MS Manager without an administration role does not see the Storage repositories screen in API builds** (C.3), so the toast of a session without `storage.repository.manage` is covered by unit tests only.
12. **Snapshot reloads.** After a write the screens reload their own list and call `ctx.reload()` (D2-08); a reload that fails (for example because the session ended) is caught, so it never becomes an unhandled rejection, and the shell's sign-in handling takes over.

No dependency was added.
