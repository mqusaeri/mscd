# M3-M02 handoff: major dependency upgrades

M3-M02 takes the major versions that Dependabot proposed in pull requests 4 and 6 and that failed CI (MILESTONE-3 K.2), in the four steps of the brief. Steps 1, 2 and 3 are in; step 4 (TypeScript 7) is left out with a Dependabot ignore rule, because no `typescript-eslint` release supports it. The production tree now holds `glob` 14.0.3 and `minimatch` 11.0.3 only, the two entries of `osv-scanner.toml` are gone, and the OSV scan finds no known vulnerability.

Three implementers worked on the package: the first did step 1 and stopped at 10:47 when the owner's laptop stopped; the second added the other server majors of pull request 4 to step 1, ran most of its acceptance and tried steps 2 and 3 in scratch copies, and was interrupted at 12:27; the third finished step 1 and did steps 2, 3 and 4. A follow-up round then applied five minor review findings: the NestJS tracing gap (step 2), the Node.js version in the `engines` fields, the stack versions in the documents, and two wording and record fixes in this note. Nothing is committed (the orchestrator commits).

## What changed

### Step 1: `kysely` 0.29 and the other server majors

- `kysely` 0.29 moved the migration classes to `kysely/migration`: `apps/server/src/db/migrator.ts`, `sql-migration-provider.ts` and `tenant-provisioner.ts` import `Migrator`, `Migration`, `MigrationProvider` and `MigrationResult` from there.
- Its `PostgresPool` interface now has an `options` member. `GuardedPool` (`db/pool-guard.ts`) exposes the options of the underlying `pg` pool through a getter; its own settings field is renamed `guardOptions`.
- Its PostgreSQL adapter takes the migration lock as a session lock (`pg_advisory_lock`, released with `pg_advisory_unlock`); 0.28 took a transaction lock (`pg_advisory_xact_lock`) and released nothing. Tenant provisioning (C.8) runs the tenant migrations inside its own transaction with `disableTransactions`; when a migration failed there, the release query failed in the aborted transaction and hid the migration's error (`test/int/db/tenant-provisioner.test.ts`, "rolls every step back when a tenant migration fails"). `createKysely` in `db/kysely.ts` takes a new option `transactionMigrationLock`: a dialect whose adapter takes the same lock id as a transaction lock and releases nothing, as before. `TenantProvisioner.create` uses it; every other Migrator (the `migrate` run mode) uses Kysely's own adapter.
- `bullmq` 6 (`modules/jobs/bullmq-job-queue.ts`): the Redis client is read with `queue.getBackend().client`; the due-job scan reads the lists `wait` and `prioritized` only, because BullMQ 6 keeps the jobs of a paused queue in the waiting list and has no job type `paused` any more.
- `ioredis` 6 speaks RESP3 by default. The BullMQ connection options and the Valkey client of the rate limit store (`modules/platform/rate-limit.ts`) set `protocol: 2`, the protocol of ioredis 5, so the data in Valkey and the replies the code reads keep their form.
- `undici` 8 offers HTTP/2 by default. The provider client of the Microsoft 365 and Google Drive adapters (`gateway/adapters/m365/provider/http.ts`) sets `allowH2: false` and keeps HTTP/1.1. The other undici agents of the server call MSCD's own Fastify servers (storage gateway, tenant provisioning), which answer HTTP/1.1 only.
- `testcontainers` 12 waits for an image's health check by default; the SeaweedFS container of the gateway tests (`test/int/gateway/helpers.ts`) waits for its listening port, as before, and the readiness loop that follows stays.
- `commander` 15 and `ical-generator` 11 needed no change. `ical-generator` has no importer in the repository (follow-up 3).

### Step 2: NestJS 12, the Fastify plugins and `nestjs-pino` 5

- One source change, in the OpenTelemetry preload (`modules/observability/otel-preload.ts`). The NestJS instrumentation of `@opentelemetry/auto-instrumentations-node` 0.80.0 (`@opentelemetry/instrumentation-nestjs-core` 0.68.0, the newest release) patches `@nestjs/core` from 4.0.0 up to below 12 only. Under NestJS 12 it skips its patch without a message, so a server with `telemetry.enabled: true` sends the HTTP server span of each request and no NestJS request or handler spans. The preload now turns that instrumentation off explicitly, with the reason in a comment, so the gap shows in the code; the settings moved into an exported `autoInstrumentationConfig()`. A new unit test (`test/unit/observability/otel-preload.test.ts`) checks the settings and fails as soon as the installed instrumentation supports the installed `@nestjs/core`, as the reminder to turn it on again (follow-up 7). Telemetry is off by default (`telemetry.enabled: false`), so a default install sees no change. The other instrumentations that meet an upgraded package accept the new versions: pino below 11, ioredis below 7, pg below 9, and undici through its diagnostics channels without a version range.
- Apart from that, the server builds and its CLI help, request log lines (fields, redaction, `set-cookie` censored) and response headers are the same as under NestJS 11 (a small application with the server's logger parameters, compared before and after).
- `nestjs-pino` 5.1 and later keep one `pino-http` instance for the whole process, made by the first application that starts in it; later applications of the same process reuse it with the first one's settings. Every MSCD process (api, worker, storage gateway, migrate and each CLI command) builds one application, so production logging is unchanged. The integration tests build several applications in one process: the J.5 log redaction test (`test/int/security/http.test.ts`) asked for level `info` in its second application, got the silent logger of the first and saw no line. The test now sets the level on the shared logger through `PinoLogger.root` (the documented way to change logger settings at run time) and restores it afterwards; its assertions are unchanged. No other test reads the logs of a later application: ops-routes builds its `warn` application first in its file, and the notification and evidence pack helpers raise the level for troubleshooting only. `nestjs-pino` 5.0.0 still built one instance per application, but staying on it would need an ignore rule against every later 5.x fix.
- `fastify` stays deduplicated: one copy at the root (5.12.7), used by the server, `@nestjs/platform-fastify` and the mock providers. The NestJS 12 packages and pino 10 sit in `apps/server/node_modules`, because the mock providers keep pino 9 through Fastify.

### Step 3: ESLint 10, vitest 5, React 19 and Vite 8

- ESLint 10's recommended rules add `no-useless-assignment` and `preserve-caught-error`; the lint found 28 places. Each `let x = initial` whose value every path replaces before reading it lost the initial value (vault retention and legal hold, the BullMQ delay, licence check, metric samples, deletion certificate signature, ops health organisations, invitation mail flag, the web identity provider sample host and time zone list, three integration test helpers, the mock provider self-test, the e2e cache and build locks, the smoke runners' results). Each error thrown from a `catch` block now carries the caught error as `cause` (anchor key and export verify key files, pg-boss start, pack signing and public keys, the SeaweedFS test helper, the e2e cache lock). The messages are unchanged; Node.js prints the cause under an uncaught error, and pino adds it to a logged error. `eslint.config.mjs` needed no change.
- `minimatch` 11 for the whole tree through one override (`"minimatch": "11.0.3"`, replacing the step 1 override inside `readdir-glob`): ESLint 10 and `typescript-eslint` 8.72 still ask for minimatch 10. ESLint lints the same 1536 files with minimatch 10 and 11 and reports the same result.
- `vitest` 5 takes `vite` as a peer dependency, and npm overrides do not reach peer dependencies, so the `vite` override alone left each workspace with its own `vite`. The root `package.json` now names `vite` 8.3.4 as a development dependency, with the same exact spec in the override and in the web app; the tree holds one `vite`, one `vitest` and one copy of each `@vitest` package.
- React 19 changed the markup of `react-dom/server`, which only the web unit tests use (the app renders in the browser with `createRoot`): a `<link rel="preload" as="image">` for each image comes first, and an input's `name` and `value` come after its other attributes. Nine assertions in `test/auth/pages.test.ts`, `test/auth/motion.test.tsx` and `test/screens/my-confirmations.test.tsx` now check the same attributes one by one (`inputAttributes`) or strip the logo preload before the markup that must come first. No browser spec needed a change for React 19.
- Vite 8 builds with Rolldown; the build settings needed no change. The server's `vitest.*.config.ts` files print a notice that a future Vite major will load configuration files natively (follow-up 4).
- Vite 8's proxy ends the request to the api when the browser goes away before the answer (`res.on('close')` destroys the proxied request); Vite 6's proxy did that only for a request whose body had not fully arrived. The API suite runs the web app with `vite preview` and this proxy, so a page that a test closes or leaves now aborts its open requests at the api. The test reset's request gate (`modules/test-support/request-gate.ts`, M2-21) lets an aborted request go at once (Fastify's `onRequestAbort`), while its handler can still be inside a transaction; the reset then dropped the database (`WITH (FORCE)`) under that transaction, and when the end of the session reached a checked-out `pg` client between two statements, that client had no error listener and the api process stopped ("terminating connection due to administrator command", 57P01). The API suite of step 3 failed twice that way (349 and 411 tests failed after a lane's api stopped), while smoke, journey and lifecycle passed. `recreateDatabase` (`modules/test-support/database-reset.ts`) now waits, before the drop, until no other session of the database runs a statement or holds a transaction (`pg_stat_activity`, at most 5 seconds; the reset logs a warning when the time ran out), and the reset service passes that on. The change is in the test reset only, which test profiles alone enable; production code is unchanged. A new integration test holds a transaction open on the database during a reset: the reset waits for it and the transaction commits; with the wait disabled the same test fails with the connection error the lanes had.

### Step 4: TypeScript 7 left out

- TypeScript 7 ships the compiler as a native program: `require('typescript')` gives only `version` and `versionMajorMinor`, without the compiler API that `typescript-eslint` loads for type-aware lint, and no `typescript-eslint` release supports it (8.72.1, the newest, accepts TypeScript below 6.1). The brief takes TypeScript 7 only when every tool that loads the compiler supports it, so the step was not applied.
- For the follow-up: the TypeScript 7.0.2 compiler checks every workspace without an error (`tsc --noEmit` in a scratch copy: 3635 files of the server, 781 of the web app, and shared, pack-tools and mock providers), and so does TypeScript 6.0.3.
- `.github/dependabot.yml` ignores `typescript` from 7.0.0 on, with the reason. Dependabot may still propose TypeScript 6.0, which `typescript-eslint` supports.

## Follow-ups

1. TypeScript 7: remove the ignore rule when `typescript-eslint` supports it; the compiler itself already checks every workspace.
2. `@types/node`: move the ignore rule with the Node.js runtime of CI and the images.
3. `ical-generator` is a server dependency that no file imports. Remove it, or keep it for a planned calendar feed.
4. A future Vite major loads configuration files natively: the server's `vitest.*.config.ts` files use ESM syntax in a CommonJS package. Rename them to `.mts` (and update `package.json`, `tsconfig.json` and CI) or set `VITE_CONFIG_NATIVE_IGNORE_WARNING`, before that major.
5. CI uses `node-version: '22'`. `testcontainers` 12 needs Node.js 22.22 or later, `undici` 8 22.19, NestJS 12 and `commander` 15 22.12, and every `engines` field now says `>=22.22`; the build host has 22.22.0 and the image base `node:22-alpine` 22.23.4. If a CI runner ever resolves an older 22.x, set `check-latest: true` in the setup step.
6. Production hardening, outside this package: a checked-out `pg` client that loses its connection between two statements stops the process, because `pg` removes its error listener while a client is checked out. The test reset no longer causes that, but a database restart or an operator's `pg_terminate_backend` in the middle of a request can. An error listener on each checked-out client in `GuardedPool` (`src/db/pool-guard.ts`) would turn that into a failed request; it changes production behaviour, so it was left out here.
7. NestJS tracing: turn `@opentelemetry/instrumentation-nestjs-core` on again in `otel-preload.ts` when a release supports NestJS 12 (`test/unit/observability/otel-preload.test.ts` fails then and says so). Until then, traces hold the HTTP server span of each request without NestJS request and handler spans.
8. The orchestrator applies the `CLAUDE.md` and `BUILD-PLAN.md` lines of "Documents".
