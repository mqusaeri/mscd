# M2-18 handoff: fresh-organisation journey and release check

M2-18 proves that a customer organisation without demo data can run its ISO/IEC 27001 programme in the browser, from the first administrator's invitation to the certificate, on-premise and, up to the creation of the management system, on SaaS. It also extends the release artefact check with the demo texts of E.4 and the lead auditor sign-off of E.2, makes the strict layout check of the smoke test the default, replaces the browser console helper of `docs/INSTALL-ONPREM.md` with the screens of Milestone 2, and corrects `project/MSCD User Guide.dc.html`. No application code, shared contract, generated view, migration or dependency changed.

## What was built

### The journey runner (`tools/smoke/run-journey.mjs`, script `journey`)

`npm run journey -w @mscd/smoke` and `npm run journey -w @mscd/smoke -- --saas`. Both take the host lock (R-05) because they publish the ports of the smoke stack.

| Stack | `deploy/compose/docker-compose.yml`, `docker-compose.demo.yml` and `tools/smoke/compose/journey.yml` as project `mscd-journey` (`JOURNEY_PROJECT`). The overlay gives the one-shot `seed` service a profile that is never started and lets api and worker no longer wait for it, so the database holds no organisation; turns the demo personas off; and fixes the server date (`demo.fixed_today`) to today in the organisation's time zone. ### The journey (`tools/smoke/tests/fresh-org.spec.mjs`)

Each person has their own browser session; every step is done on screen. Emails come from Mailpit, authenticator codes from the secret each person enrolled (read from the enrolment page as a phone scans it), and the team signs in through the development Keycloak. Every step fails on a page error, a console error (the browser's own "Failed to load resource" lines for 4xx answers are not errors of the app) or a 5xx answer. Every screen a person visits for the first time is checked with `expectReadableText` of `lib/readable.mjs`: WCAG AA contrast (4.5:1, 3:1 for large text) against the composited background, and no text under 12px; every dialog and drawer is checked with `expectOverlayReadable`. The first-visit checks cover the screens of the sidebar (`go`) and, through `firstVisit`, the sign-in pages (their card is in `main`): the invitation page, its "Find the sign-in of my organisation" lookup on SaaS, the invitation page with the company sign-in, the set-password page and the enrolment page, the sign-in page the SaaS operator uses after setting a password, and the sign-in and second-factor pages of anyone who signs in again (no step of either run does today); and the first screen each person lands on: Getting started for Ana and Dewi, the first administration screen for Bagus, and for Rina, Hendra and Maya the full-page message "You hold no role in a management system of this organisation yet.", which has no `main` and is checked with `PANEL_SCOPE`. A check whose scope measures no visible text fails, so a screen outside the scope can no longer pass unmeasured.

### Release check (`deploy/scripts/check-release-artefacts.sh`)

For every framework pack (a `.pack` or `.bundle` file given as a target or found inside a bundle, an image layer or a folder), after the existing checks:

- the demo texts of E.4: `NC-2025-02`, `SoA v3.0`, `DC Jakarta` and "Internal audit 2026 report" in any file of the pack, `SharePoint` in its `prep_tasks.csv` and `cycle_requirements.csv`, and the demo phase "ISO 9001:2026 transition" in the ISO 9001:2026 pack (the ISO 9001:2015 pack keeps its transition phase as release content, M2-04 deviation 8);
- a lead auditor sign-off row in `packs/README.md` ("Lead auditor sign-off" table) for its `pack_id` and `pack_version`, with a name other than "not signed yet" and a date. Without it the check fails; `MSCD_ALLOW_UNSIGNED_PACKS=1` turns that finding into a warning for rehearsal builds and is never set for a release.

`--help` documents both. Checked with crafted packs: a clean pack fails on its missing sign-off and passes as a warning with the variable; a pack with "SoA v3.0" fails also with the variable; the 2026 pack with the transition phase fails; the 2015 pack passes; SharePoint in a prep task of a pack inside a `.tar.gz` fails; a copy of the script whose sign-off table signs ISO27001-2022 1.3.0 passes that pack; a pack of `packs/dist` still fails on the development key id. `shellcheck` passes.

## Deviations

1. **Time passes on the server.** BR-08 refuses an effectiveness check on the day of the implementation, and Record result shows only for an audit that has taken place. The journey therefore plans the audits ahead and later moves the server date forward 35 days: it recreates api and worker with a later `demo.fixed_today` (demo builds only), with every page closed during the restart and the 5xx count paused, then waits until the web container reaches the new api (NGINX keeps a resolved address for 10 seconds) and opens the pages again with their sessions. The harness stands in for the weeks between the steps; the journey changes no data through the API or the console.
2. **The roles.** Getting started needs two people who can verify per system, so Hendra holds Programme Owner next to Top Management; the four-eyes approval is shown with Bagus, a Storage Admin, because with two Tenant Admins a grant to either of them has no one left to approve it.
3. **The ISMS starts in the Managed Vault.** The file pickers of a system on SharePoint or Google Drive offer Link only: they read the system's default repository, so neither Pass-through nor a routing rule by kind or classification changes them (the read model's default route takes only rules of a whole system). To upload the POL-01 file in the browser, as the brief asks, the journey creates the ISMS with the Managed Vault as its default repository. After Hendra approves POL-01, the ISMS gets its folder in the library and **Edit** in Management systems makes the library its default repository; the evidence and the audit report are then linked from the library, and POL-01 stays in the vault. Section 10.4 of the install guide describes the same move.
4. **Internal audit activity.** No pack has activity templates for internal audits (M2-14 backlog) and the internal audit drawer has no action that adds an activity (there is no route for one either: only `audit-activities.generate` and `.update`). The journey presses "Generate from templates" and asserts the message that the pack has no templates and "No activities yet.", then records the outcome summary, the report and the finding.
5. **Readiness.** The Overview shows the level of each clause group (0.0 to 4.0, or "-" when not computed); the journey requires a level above 0. With the work of the journey, Leadership (clause 5) reaches 3.0.
6. **SaaS company sign-in needs a verified domain.** On a service with several organisations the invitation link names no organisation, so the invite page lists no company sign-in until the person looks it up by work email, which finds an organisation only through a verified email domain. The SaaS variant therefore verifies the domain in the operator console (M2-S11, M2-S12) before the team accepts.
7. **Reloads between people.** A person's open page keeps the snapshot it loaded and reloads it after the person's own changes; changes of other people show after the app loads again. The journey loads the app again before a person acts on another person's change, as a person coming back later does. One case needs it although the person made the earlier move (see "Needs from the orchestrator" 3).
8. **Dates on screen.** `fixed_today` is the date of the organisation's time zone when the run starts, so the dates the screens show stay the same for the whole run; the authenticator codes and the sessions use real time.

No dependency was added. `tools/smoke/package.json` gained the script `journey` and a longer description; the lockfile does not change.

## Needs from the orchestrator

1. **SaaS: the api cannot create organisations (`deploy/compose/docker-compose.saas.yml`, M2-S02 or M2-S13).** `POST /ops/organizations` answers 503 "Creating an organisation needs the database owner role in the api (database.migrator_url_file)": the api of the SaaS Compose stack has no `db-migrator.url` secret, so "Create organisation" of the operator console fails on a real SaaS server. The journey's SaaS overlay adds the secret to the api (`tools/smoke/compose/journey-saas.yml`); the SaaS overlay needs the same (and the Helm values for multi tenancy should be checked).
2. **Release check and rehearsal builds (`.github/workflows/ci.yml` of M2-S13, `deploy/scripts/build-release-images.sh`, `build-bundle.sh`, `deploy/scripts/test/saas-rehearsal.sh`).** Every pack version in `packs/README.md` reads "not signed yet", so `check-release-artefacts.sh` now fails on every release image and bundle until a lead auditor signs the packs (E.2). The CI `images` job, the deploy rehearsal and any bundle rehearsal need `MSCD_ALLOW_UNSIGNED_PACKS=1` (rehearsal runs only); `release.yml` and the customer bundle build must not set it.
3. **Registers (M2-13, `apps/web/src/screens/registers/api.ts`).** The page that moved a treatment to Implemented keeps that status after the risk owner accepts the residual risk in another session: `treatmentOf` keeps a move while the record's action text is unchanged, and Implemented, Residual accepted and Closed all have no action text. "Close treatment" stays disabled ("Accept the residual risk first") until the page loads again. Comparing the record's ETag as well would fix it. The journey loads the page again before closing the treatment.
4. **Internal audit activities (M2-14 backlog).** On screen an internal audit cannot get an activity: no template in any pack, no "Add activity" in the drawer and no create route. Either the pack content (a lead auditor writes internal audit templates) or a route and form are needed.
5. **Upload into a customer repository (M2-09, M2-11, M2-12, the generated picker).** A system on SharePoint or Google Drive cannot receive a file uploaded in the browser, also with Pass-through allowed; per-kind and per-classification routing rules do not change the pickers. The journey covers the browser upload through the Managed Vault (deviation 3).
6. **Demo text in the Framework library (`apps/web/src/MscdApp.jsx`, M2-01 or M2-17 owner).** A fresh organisation sees "Last bundle imported 18 Sep 2026 (ISO9001-2026 v0.9)" on-premise and "Packs are distributed automatically ... Last check 29 Sep 2026 06:00: 2 updates available." on SaaS in the update channel card: fixed sample sentences, the second one also contradicts M2-16 (the operator installs packs on SaaS).
7. **SaaS invitations (M2-06 or M2-S11).** The invitation link could carry the organisation (`/invite?org=<slug>#token=`), so a person invited to a SaaS organisation sees its company sign-in without a verified domain (deviation 6).
8. **Edit drawer of Management systems (M2-06, `apps/web/src/screens/systems/Screen.tsx`).** `SystemDrawer` stays mounted while closed and fills the form of the chosen system in an effect after **Edit** opens it. A change made in the first render after the opening uses the form of that render, which still holds the previous values (`set` spreads the `form` of its render): the scope, the certification body and the colour are emptied, and Save stops on "Fill in this field." The journey hit it once by choosing the default repository at once; it now waits until the form shows the system's values, as a person sees them. A functional `setForm((f) => ...)` in `set`, or a `key` per opening, would fix it.
9. **Display walks of the sample E2E (`apps/web/e2e/display.spec.js`, the walks at lines 54, 131 and 147).** The dark theme, density and font pairing walks have no `test.slow()`; alone they take 42 to 55 seconds of their 60 second limit, so a run next to a Compose stack times them out (21 of them in the first sample run of the review). `test.slow()` on them, as on the Indonesian walks, would give them room.
10. **Lock table of the test PostgreSQL (`apps/server/test/setup/global-db.ts`, M2-S13 owns `apps/server/test/setup/**`).** The full server integration suite fails at random on this host: the test PostgreSQL runs with the default `max_locks_per_transaction` of 64 (with `max_connections` 100, a lock table of about 6,400 entries), and two test files that provision tenant schemas (migration `0008_milestone2`) or reset the demo at the same moment exhaust it with `out of shared memory` (code 53200, hint "You might need to increase max_locks_per_transaction."). In the review, two of three full runs failed this way (`onboarding/organization.test.ts` at `CREATE POLICY tenant_isolation ON org_settings.management_review`; `entitlements.test.ts` at a `GRANT` on `org_zeta.document`; `seed/seed-command.test.ts` at `deleteFrom platform.app_user` of `seed-demo.ts`), the third passed, and `pg_locks` peaked at 11,921 rows. M2-18 changed no server file. Starting the container with `.withCommand(['postgres', '-c', 'max_locks_per_transaction=256'])` would fix it. No file of the repository sets the value: the bundled PostgreSQL of the Compose stack (`deploy/compose/docker-compose.yml`) runs with 64 too, and so does the SaaS overlay (`deploy/compose/docker-compose.saas.yml` sets memory settings in its `command` but not this one), and the Helm chart uses the customer's own PostgreSQL, so concurrent organisation creation on SaaS (several tenant migrations at once) should be checked against the same limit, and the install guide could name the setting for an external server.
