### `saas-stack.sh`

- **up:** removes what an earlier run of the same project left, checks that the two ports are free, picks the networks (`172.31.250.0/24` and `172.31.251.0/24`, or the first two free `172.31.x.0/24` ranges when another Docker network uses them), makes a throwaway key set with `saas-keys.sh --print-only`, builds the release images with it (`build-release-images.sh --load --registry localhost/<project>`), copies the build logs into the state folder, writes `.env` from `.env.saas.example` (`MSCD_TLS_MODE=internal`, `MSCD_DOMAIN=localhost`, `MSCD_PUBLIC_URL=https://localhost:18443`, the digests of `digests.json`, Mailpit as SMTP relay, the site on `site.localhost`, `MSCD_EDGE_IPV6=false` when the host has no IPv6), fills the secrets folder (the production `platform.key`, `storage.key` and audit anchor pair of the key set, the rest with the generators of `lib/common.sh`), copies `index.html`, `id/` and `assets/` of `apps/site`, writes a test overlay (Caddy on `127.0.0.1:18080` and `127.0.0.1:18443`, Mailpit on the internal network without a port), runs `docker compose config -q` and `up -d --wait` (migrate first, its exit code checked) and copies `/data/caddy/pki/authorities/local/root.crt` to `/tmp/mscd-saas-test/caddy-root.crt`. State folder `MSCD_SAAS_TEST_DIR` (default `/tmp/mscd-saas-test`): a plain absolute path below `/tmp`, `/var/tmp` or `$TMPDIR`, without `.` or `..` parts, `//` or a final `/`, because `down` deletes it (so `/tmp/../etc` is refused before anything runs).
- **check:** the five assertions of the brief plus the two of the acceptance text and a few more:
  - tenancy mode `multi`, read by the configuration loader of the server inside the `cli` service (`docker compose run --rm cli`), and the flavour `release`;
  - only Caddy publishes ports (from `docker inspect` of every container of the project), and it publishes 80/tcp, 443/tcp and 443/udp;
  - `curl --cacert /tmp/mscd-saas-test/caddy-root.crt https://localhost:18443/healthz` answers 200; `http://localhost:18080/` answers 308 to `https://localhost/`; HSTS is exactly `max-age=31536000; includeSubDomains`; the app page has the Content-Security-Policy with `frame-ancestors 'none'`, `X-Frame-Options: DENY`, no `Server` header and no `fonts.googleapis.com` (GL-25, GL-56);
  - 80 requests at once to `/api/v1/auth/mscd-rate-limit-probe` get at least one `429` with `Retry-After: 1` and `application/problem+json` and nothing but 404 and 429; three seconds later the address is served again;
  - a request with a forged `X-Forwarded-For: 203.0.113.99`: NGINX logs the address Caddy saw, neither the forged one nor Caddy's; a `token` query value reaches neither the Caddy nor the NGINX log; Caddy writes a JSON line with the query string removed;
  - `GET /api/v1/system/profile` through Caddy reports `deploy` `saas`; the site on `site.localhost` answers 200 with its own CSP and HSTS without `includeSubDomains`, and `check.mjs` answers 404;
  - audit anchor: `cli tenant create` adds a row to the platform audit chain, the job `audit.verify-chain` is queued through pg-boss inside the worker container, the script waits for "audit.verify-chain done", then asserts that the worker log has no line "not among the anchor keys compiled into this build" and that the worker wrote an `audit.anchor` line (so the key was really used).
- **down:** `docker compose down --volumes --remove-orphans` (cli profile included), then removes any container, volume or network still labelled with the project, the test images (unless `MSCD_SAAS_TEST_KEEP_IMAGES=true`) and the state folder. The images are removed by name: the names in `digests.json`, `localhost/<project>/mscd-server:<version>` and `localhost/<project>/mscd-web:<version>`, and every other tag under `localhost/<project>/`, so the images of a build that failed its gate (loaded, but no `digests.json`) go as well. `down` then lists what is left (containers, volumes, networks, images, state folder) and fails when anything is; the PASS line names the images only when they are gone, and says "images kept" with their names under `MSCD_SAAS_TEST_KEEP_IMAGES=true`. The "Clean start" of `up` uses the same check, so leftover images of an earlier run are removed too.

## Deviations

| # | Brief | Built | Why |
|---|---|---|---|
| 1 | `reverse_proxy web:8080` | `reverse_proxy {$MSCD_WEB_UPSTREAM:web:8080}`; Compose sets `MSCD_WEB_UPSTREAM=tcp4/<MSCD_WEB_EDGE_ADDRESS>:8080`, the web container's fixed IPv4 address on `edge` | With IPv6 on the edge network (deviation 4) the name `web` also resolves to an IPv6 address. ## Follow-ups

- **M2-S05 (deploy script):** write `.env` from `.env.saas.example` with the digests of `digests.json`, `MSCD_DOMAIN`, `MSCD_PUBLIC_URL`, `ACME_EMAIL`, `ACME_CA`, the SMTP values and `MSCD_SECRETS_DIR`; set `MSCD_EDGE_IPV6` from the server (false when it has no IPv6); refuse `MSCD_TLS_MODE=internal` on staging and production; when `MSCD_SITE_DOMAIN` is set, copy `apps/site/index.html`, `apps/site/id/` and `apps/site/assets/` of the release into `MSCD_SITE_DIR`. The order "staging CA first, then production CA" of `docs/saas/stack.md` belongs in its first-deploy steps. `caddy_data` must survive every deploy (never `down -v`).
- **IPv6 path not tested here:** the kernel of this build host has no IPv6, so `MSCD_EDGE_IPV6=true` was only checked with `docker compose config`. Check it on staging in the M2-S05 rehearsal or M2-S13: an IPv6 client must appear with its own address in the Caddy and NGINX logs.
- **STARTTLS is not enforced:** `secure: false` on port 587 upgrades to TLS when the provider offers STARTTLS (every transactional provider on 587 does and refuses the login without it), but nodemailer would continue in plain text if a man in the middle removed the offer. A profile key `mail.smtp.require_tls` (nodemailer `requireTLS`) needs the contract owner (R-14); then set it in `saas.yaml`.
- **Web base image on this host:** the default `MSCD_SAAS_TEST_SCAN=gate` needs a build machine that reaches the Alpine mirrors, or a web base image that already carries `brotli-libs` 1.2.1-r0 and `curl` 8.23.0-r0 (the open M2-S01 follow-up). Run acceptance line 4 once without `MSCD_SAAS_TEST_SCAN` on such a machine.
- **Seed and parity integration tests:** they fail on the pack version change of M2-03 (see the results); M2-03 updates the expected values or the sample.
- **`deploy/docker/README.md`** (no Milestone 2 owner) lists the settings of the web image; add `MSCD_RATE_LIMITS` and the five `MSCD_RATE_*` values.
- **On-premise bundle:** `install_config` of `lib/common.sh` copies every folder of `deploy/compose/config`, so bundles now also carry `config/caddy` (unused on-premise, harmless). `build-bundle.sh` could skip it.
- **M2-S08:** `conf.d/ops.caddy` can use `import mscd_tls` and `import mscd_log`. Caddy's admin endpoint (with its metrics) listens on 127.0.0.1:2019 inside the container only; to scrape Caddy, add a `metrics` site on the internal network in `ops.caddy` rather than opening the admin endpoint.
- **M2-S13:** add `deploy/scripts/test/saas-stack.sh` to the shellcheck step of `ci.yml`, and run its `up`, `check`, `down` in the `saas-smoke` job (GL-01, GL-03, GL-04, GL-20, GL-25 and GL-56 name it as evidence).
- **Records of processing:** the log retention is now 10 files of 20 MB per container; measure the days it covers after the first month (`docs/saas/records-of-processing.md`, owner M2-S04's document).
- **Plan text:** if the orchestrator accepts deviations 1, 2 and 5, the brief of M2-S02 in `docs/platform/MILESTONE-2.md` can say so.
